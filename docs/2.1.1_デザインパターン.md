## 1. 可用性・拡張性を高める構成（ロードバランサ）

### 要件と狙い
- ロードバランサを使った**高可用性構成**を実現する。

### 構成（図の再現）
- **さくらのクラウド** 内に、インターネットからの入口として **ルータ+スイッチ** を配置。
- **ロードバランサ(アプライアンス)** が負荷分散を担い、配下のスイッチを介して **Webサーバ#1 / Webサーバ#2** へトラフィックを振り分ける。
- Webサーバの背後に **データベースアプライアンス** を配置。
- 流れ: インターネット → ルータ+スイッチ → ロードバランサ(アプライアンス)〔負荷分散〕 → スイッチ → Webサーバ#1/#2 → データベースアプライアンス。

### 設計のポイント・根拠
- **拡張（スケール）操作はサーバ停止を伴う**ため、対象を**負荷分散の対象から除外してから**操作する。
  - サーバ拡張 = **プラン変更**。
  - ディスク拡張 = **ディスクをコピーしてサイズ拡張**。
- **ロードバランサ(アプライアンス)の仕様は固定**（要暗記）:
  - 振り分け方式 = **DSR方式**
  - 振り分けアルゴリズム = **最小接続数（Least Connection）**
  - 負荷分散レイヤ = **L4負荷分散**
  - → これらの固定仕様で**要件を満たさない場合の代替**:
    - **エンハンスドロードバランサ**（グローバル / **L7対応**あり）
    - **マーケットプレイスのネットワークサービス**（グローバル/プライベート, **L4〜L7対応**あり）
- **データベースアプライアンス**採用の根拠 = DBのサーバインフラ管理を省力化し、**Webサーバ環境の運用に注力**できる。

> 試験ポイント: アプライアンスLBは「**DSR / 最小接続数 / L4**」で固定。L7やグローバルが必要ならエンハンスドLB（またはマーケットプレイスNWサービス）へ。

## 2. コストパフォーマンスを意識した構成（CDN + オブジェクトストレージ）

### 要件と狙い
- **CDNとオブジェクトストレージを組み合わせて配信コストを効率化**する。

### 構成（図の再現）
- インターネットからのリクエストを**コンテンツ種別で振り分ける**。
  - **画像等の静的ファイルへのリクエスト** → **さくらのウェブアクセラレータ（CDN）** 経由で配信。CDNのバックエンド（オリジン）は **オブジェクトストレージ**。
  - **動的コンテンツへのリクエスト** → **オリジンのWebサーバ**側で応答（ゾーン内）。
- CDNバックエンド用ストレージに**安価なオブジェクトストレージ**を使い、配信コストを下げる。

### 設計のポイント・根拠
- **さくらのウェブアクセラレータ**
  - 要件にあわせて**ドメイン種別を選択**する。
  - **キャッシュ期間**は画像の更新頻度・配信容量を考慮し、**可能な限り長め**にすると **CDNの導入効果が最大化**される（オリジンへの到達を減らせる）。
- **オブジェクトストレージ（CDNオリジン時）**
  - CDNオリジンをオブジェクトストレージにする場合は**バケットの指定が必須**。
  - **1サイトにつき指定できるバケットは1つ**。大容量の場合は**バケット容量の上限**に注意し、**サイト設定/バケットを分割**する構成を検討（**サブドメインも複数必要**になる）。

> 試験ポイント: 静的=CDN(オリジンはオブジェクトストレージ)、動的=Webサーバ。1サイト1バケット制約／キャッシュ期間は長めが効果最大。

## 3. DR（Disaster Recovery）を実現する構成（GSLB）

### 要件と狙い
- **GSLBを活用**し、メインサイト障害時に**DRサイトへ切り替え**る。

### 構成（図の再現）
- サーバ前段に **GSLB** を配置。
  - 通常時 → **メインサイト**（**東京第2ゾーン**）に振り分け。
  - メインサイト障害時 → **DRサイト**（**石狩第3ゾーン**）に振り分け。
- 各サイトは「Webサーバ → スイッチ」の構成。
- 両サイトのサーバ間を **ブリッジ接続** 経由でデータ同期し、**DRサイト側を常に最新状態**に保つ。

| サイト | ゾーン | 役割 |
|--------|--------|------|
| メインサイト | 東京第2ゾーン | 通常時に振り分け |
| DRサイト | 石狩第3ゾーン | メインサイト障害時に振り分け |

### 設計のポイント・根拠
- **GSLB（広域負荷分散）の特性**
  - **DNSラウンドロビン相当**の負荷分散となる。
  - 要件を満たさない場合は **エンハンスドLB**（グローバル / **L7対応**あり）を検討。
- **DR要件とコスト効率のバランス（トレードオフ）**
  - 同一スペック/同一構成を複数サイトに常時起動する **ウォームスタンバイ構成** は、**コストが2倍**発生する。
  - DR要件に応じて、コスト最適化を検討:
    - **パイロットライト構成** = 通常時はDR側サーバを**停止**、障害検知時にDRサイトのサーバを**起動**。
    - **バックアップから復元する構成** 等。

> 試験ポイント: GSLB=DNSラウンドロビン相当。常時2サイト起動（ウォームスタンバイ）はコスト2倍 → パイロットライト/バックアップ復元でコスト最適化。

## 4. インターネットVPNを使用したユーザ拠点との接続構成

### 要件と狙い
- **インターネットVPN**で、ユーザ拠点とクラウドを**プライベートNW接続**する。
- **安価でセキュリティが担保**された接続環境を構築する。

### 構成（図の再現）
- **さくらのクラウド側**: アプリサーバ → スイッチ → **VPNルータ**。
- **利用者拠点側**: 拠点ユーザ → **拠点側VPNルータ**。
- クラウド側VPNルータと拠点側VPNルータ間を **インターネットVPN接続（サイト間VPN）** で結ぶ。
- 拠点ユーザは**プライベートNW接続**でクラウド上のアプリサーバへ通信する。

### 設計のポイント・根拠
- **VPN接続時の End to End での品質**
  - クラウド側/VPN対向拠点側で**回線品質が異なる場合、より低い品質が最大性能**となる（ボトルネックは弱い側）。
  - クラウド側プラン選定時は**対向側の回線品質に応じて適切なプランを選定**する。
- **高度なVPN仕様（動的ルーティング等）**
  - 複数WAN経由の**マルチセッションVPN接続**等、**BGPを使った動的ルーティング**前提の構成は **VPNルータでは対応できない**。
  - その場合は **VPNルータをマーケットプレイスのネットワークサービスに置き換える**ことを検討する。

> 試験ポイント: E2E品質は「低い側が上限」。BGP/動的ルーティング/マルチセッションはVPNルータ不可 → マーケットプレイスNWサービスへ。

## 5. ハイブリッド構成（さくらのクラウド + 専用サーバPHY）

### 要件と狙い
- **クラウドの柔軟性**と**物理サーバの処理性能**を組み合わせたハイブリッド環境。
- 各サービスの強みを活かす:
  - **Webサーバ** = 柔軟に**スケールアップ/ダウン**可能な**クラウド**を選択。
  - **データベースサーバ**（高パフォーマンス要求）= **物理専有サーバ（さくらの専用サーバPHY）** を選択。

### 構成（図の再現）
- **さくらのクラウド**: Webサーバ → スイッチ。
- **さくらの専用サーバPHY**: データベースサーバ ←→ ローカルネットワーク。
- クラウド側スイッチと専用サーバPHY側ローカルネットワークを **ブリッジ接続** で連結。

### 設計のポイント・根拠
- **Web/データベースサーバ間の通信要件（帯域）**
  - **専用サーバPHY側**はローカルネットワーク帯域 **2〜20Gbps** を使用可能。
  - **クラウド側**はサーバの**搭載メモリ量次第で 1〜10Gbps** の帯域を使用可能。
  - 必要帯域次第で、各環境のオプション追加/スペック増強を検討する。
- **データベースサーバのバックアップ**
  - **専用サーバPHYではバックアップサービスが提供されていない** → **マーケットプレイスのバックアップサービス**利用を検討する。

> 試験ポイント: 帯域は PHY=2〜20Gbps / クラウド=メモリ量依存1〜10Gbps。PHYは標準バックアップなし → マーケットプレイスで補う。

## 6. デザインパターン横断まとめ（代替サービスの定石）

要件が標準アプライアンスの固定仕様を超えるときの「乗り換え先」を整理（試験頻出）。

| 標準構成 | 固定/制約 | 要件を満たさない場合の代替 |
|----------|-----------|---------------------------|
| ロードバランサ(アプライアンス) | DSR / 最小接続数 / L4 固定 | エンハンスドLB（グローバル・L7）、マーケットプレイスNWサービス（L4〜L7） |
| GSLB | DNSラウンドロビン相当 | エンハンスドLB（グローバル・L7） |
| VPNルータ | BGP/動的ルーティング非対応 | マーケットプレイスNWサービス |
| 専用サーバPHY | バックアップサービスなし | マーケットプレイスのバックアップサービス |

## 7. 試験対策・要点チェック

- [ ] **アプライアンスLB**の固定仕様 = **DSR方式 / 最小接続数（Least Connection）/ L4**。L7・グローバルが要るなら**エンハンスドLB**かマーケットプレイスNWサービス。
- [ ] LB配下サーバの拡張（プラン変更/ディスクコピー拡張）は**サーバ停止を伴う** → **負荷分散対象から除外してから**操作。
- [ ] **DBアプライアンス**採用理由 = インフラ管理省力化でWeb運用に注力。
- [ ] CDN構成: **静的=ウェブアクセラレータ（オリジン=オブジェクトストレージ）/ 動的=Webサーバ**。
- [ ] CDNオリジンがオブジェクトストレージなら**バケット指定必須**、**1サイト1バケット**、容量上限注意（分割時はサブドメインも複数）。
- [ ] CDNの**キャッシュ期間は長めにするほど効果最大**。
- [ ] **GSLB = DNSラウンドロビン相当**。DR構成はメイン=東京第2ゾーン、DR=石狩第3ゾーン、**ブリッジ接続でデータ同期**。
- [ ] DRのコスト: **ウォームスタンバイ=常時2倍コスト** → **パイロットライト**（DR側通常停止/障害時起動）やバックアップ復元で最適化。
- [ ] **サイト間VPN（インターネットVPN）= 安価・セキュア**。E2E品質は**回線品質が低い側が上限**。
- [ ] **BGP/動的ルーティング/マルチセッションVPN**は**VPNルータ不可** → マーケットプレイスNWサービスへ置換。
- [ ] ハイブリッド: **Web=クラウド（柔軟スケール）/ DB=専用サーバPHY（高性能）**、間は**ブリッジ接続**。
- [ ] 帯域: **PHY=2〜20Gbps / クラウド=搭載メモリ量次第で1〜10Gbps**。
- [ ] **専用サーバPHYはバックアップサービスなし** → マーケットプレイスのバックアップサービスを検討。
