# 1.5.1 データ暗号化（KMS・クラウドHSM）

> 出典: SCA1.5.1_DataEncryption（さくらのクラウド検定アドバンスド教材, CC BY-SA 4.0 / さくらインターネット）
> 学習目標: さくらのクラウドで提供されるデータ暗号化に用いられるサービスの特性を理解し、要件に応じたデータ保護の設計と最適化ができる
> キーワード: KMS / シークレットマネージャ / クラウドHSM

---

## 0. 全体像（このノートの構成）

本テーマは STEP5「セキュリティとガバナンス」に属する。データ暗号化に関わる3つのマネージドサービスを扱う。

| サービス | 役割 | ひとことで |
|----------|------|-----------|
| **KMS（Key Management Service）** | 暗号鍵の生成・保管・管理 | 鍵のマネージドサービス |
| **シークレットマネージャ** | APIキー・パスワード等の機密情報の保管・管理 | 機密情報のマネージドサービス（KMSと連携して暗号化） |
| **クラウドHSM** | 暗号鍵を専用ハードウェア内で安全に保持・利用 | 専用ハードウェアによる鍵管理 |

## 1. KMS（Key Management Service）

### 1.1 概要
- さくらのクラウドのKMSは、**データの暗号化に使用する「暗号鍵」を安全に生成・保管・管理できる**サービス。
- 直感的な**コントロールパネル操作やAPI**を通じて、暗号鍵の**ライフサイクルを一元管理**できる。

### 1.2 エンベロープ暗号化（KMSがデータを暗号化する仕組み）【重要】
- 大量のデータを効率的に処理するため、さくらのクラウドのKMSは **「エンベロープ暗号化」** を採用。
- 鍵が2階層になっている:

| 鍵 | 役割 |
|----|------|
| **データ暗号キー（データ暗号化キー）** | 個々のデータを暗号化するための、**使い捨てに近い鍵** |
| **KMSキー** | データ暗号キー自体を暗号化して保護するための**マスターキー** |

**処理の流れ:**
1. **データ暗号キーでデータを暗号化**
2. **データ暗号キーを KMSキーで暗号化**
3. **暗号化されたデータとデータ暗号化キーをセットで保存**

> データと鍵の両方を保護することで、**鍵の漏洩リスクを低減**できる。

### 1.3 KMSキーの生成方法【重要】
KMSキーの作成には2つの方法がある。

| 生成方法 | 内容 |
|----------|------|
| **自動生成** | **FIPS 140-2 level 3 認証を受けた KMS内のHSM（Hardware Security Module）で生成**する |
| **BYOK（Bring Your Own Key）** | お客様独自の環境で生成した鍵情報を安全にKMSへインポートする。利用者環境で暗号鍵を生成し、KMSへアップロードしてKMSで管理する |

- **BYOK使用時の入力仕様**: 利用者環境で生成した **256 bit長**の暗号鍵を **base64エンコード**した状態で入力する。

### 1.4 KMSキーのステータス【最重要表】
KMSキーには「有効」「制限中」「一時停止中」「削除保留中」の4ステータスがある。

| ステータス | 説明 | 暗号化 | 復号 |
|------------|------|:---:|:---:|
| **有効** | 暗号化や復号などの操作が可能な状態 | ○ | ○ |
| **制限中** | 暗号化には利用できず、**復号のみ可能**な状態 | × | ○ |
| **一時停止中** | 暗号鍵を利用した操作が**一切できない**状態 | × | × |
| **削除保留中** | KMSキーは即座に削除できず、**削除予約**が行われる | － | － |

- **削除保留中の猶予日数**: **7～90日**。指定した猶予日数が経過するとKMSキーは**完全に削除**され、**削除されたKMSキーは復元できなくなる**。

### 1.5 KMSキーのローテーション【重要】
- KMSキーの**バージョンを手動で更新**することができる（キーマテリアルを変更）。
- **最新バージョンのKMSキーは暗号化・復号の両方が可能**。**古いバージョンは復号のみ利用可能**となる。

| | バージョン1（旧） | バージョン2（旧） | バージョン3（最新） |
|--|:---:|:---:|:---:|
| 暗号化 | × | × | ○ |
| 復号 | ○ | ○ | ○ |

### 1.6 KMSの利用例：ディスク暗号化機能
- サーバ上で行われるディスクへの読み書きに対し、それを受け持つ**クラウド基盤内の仮想デバイスドライバ**で**透過的に**KMSを用いた暗号化・復号処理を行い、データの安全性を高める。
- ディスクの暗号化キーをKMSで管理する。

### 1.7 KMSキーの操作（コントロールパネル）
- KMSキーは **「グローバル」カテゴリ内の「KMSキー」** からアクセスする。新規作成は「追加」ボタン。
- 「自動生成」を選択した場合、暗号鍵は **FIPS 140-2 level 3 認証を受けたHSM** によって生成される。
- 「BYOK」使用時は **256 bit長の暗号鍵を base64エンコード**して入力。
- 詳細画面（ダブルクリック or 右上の詳細ボタン）から以下を操作:
  - **KMSキーのステータス変更**: キーの状態を変更
  - **KMSキーのローテーション**: 作成済みKMSのキーマテリアルを変更
  - **KMSキーを削除**: 猶予日数（7～90日）経過後に完全削除、復元不可

### 1.8 KMS利用上の注意【重要】
- **KMSキーの削除は慎重に行う**。
- KMSキーを**他サービスと連携利用中**でも削除できるが、削除すると**連携中のサービスで暗号化/復号ができなくなる**。
- ステータスが**削除保留中**に、KMSキーの削除が原因で復号できないデータが検出された場合は、**削除をキャンセルすることで解決**できる。

## 2. シークレットマネージャ

### 2.1 概要
- **APIキーやパスワードなどのシークレット情報を安全に保管・管理**できるサービス。
- アプリケーションに認証情報を直接記載せず、**シークレットマネージャ経由で取得**することで認証情報を安全に管理。

### 2.2 ハードコーディングのリスク回避（利点）【重要表】

| 観点 | ハードコーディング | シークレットマネージャ利用 |
|------|--------------------|----------------------------|
| 方式 | 機密情報をコードや設定ファイルに直接書く<br>`config.database.password = "supersecret"` | 機密情報をコードの外で管理し実行時に取得<br>`config.database.password = ENV['DB_PASSWORD']` |
| 漏洩 | 共有・誤公開で漏洩しやすい | 共有・誤公開しても機密情報が漏れにくい |
| パスワード変更 | 変更のたびにコード修正や再デプロイが必要 | コード修正や再デプロイが不要 |
| 開発者 | 本来不要な機密情報を知る必要が出る | 本来知る必要のない機密情報を扱わずに済む |

### 2.3 利用例：データベースパスワードの管理
- アプリケーションサーバが**シークレットマネージャからデータベースのパスワードを取得**する。
- これにより、APIキーやパスワードを誤って公開する事故を防ぎ、コードや設定ファイルに機密情報を書き込まない運用が可能。
- **シークレットはKMSと連携して暗号化される**。

### 2.4 シークレットローテーション【重要】
- データベースのパスワードなどの機密情報を**一定の間隔で自動的に変更**し、安全な状態を維持する仕組み。
- 認証情報の使い回しを防ぎ、漏えい時の影響を最小限に抑え、**運用負荷の軽減**にもつながる。
- ローテーション設定（スケジュール）に従い、現在のパスワードを新しいパスワードへ更新する。
- **変更対象サービス**（※）: **データベースアプライアンス / エンハンスドデータベース**

### 2.5 シークレットマネージャ利用の流れ
1. **シークレット保管庫作成**: コントロールパネルでシークレット保管庫を作成し、**KMSキーを指定**
2. **シークレット情報登録**: 機密情報を暗号化して保管庫に登録（Secret 1, 2, …）
3. **シークレットローテーションの利用**: シークレットローテーション予定を作成し、シークレットを定期的に更新して利用

### 2.6 コントロールパネル操作
- **シークレット保管庫**: 「グローバル」カテゴリ内の「シークレット保管庫」→「追加」。作成時に**あらかじめ作成したKMSキーを指定**する。
- **シークレット作成**: 保管庫詳細画面＞シークレットタブから、**名前と値**を入力して作成。
- **シークレットローテーション予定**: 「グローバル」カテゴリ内の「シークレットローテーション予定」→「追加」。
  - **必須項目**: シークレット名 / **サービスプリンシパルID** / ローテーション間隔 / 対象種別（更新対象DBの選択）
  - 詳細画面から「**シークレットを今すぐ更新**」で手動ローテーション実行可能。シークレットは更新されると**バージョンが1つ上がる**。
  - 「シークレットローテーション予定を削除」で削除可能。

### 2.7 シークレットマネージャ利用上の注意【重要】

**KMSキーとの関係:**
- **KMSキーの削除はシークレット保管庫のデータを復元不能にする**。
- シークレット保管庫で使用する**KMSキーの管理はユーザーの責任**。誤ってKMSキーを削除・紛失すると、そのキーで暗号化されたシークレットデータは**クラウド事業者でも復元不可能**になる。
- 特にKMSキーを削除すると、保管庫内のデータも**二度と復号できなくなる**ため、削除操作は慎重に。

**サービスプリンシパルの権限（ローテーションの成否に直接影響）:**
- シークレットローテーションは、さくらのクラウドAPIを実行する**サービスプリンシパルIDの権限に依存**する。
- **更新対象リソースとシークレット保管庫の両方**に対する**設定編集権限**を付与する必要がある。
- いずれかの権限が不足している場合でも**スケジュールは有効だが更新実行は失敗**する。権限を修正後に**スケジュールを手動実行**することでシークレットを利用可能な状態に更新できる。

**ゾーンの制約:**
- シークレットローテーション予定は**更新対象リソースと同じゾーンで作成する必要がある**ため、他ゾーンのリソースは選択肢に表示されない。
- マルチゾーン構成ではゾーンをまたいだ一元管理はできず、**ゾーン単位で設計・管理**する必要がある。

## 3. クラウドHSM

### 3.1 概要
- 暗号鍵を**専用ハードウェア内で安全に保持・利用**するサービス。
- クラウド上で**秘密鍵を物理的に安全に管理**する専用ハードウェアリソース（**HSM: Hardware Security Module**）を提供。
- **FIPS 140-2／3 などの厳格なセキュリティ規格に準拠**した鍵管理が求められる場面で利用される。

### 3.2 HSM（Hardware Security Module）とは
- 秘密鍵の**生成・格納・管理・使用を保護する専用ハードウェア**。
- **物理的な取り出しやコピーができないように設計**されている。
- アプリケーションから暗号/署名リクエストを受け、**HSM内部で暗号化/復号を行い**、処理結果（暗号化データ/署名）を返す。秘密鍵はHSM内部に留まる。

### 3.3 クラウドHSMとKMSの比較【最重要表】

| | KMS | クラウドHSM |
|--|-----|-------------|
| 重視点 | **利便性と統合性** | **最高水準のセキュリティと専門性** |
| 性質 | 汎用的な鍵管理サービス | 専用ハードウェアによる保護 |
| 利用シーン | クラウドアプリケーションやシステムで**幅広く利用** | より**厳格なセキュリティや管理規則などの規制に適合が必要**なシナリオ |

### 3.4 サービス構成【重要】
- HSM内に切り分けた**パーティションをリソースあたり1つ**、**アプライアンス型**で提供。
- 利用者が作成したサーバに**クライアントソフトウェアをインストール**し、HSMパーティションへアクセスして使用する。
- **「スイッチ」及び「ローカルルータ」を使用しての閉域接続を基本**とする。
- 構成: クライアントソフトウェア（サーバ）→ スイッチ → ローカルルータ → クラウドHSM

### 3.5 仕様・サービスプラン【最重要表】

| 項目 | 仕様 |
|------|------|
| HSMハードウェア | **Luna Network HSM 7** |
| サービス利用料金 | **1パーティション** |
| パーティションスペック | **メモリ640KB、性能目安：RSA100 qps** |
| 仮想IPアドレス(VIP)、ポート番号 | **最大20個まで** |
| クライアントソフトウェアライセンス（クラウドHSMライセンス） | クラウドHSMへのアクセスに使用するソフトウェア。**1サーバ/VM毎にライセンスが必要** |

### 3.6 クラウドHSM利用の流れ
1. **事前申請・環境構築**: **エクストラサービス**から申し込みを行い、接続に必要なリソースを作成
2. **接続の確立**: クラウドHSMを作成後、**ローカルルータとピアリング**し、ネットワーク経由でクラウドHSMにアクセス
3. **クライアント準備**: クラウドHSMライセンスを取得後、サーバにクライアントソフトウェアをインストールし、利用を開始

### 3.7 鍵データの冗長化・バックアップ【重要】
- HSMリソース（パーティション）内の**データ管理は利用者で行う必要がある**。
- パーティション内に保管された鍵データについて、**さくらインターネットは内容に関与せず、冗長化やバックアップは提供されない**。
- 可用性や復旧性が求められる場合は、**複数パーティション契約による冗長構成**を検討する。

### 3.8 クラウドHSMライセンス【重要】
- クラウドHSMライセンスは、**クラウドHSMに接続するクライアントアプリケーションをインストールするサーバごとに必要**。
- **同一のHSMを利用する場合でも、サーバの台数が増えると必要なライセンス数も増加**する。
- 冗長構成やスケールアウト構成では、**VM増加に伴うライセンス数・コストの増加を前提に設計**する必要がある。

## 4. 試験対策・要点チェック

### KMS
- [ ] KMSは暗号鍵を**生成・保管・管理**するマネージドサービス。鍵の**ライフサイクルを一元管理**。
- [ ] KMSは **エンベロープ暗号化** を採用。**データ暗号キー**（使い捨てに近い）を **KMSキー**（マスターキー）で暗号化し、**暗号化データとデータ暗号化キーをセットで保存**。
- [ ] KMSキー生成は **自動生成**（FIPS 140-2 level 3 認証のHSMで生成）と **BYOK**。
- [ ] BYOKは **256 bit長**の暗号鍵を **base64エンコード**して入力。
- [ ] ステータス4種: **有効**（暗号化○復号○）/ **制限中**（暗号化×**復号○**）/ **一時停止中**（**両方×**）/ **削除保留中**（削除予約）。
- [ ] 削除予約の猶予日数は **7～90日**。経過後は完全削除で**復元不可**。
- [ ] ローテーション: **最新バージョン＝暗号化・復号OK / 古いバージョン＝復号のみ**。バージョン更新は**手動**。
- [ ] ディスク暗号化機能は**クラウド基盤内の仮想デバイスドライバで透過的に**暗号化/復号。
- [ ] KMSキーは「**グローバル**」カテゴリ。

### シークレットマネージャ
- [ ] APIキー・パスワード等の機密情報を保管・管理。**ハードコーディングを回避**。
- [ ] **シークレットはKMSと連携して暗号化**される。保管庫作成時に**KMSキーを指定**。
- [ ] **KMSキーを削除すると保管庫データは復元不可（事業者でも不可）**。KMSキー管理は**ユーザー責任**。
- [ ] シークレットローテーションの**変更対象サービス＝データベースアプライアンス / エンハンスドデータベース**。
- [ ] ローテーション予定の必須項目: シークレット名 / **サービスプリンシパルID** / ローテーション間隔 / 対象種別。
- [ ] ローテーションは**サービスプリンシパルの権限**に依存。**更新対象リソースと保管庫の両方に設定編集権限**が必要。権限不足でもスケジュールは有効だが実行は失敗 → 修正後に手動実行。
- [ ] ローテーション予定は**更新対象リソースと同じゾーン**で作成（ゾーンまたぎ不可）。
- [ ] シークレット更新で**バージョンが1つ上がる**。

### クラウドHSM
- [ ] 暗号鍵を**専用ハードウェア（HSM）内**で保持・利用。**FIPS 140-2／3** などの厳格な規格に準拠。
- [ ] HSMは秘密鍵の取り出し・コピー不可。**暗号化/復号はHSM内部**で行う。
- [ ] KMS＝**利便性・統合性・汎用**、クラウドHSM＝**最高水準のセキュリティ・専門性・規制適合**。
- [ ] **パーティションをリソースあたり1つ、アプライアンス型**で提供。**スイッチ＋ローカルルータで閉域接続**。
- [ ] ハードウェア＝**Luna Network HSM 7**。スペック＝**メモリ640KB、RSA100 qps**。VIP/ポートは**最大20個**。
- [ ] **ライセンスは1サーバ/VM毎に必要**（同一HSMでもサーバ増で増加）。
- [ ] 申し込みは**エクストラサービス**から。接続は**ローカルルータとピアリング**。
- [ ] **冗長化・バックアップは提供されない（利用者が管理）**。可用性が必要なら**複数パーティション契約**。
