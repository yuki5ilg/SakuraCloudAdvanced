# 1.1.2 アプリケーション連携

> 出典: SCA1.1.2_ApplicationIntegration（さくらの␣クラウド検定アドバンスド教材, CC BY-SA 4.0 / さくらインターネット）
> 学習目標: さくらのクラウドで提供されるアプリケーション連携に用いる各種サービスの特性を理解し、要件に応じたアプリケーション連携の設計と最適化ができる

## 0. アウトライン（取り扱うサービス）

| サービス | 一言で言うと |
|----------|--------------|
| シンプルMQ | マネージド型のメッセージキュー（非同期連携） |
| シンプル通知 | 任意のタイミングでメール/Webhook通知を送るサービス |
| EventBus | 変更検知/スケジュールで自動的にジョブを実行するサービス |
| APIゲートウェイ | APIを簡単に作成・公開し一元管理するマネージドサービス |
| Workflows | YAML(Runbook)で処理手順を定義し自動実行する仕組み |
| Add-on | さくらのクラウドを経由して利用できる拡張機能群 |

## 1. シンプルMQ

### 概要
- **マネージド型のメッセージキューサービス**。
- ソフトウェアコンポーネント間でデータを**非同期に送受信**できるメッセージキュー機能を提供。
- 処理の遅延を抑えつつシステム内の連携を効率化できる。
- **APIによる柔軟な操作**が可能。

### メッセージキューとは
- 処理したいデータ（メッセージ）を**一時的に順番待ちで保存**し、**送信側と受信側を直接つながずに**連携させる仕組み。
- 処理速度や稼働タイミングが異なるシステム同士でも、安定して**非同期**に処理を進められる。
- 登場人物: **Producer（送信側）** → キューに登録 → **Consumer（受信側）** がキューから受信。

### 基本仕様（最重要表）

| 項目 | 仕様 |
|------|------|
| 配信順序 | 原則として **FIFO（先入れ先出し）**。ただし**完全な順序保証ではない** |
| 配信保証 | **少なくとも1回配信（At-Least-Once）**。**重複配信が発生する可能性あり** |
| メッセージ最大サイズ | **256KB** |
| バイナリデータ | **直接送信不可**。**Base64エンコード**して送信する必要がある |

### 可視性タイムアウト
- 処理の重複を防ぐために、**キューから受信したメッセージを他の受信リクエストには受信させないようにしておく時間**。
- 受信したあと**完了リクエストを送られないまま**この秒数が経過すると、該当メッセージは**再び受信可能**となる。
- 【Tips】受信後のメッセージに対して**可視性タイムアウトを延長するAPI**が提供されている。処理中に延長し、処理完了前の再配信を防ぐ。
  - 外部API応答待ちや大容量データ処理では想定以上に時間がかかる場合がある。
  - 一方、あらかじめ極端に長い可視性タイムアウトを設定すると**障害発生時の再試行が遅れる**。
  - → 適切な可視性タイムアウトを設定したうえで、必要に応じて延長する実装を検討する。

### 未処理メッセージ保存期間
- キューに登録されたメッセージが**削除されるまでの最大保存時間**。
- **受信リトライの回数に関係なく**、登録後にこの時間を超えたメッセージは**自動的に削除**される。

### 利用例：注文完了処理（画面表示＋通知メール非同期）
- Webサーバは内部処理後に注文完了画面を返却し、メール処理はキューへ登録。
- メールサーバはシンプルMQからメッセージを取得し、メール送信を非同期で実行。
- 注文完了画面の表示: **1→2→3**（リクエスト受信→内部処理→レスポンス送信）
- 注文完了の通知メール送信: **1→2→a→b→c**（a.メッセージ送信(登録)→b.メッセージ受信(取得)→c.メール送信処理）
- → 注文受付とは**非同期**で通知メールを送信。

### 作成・管理（コントロールパネル操作）
- **「グローバル」カテゴリ内の「シンプルMQ」**からアクセス、「追加」で新規作成。
- 作成時に**キュー名**を設定。**作成後のキュー名の変更はできない**。
- 作成後、**APIキーが一度だけ表示される**。**再表示はできない**が、紛失した際には**APIキーの再発行が可能**。
- 詳細画面の操作:
  - 「メッセージ数の取得」: キュー内のメッセージ数を確認 ※テキスト原文は「メッセージ数の所得」と誤記
  - 「APIキーの再発行」: APIキーを再発行
  - 「キュー設定変更」: **可視性タイムアウト**や**未処理メッセージ保存期間**を変更
  - 「キュー内メッセージを削除」: キュー内の**すべてのメッセージを削除**
  - 「シンプルMQを削除」: 対象のキューを削除

### 利用上の注意（試験頻出）
- **メッセージは複数回配信される可能性がある**（可視性タイムアウトや再試行の影響で一部メッセージが2回以上配信され得る）。
  - → コンシューマ側で**冪等（同一処理を重複して行っても影響がない）設計**を考慮する必要がある。
- **キュー名は作成後に変更できない**。作成時の一度のみ設定可能で、**プロジェクト内では同一名のキューを重複して作成できない**。
  - 変更したい場合は、新しい名前でキューを作成し、送受信先を切り替えた上で旧キューを削除する。
- **APIキーの画面表示は一度だけ**。紛失したら再発行し、アプリケーション側の設定を新しいキーに更新する。

### 試験対策・要点チェック（シンプルMQ）
- [ ] 配信順序＝**原則FIFO（完全保証ではない）**、配信保証＝**At-Least-Once（重複あり）**。
- [ ] 最大サイズ＝**256KB**、バイナリは**Base64エンコード必須**。
- [ ] 重複配信があるので**コンシューマは冪等設計**。
- [ ] **可視性タイムアウト＝受信中に他から見えなくする時間**、延長APIあり。
- [ ] **キュー名は作成後変更不可**、**APIキーは一度だけ表示・再発行可**。

## 2. シンプル通知

### 概要
- **任意のタイミングで通知を送信するサービス**。
- **メールまたはWebhook**を使って通知を送信できる。
- 通知先を**グループ化**して用途ごとに管理可能。
- **API、モニタリングスイート（アラート）、EventBus**から呼び出して通知が可能。

### 呼び出し元
- **通知API / モニタリングスイート（アラート） / EventBus** の3つから呼び出しに対応。
- 呼び出し元 → 通知の送信（通知先グループ・通知するメッセージ等を指定）。

### 利用できる通知方法（重要表）

| 通知方法 | 内容 |
|----------|------|
| メール | 通知先アドレスにメールが送信される。**本登録にはメールアドレスの認証が必要** |
| Webhook | 指定したWebhook URLに**POSTリクエスト**で通知。**Slack、Discord、Microsoft Teams、IFTTT、Zapier**で動作確認済み |

### 利用例：監視対象サーバでの異常発生時のメール通知
- モニタリングスイートであらかじめ設定した**アラート条件に一致**すると、判定結果が自動的にシンプル通知へ連携。
- シンプル通知は受け取ったアラートイベントをもとに、事前設定の通知先・通知方法に従ってメール等で利用者へ通知。
- フロー: サーバ（メトリクス/ログ収集）→ モニタリングスイート（アラート通知）→ シンプル通知（通知先アドレスにメール送信）→ 利用者。

### 利用の流れ（3ステップ）
1. **通知先を登録する**（通知を送信する個々の送信先を登録: メール/Webhook）。
2. **通知先グループを作る**（用途ごとにグループ化して運用）。
3. **通知を設定する**（呼び出し元から通知を送る仕組み＝通知ルーティングを設定）。

### 作成・管理（コントロールパネル操作）
- **「シンプル通知」カテゴリ内の「通知先」**からアクセス、「追加」で新規作成。**通知先タイプと通知先アドレス**を設定。
- 通知先アドレス宛に**本登録手続き用の通知メール**が送信される。
  - **本登録完了までの間、通知先の有効状態は「本登録待ち」**となり、通知先として利用できない。
- **「通知グループ」**から作成し、**作成した通知先を選択**。
- **「通知ルーティング」**から作成し、**通知先グループと通知を受け取るサービス**を選択。
- ルーティング詳細画面: 「設定を変更」（通知先グループや受信サービスを変更）、「通知先ルーティングを削除」。

### 利用上の注意：通知送信数の上限（試験頻出・要暗記）
- **通知先グループ単位**で:
  - **10分間あたり最大 1,200件**
  - **1日あたり最大 1,500件**（**JST 03:00 リセット**）
- 配信数の上限を超える要件（短時間に大量の通知を送る用途など）がある場合は、別の仕組みを検討する。

### 試験対策・要点チェック（シンプル通知）
- [ ] 通知方法＝**メール / Webhook**。Webhookは**POST**、Slack/Discord/Teams/IFTTT/Zapierで動作確認済み。
- [ ] 呼び出し元＝**通知API / モニタリングスイート（アラート） / EventBus**。
- [ ] メールは**本登録に認証が必要**、未完了は「**本登録待ち**」で利用不可。
- [ ] 送信上限＝通知先グループ単位で**10分1,200件 / 1日1,500件（JST 03:00リセット）**。

## 3. EventBus

### 概要
- **変更検知を利用して、自動的にジョブを実行するサービス**。
- **イベント検知サービスとジョブスケジュールサービスを統合**したマネージドサービス。
- 定期的なジョブの実行や、イベントを検知してジョブを実行できる。
- **APIベースの操作**で外部サービスとの連携が簡単。

### 対応ジョブ（実行先）
- **シンプル通知 / シンプルMQ / オートスケール** でのジョブ実行が可能。
  - シンプル通知: メールやアプリへ通知
  - シンプルMQ: メッセージをキューに登録
  - オートスケール: サーバの自動増減

### 対応トリガー（重要表）

| トリガー | 内容 |
|----------|------|
| スケジュール | 指定した時間間隔でジョブを実行。周期は**最短1分**から設定できる |
| イベント検知 | 特定のイベント発生時にジョブを実行。対応ソース: **モニタリングスイート（アラート）／イベントログ** |

### 利用例：新規サーバ作成時の自動記録・通知
- さくらのクラウドでサーバが作成されると、その操作が**イベントログに記録**される。
- EventBusはサーバ作成イベント（**`Server.created`**）をトリガーとして、運用チャンネルへ自動通知（シンプル通知経由・Webhook）。
- 通知例: 「新規サーバが作成されました 2026-01-11-11:11, ゾーン：石狩第1, リソースID：111111111111」。

### 利用の流れ
1. **事前準備**: APIキーを発行し、通知先サービスを準備する。
2. **実行設定を作成する**: EventBusで実行する内容（ジョブ）を実行設定として登録。
   - 例（シンプル通知）: 通知先グループ / メッセージ / APIキー情報。
3. **スケジュールを作成する**: ジョブを定期的に実行する場合。
3'. **トリガーを作成する**: イベント検知でジョブを起動したい場合。

### 作成・管理（コントロールパネル操作）
- **「EventBus」カテゴリ内の「実行設定」**からアクセス、「追加」で新規作成。選択サービスにより設定項目が変化。
  - シンプル通知の例: **グループ**（通知先グループ名）/ **メッセージ** / **APIキーのアクセストークン** / **APIキーのアクセストークンシークレット**。
- **「スケジュール」**: 実行設定を選択しスケジュールタイプを選択。
  - **実行間隔** / **実行間隔の単位（日・時間・分から選択）** / **実行開始時刻**。
- **「トリガー」**: 実行設定を選択し、**ソース**（イベントの送出元）/ **タイプ**（イベントのタイプ）/ **条件**（キーとそのキーが取りうる値）を選択。
- 実行設定の詳細: 「実行設定のシークレット設定」「実行設定を変更」「実行設定を削除」。

### 利用上の注意（試験頻出）
- **ジョブの実行はベストエフォート型**で、厳密なリアルタイム性は保証されない。
  - スケジュールは最短1分単位で設定できるが、**厳密な実行時刻は保証されない**。
  - 秒単位の正確さが必要な用途には向かない。重要な処理では**遅延を前提にした補完設計**が必要。
- **EventBus連携時のオートスケール設定に注意**:
  - EventBusとオートスケールの双方が同時にスケール判断を行うと、意図しない増減や振る舞いが発生する可能性。
  - **EventBusからオートスケールを実行する場合、オートスケール側の自動スケーリング機能は無効化しておく必要がある**。

### 試験対策・要点チェック（EventBus）
- [ ] **イベント検知＋ジョブスケジュールを統合**したサービス。
- [ ] 対応ジョブ＝**シンプル通知 / シンプルMQ / オートスケール**。
- [ ] トリガー＝**スケジュール（最短1分）／イベント検知（ソース: モニタリングスイート・イベントログ）**。
- [ ] **ベストエフォート型**で実行時刻は保証されない。
- [ ] **EventBusからオートスケール実行時はオートスケール側の自動機能を無効化**する。

## 4. APIゲートウェイ

### 概要
- **APIを簡単に作成・公開し、一元管理できるマネージドサービス**。
- さくらのクラウド上のWebアプリやオブジェクトストレージなど、**任意のバックエンドにアクセスするAPIを作成**できる。
- 入力リクエスト・出力レスポンスに対して**変換や加工**を行う設定が可能。
- **複数の認証方式**をサポートし、セキュリティを担保しつつ柔軟なアクセス制御が可能。

### 主要な構成要素
- **サービス**: APIゲートウェイが管理する**バックエンドサービスのエンドポイントを指定**する。
  - HTTP(S)エンドポイント: バックエンドにアクセスするためのURLなどを設定。
  - オブジェクトストレージ: アクセスするためのエンドポイントやバケット名などを設定。
- **ルート**: クライアントから送られたリクエストを**適切なバックエンドサービスにルーティング**する。
  - 例: `GET /profile`→ユーザーサービス、`POST /login`→認証サービス、`GET /notifications`→通知サービス。

### アクセスの制御：認証方法（重要表）
- 認証機能を用いて、**APIごとにユーザ認証**が可能。

| 認証方法 | 概要 |
|----------|------|
| BASIC認証 | ユーザー名とパスワードを**HTTPヘッダに載せて送信** |
| HMAC認証 | **秘密鍵を使ってリクエストに署名**し、改ざんを検証 |
| JWT | **署名付きトークン**でユーザー情報を表現 |
| OIDC認証 | **外部の認証基盤でログイン**し、結果を利用 |

### リクエスト・レスポンス変換
- クライアントとバックエンド間で、通信内容（リクエスト・レスポンス）を**通過中に書き換える**ことができる。
- API仕様の違いや変更を間で吸収でき、**互換性維持・安全な公開**などが可能。
- 例: リクエスト変換で `user_id → userId`（Rename）、レスポンス変換で `internalFlag` を削除（Remove）。

### ドメイン・証明書設定
- 外部公開APIを**独自ドメイン**で提供可能。
- 利用中のDNSサーバ上で、ドメイン名と **`cname.tk1.apigw.sakura.ne.jp`** との**名前解決（CNAME）**が設定されている必要がある。
  - 例: `example.com IN CNAME cname.tk1.apigw.sakura.ne.jp`
- **HTTPS通信を行う場合は、事前にTLS/SSL証明書を発行して追加**する。
- APIゲートウェイ側でドメイン管理に独自ドメインを設定し、**ルート作成時にそのドメインを選択**する。

### 利用例：サーバレスWebアプリケーションの構築
- 管理者が登録したコンテナイメージをAppRunが読み込み、オートスケールする実行基盤としてアプリを動作させる。
- 外部からのアクセスはAPIゲートウェイで受け付け、AppRun上のアプリをAPIとして公開。
- 構成: ユーザ → インターネット → APIゲートウェイ → AppRun(オートスケール) ←コンテナレジストリ。

### 利用の流れ（3ステップ）
1. **APIゲートウェイ有効化**（コントロールパネルから新規契約）。
2. **サービス作成**（バックエンドサービスのエンドポイントを設定）。
3. **ルート作成**（リクエストを適切なバックエンドサービスに転送するルートを設定）。

### 作成・管理（コントロールパネル操作）
- クラウドホームのトップから「APIゲートウェイ」を選択。
- 新規利用は**契約**を行う（契約の名前を入力して契約）。
- 契約完了後「サービス一覧」→「サービス作成」。**サービス名を入力し紐づける契約を選択**。
  - ※**作成後に関連付ける契約を変更することはできない**。
- 「サービス一覧」から作成したサービスを選択 →「ルート一覧」→「ルート作成」。
- ルート設定項目:
  - **名前**: 任意のルート名
  - **プロトコル**: **http / https / http/https**
  - **ホスト**: 自動発行されるホスト値、またはドメイン管理にて設定したドメイン
  - **パス**: 任意のパス
  - **HTTPメソッド**: ルートへのアクセスメソッド

### 利用上の注意（試験頻出）
- **オブジェクトストレージ向け接続におけるHTTPメソッド制限**:
  - APIゲートウェイでオブジェクトストレージをバックエンドとして利用する場合、使用できるHTTPメソッドは **GET / HEAD / OPTIONS のみ** に制限される。
  - **書き込み系のAPIを構築する場合は、コンテナやサーバーなど別のバックエンドを利用する**必要がある。

### 試験対策・要点チェック（APIゲートウェイ）
- [ ] 構成要素＝**サービス（バックエンドのエンドポイント）/ ルート（ルーティング）**。
- [ ] 認証方法4つ＝**BASIC / HMAC / JWT / OIDC**。
- [ ] **リクエスト/レスポンス変換**で互換性吸収（Rename・Remove等）。
- [ ] 独自ドメインは **`cname.tk1.apigw.sakura.ne.jp`** へのCNAME、HTTPSはTLS/SSL証明書を事前発行。
- [ ] **作成後に契約は変更不可**。
- [ ] **オブジェクトストレージをバックエンドにする場合はGET/HEAD/OPTIONSのみ**（書き込み不可）。

## 5. Workflows

### 概要
- **リソース操作やAPI呼び出しを定義どおりに自動実行する仕組み**。
- **YAML形式のRunbook**で処理手順を定義し、さくらのクラウド上で繰り返し実行できる。
- シリアル処理に加え、**並列実行、条件分岐、ループ、エラー処理**を記述できる。
- **HTTP API / さくらのクラウドAPI / AppRun** を利用して外部サービス連携やクラウドリソース操作ができる。

### Runbook の構成
- YAML形式のランブック（Runbook）に処理手順を記述。
- ランブックは **meta・args・steps** から構成され、**リビジョンやリビジョンエイリアス**によって改版を管理できる。

| キー | 内容 |
|------|------|
| `meta` | メタ情報を記述 |
| `args` | 実行時に渡す引数の定義を記述 |
| `steps` | 各ステップを記述（**上から順に実行される**） |

### フロー制御
- **シリアル処理**（ステップを順番に実行）に加え:
  - **`parallel`** による並列実行
  - **`switch` / `for` / `try-except`** などによる条件分岐・ループ・エラー処理
- 処理の依存関係やエラー時の挙動を明示しながら柔軟なフロー制御が可能。

### 外部サービス・クラウド連携
- **`call` ステップ**を用いて以下を実行できる:
  - HTTP APIによる**外部サービス呼び出し**
  - さくらのクラウドAPIによる**クラウドリソース操作**
  - **AppRun API**によるアプリケーション操作
- サーバの起動・停止からクラウド運用、業務処理をワークフローとして自動化できる。

### 利用例：サーバの自動リカバリー処理
- サーバの状態をWorkflowsで確認し、**停止（DOWN）していた場合に自動で起動**する。
- 人が手動で確認・操作しなくても、サーバの**自己復旧**を実現。
- フロー: 開始→サーバのステータスチェック→分岐（DOWN: サーバ起動／UP: 終了）。

### 利用の流れ（3ステップ）
1. **プラン設定**: コントロールパネルで利用するプランを選択（**600Kプラン / 200Kプラン**）。
2. **ワークフローの作成**: 名前・説明等を設定し、YAML形式でRunbookを記述。
3. **ワークフローの実行**: 「最新のリビジョンで実行」を行い、実行画面で引数を入力してワークフローを開始。

```yaml
meta:
  description: サンプルワークフロー
args:
  sample:
    type: number
    description: サンプル引数
steps:
  result:
    return: ${args.sample * 2}
```

### 作成・実行（コントロールパネル操作）
- Workflowsのプランを選択し利用開始 →「ワークフロー一覧」→「ワークフローを作成」。
- **実行の制御方法**を選択:
  - **並列実行**: 同時に複数の実行が可能
  - **直列実行**: 前の実行が完了するまで次の実行は待機
  - **初回優先**: 実行が完了するまで追加の実行はできないようにする
- **ワークフロー名**を入力。他サービスとの連携を行う場合は**サービスプリンシパルID**を入力。
  - ※**サービスプリンシパルIDはワークフロー作成後に変更できない**。
- Runbookを**YAML形式**で入力。
- 実行: 「最新のリビジョンで実行」→ 実行時の名前や引数を入力（**入力値はJSON形式で指定**）→ 実行。
- 実行後に返された出力が表示され、ステータス表示。名前をクリックで実行履歴詳細画面へ遷移。

### 利用上の注意：制限事項（最重要表・要暗記）
- ワークフローには**ステップ数・サイズ・並列度・実行時間などの制限**がある。
- 長時間・大規模な処理は**タイムアウトを避けるためRunbookを小さな単位に分割**し、複数のワークフローとして実行する必要がある。

| 項目 | 上限値 |
|------|--------|
| RunbookのYAMLでの最大サイズ | **256KB** |
| Runbookの最大ステップ数 | **5000ステップ** |
| Runbookでの並列ステップの最大数 | **100ステップ** |
| ワークフローの最大実行時間 | **1年** |
| 完了した実行履歴の保持期間 | **90日間** |

※詳細はクラウドマニュアルを確認（教材注記）。

### 試験対策・要点チェック（Workflows）
- [ ] 定義は**YAML形式のRunbook**、構成は **meta / args / steps**（stepsは上から順に実行）。
- [ ] フロー制御＝**parallel（並列）/ switch・for・try-except（分岐・ループ・エラー）**。
- [ ] 外部連携は **`call` ステップ**（HTTP API / さくらのクラウドAPI / AppRun API）。
- [ ] プラン＝**200Kプラン / 600Kプラン**。実行制御＝**並列 / 直列 / 初回優先**。
- [ ] **サービスプリンシパルIDは作成後変更不可**、実行引数は**JSON形式**。
- [ ] 制限: **YAML 256KB / 5000ステップ / 並列100 / 最大実行1年 / 履歴保持90日**。

## 6. Add-on

### 概要
- **さくらのクラウドを経由して利用できる多様な拡張機能群**（Add-onサービス）。
- さくらのクラウドを**補完**する機能をさくらのクラウドを経由して提供する。
- データ分析やグローバルに展開されるCDNサービスなど、各種機能を補完できる。
- **行政機関、法人その他の事業者を対象**としたサービス。

### 提供機能：データ分析

| サービス名 | サービス概要 |
|------------|--------------|
| データレイク/データウェアハウス | 大量データの蓄積と高速な分析を実現する基盤のサービス |
| データ処理/ETL | 多様なデータを抽出、変換、統合し、分析可能な形に整えるサービス |
| データ検索 | 必要な情報を迅速に見つけ出す検索機能のサービス |
| データ可視化/BI | データを視覚化し、ビジネスインサイトを効果的に把握するサービス |

### 提供機能：ネットワーク・セキュリティ

| サービス名 | サービス概要 |
|------------|--------------|
| DDoS対策 | 大規模攻撃からシステムを守るDDoS対策のサービス |
| WAF機能 | ウェブアプリへの不正アクセスを検知・防御するWAFのサービス |
| 脆弱性検知 | システムの弱点を早期に発見する脆弱性検知のサービス |
| グローバルCDN | 世界中のユーザーに高速で安定したコンテンツ配信を実現するCDNサービス |

### 提供機能：システム開発

| サービス名 | サービス概要 |
|------------|--------------|
| コードリリース | ソフトウェアのバージョン管理と安全なリリースプロセスのサービス |
| 機械学習/AI | OCR（文字認識）や文字起こしの機能をAPI経由で利用するサービス |

### 利用の流れ（3ステップ）
1. **申し込み手続き**: エクストラサービスのフォームから利用申請を行う。
2. **審査・承認**: さくらインターネット側で申請内容の審査を実施。
3. **Add-onの利用開始**: マニュアルを参考にAdd-onサービスの設定を行う。

### ベストプラクティス（Tips）
- クラウドマニュアルの**最適設計ガイドライン**に、Add-onサービスを用いたシステム構築のベストプラクティスが示されている。
- **Terraformやその他の設定ファイルを含むサンプル**が公開されており、構成例ごとにディレクトリが整理されている。
- URL: `https://manual.sakura.ad.jp/cloud/optimal-architecture/appendix_B/add-on_best_practice.html`

### 試験対策・要点チェック（Add-on）
- [ ] Add-onは**さくらのクラウドを"経由"して提供される補完機能群**、**行政機関・法人等を対象**。
- [ ] 提供領域＝**データ分析 / ネットワーク・セキュリティ / システム開発**。
- [ ] 利用の流れ＝**申し込み → 審査・承認 → 利用開始**（審査がある点に注意）。

## 7. 横断・総合 要点チェック

- [ ] **シンプルMQ**: At-Least-Once（重複あり）、256KB、Base64、可視性タイムアウト、冪等設計、キュー名変更不可。
- [ ] **シンプル通知**: メール/Webhook、呼び出し元はAPI/モニタリングスイート/EventBus、上限**10分1,200件・1日1,500件（JST3:00）**。
- [ ] **EventBus**: スケジュール（最短1分）＋イベント検知、対応ジョブ=通知/MQ/オートスケール、ベストエフォート、オートスケール二重制御に注意。
- [ ] **APIゲートウェイ**: サービス/ルート、認証4種（BASIC/HMAC/JWT/OIDC）、CNAMEは`cname.tk1.apigw.sakura.ne.jp`、オブジェクトストレージはGET/HEAD/OPTIONSのみ。
- [ ] **Workflows**: YAML Runbook（meta/args/steps）、callステップ、制限（256KB・5000ステップ・並列100・実行1年・履歴90日）。
- [ ] **Add-on**: 経由提供の補完機能、申し込み→審査→利用開始。
