# 2.2.2 中規模システムにおけるアーキテクチャ設計

> 出典: SCA2.2.2_ArchitectureDesign-for-MediumScaleSystems（CC BY-SA 4.0 / さくらインターネット）
> 位置づけ: 2.2 ケーススタディ。中規模システムの「冗長構成の基本パターン」を3つのケースで学ぶ。
> 学習ポイント: クラウドを使った冗長構成の基本パターン／LB（L4 vs L7）の選択／CDN＋LB配信／GSLBによるDR構成。

中規模は **「単一障害点(SPOF)を排除した冗長化」＋「マネージドサービスで運用負荷軽減」** が共通テーマ。
共通スペック前提: **Web/APサーバ2台、DBサーバ2台**、HTTPS公開・独自ドメイン利用。

---

## ケース1: 可用性を重視したコンテンツ配信（CDN＋L7 LB）

### 業務背景・要件
- CMSを使ったBtoB向けSaaS。インターネット公開、利用者増に伴う**性能・可用性向上**が必要。
- Web/AP（CMS）2台（**Act/Act**）、DB 2台（**Act/Stn**）。
- 月間PV: 数十万〜100万、月間トラフィック: 閑散期〜1TB／繁忙期〜10TB。
- 帯域: 閑散期100Mbps／繁忙期500Mbps。静的コンテンツ〜合計1TB（〜100万ファイル）。
- 要件: アクセス増でも安定応答／Web・DB層を冗長化しSPOF排除／マネージド優先／**静的コンテンツはCDN**／ストレージ層はスケーラブル。
- CMS制約: **セッション維持が必要**。スケールアウト前提で**セッションはCMS内部に保持しない**。構成のシンプルさを優先し **L7 LBのスティッキーセッション方式**を採用（障害時の再ログイン発生は許容）。CMSは画像格納先として **ローカル／NFS／S3互換オブジェクトストレージ**をサポート。

### 選択肢（負荷分散）
| 選択肢 | 特徴 | 本ケースの判断 |
|--------|------|----------------|
| ロードバランサ（アプライアンス） | **L4(TCP)・DSR型**。LBでセッション維持不可（CMS内部か外部ストアで管理が必要）。マネージド | **要件に不適切** |
| **エンハンスドロードバランサ** | **L7(HTTPS)・プロキシ型**。LBでセッション維持可（**スティッキーセッション機能**）。マネージド | **適切** |
| マーケットプレイスのネットワークサービス | L4/L7対応、インライン/ワンアーム等複数配置。セッション維持可。学習/運用コスト高 | LBで高度処理が必要な場合の代替案 |

### 選択肢（CDN）
| 選択肢 | 特徴 | 本ケースの判断 |
|--------|------|----------------|
| **ウェブアクセラレータ（独自ドメインに新規サブドメイン）＋オリジン=オブジェクトストレージ** | 静的コンテンツのみCDN経由。**CMSに改修要**（静的コンテンツはオブジェクトストレージに保存し、CMSから参照） | **適切** |
| ウェブアクセラレータ（独自ドメイン方式）＋オリジン=Webサーバ＋NFSに静的保存 | **サイト丸ごとCDN経由・CMS改修不要**。Webサーバにキャッシュ制御設定が必要。不要キャッシュをオリジンで制御。独自ドメインのエイリアスに切替時間。**全アクセスがCDN経由で配信コスト増の懸念** | CMSに手を入れたくない場合の代替案 |

### 採用構成
- 構成要素: **グローバルNW（ルータ＋スイッチ）→ パケットフィルタ → エンハンスドロードバランサ → Web/AP 2台 → DBアプライアンス(冗長化オプション)**。**ウェブアクセラレータ**でコンテンツ配信、**オブジェクトストレージ**に静的コンテンツ保存（取得時は直接アクセス）。
- 代替案: 静的コンテンツを**NFSアプライアンス**に保存しWeb/APからマウント。

### 判断ポイント
- L4/L7どちらのLBを選ぶかは**アプリのセッション維持方式の要件**で変わる。
- CDNは静的コンテンツ配信のオフロード目的。大量ファイルはオブジェクトストレージでコスパとスケーラビリティ確保。
- **CDN運用**: キャッシュ対象・TTL・更新反映方法を事前定義。保持期間最適化（表示不整合リスク注意）。**動的コンテンツ・ログイン後/管理画面など状態を持つページ・個人情報はキャッシュ対象外**。
- ⚠️ **エンハンスドLBのCPS性能は、HTTPS通信の場合プラン表示の1/10**になる点に注意してプラン選択。
- ⚠️ **NFSアプライアンスはシングル構成**での提供。冗長構成にするなら利用者側でNFSサーバを構築・冗長化。
- より高い可用性が必要ならオートスケール運用を検討。

## ケース2: WebシステムのTCP負荷分散（L4 LB）

### 業務背景・要件
- BtoCの会員向け**健康管理ダッシュボード**。体重・運動時間を記録しグラフを都度更新。スマホアプリ＋Webブラウザ双方から利用。
- Web/AP 2台（**Act/Act**）、DB 2台（**Act/Stn**）。HTTPS公開・独自ドメイン。
- MAU: 1〜10万人。月間PV(API＋Web)〜1,000万、月間リクエスト〜3,000万。月間トラフィック500GB〜1TB。帯域100Mbps。
- アプリ制約: ユーザー固有データを準リアルタイム更新。**ロードバランサはTCPで分散する方式**をとる。

### 選択肢（負荷分散）
| 選択肢 | 特徴 | 本ケースの判断 |
|--------|------|----------------|
| **ロードバランサ（アプライアンス）** | **L4(TCP)・DSR型**。LBでセッション維持不可（APサーバ内部か外部ストアで管理）。マネージド | **適切** |
| エンハンスドロードバランサ | L7(HTTPS)・プロキシ型。セッション維持可。マネージド | **要件に不適切** |
| マーケットプレイスのネットワークサービス | L4/L7対応・複数配置。セッション維持可。学習/運用コスト高 | LBで高度処理が必要な場合の代替案 |

### 選択肢（グローバルネットワーク）
| 選択肢 | 特徴 | 本ケースの判断 |
|--------|------|----------------|
| 共有セグメント＋VPNルータ | 帯域100Mbpsで十分・スケーラビリティよりコスト優先の場合。**LB(アプライアンス)は共有セグメントに直接接続不可→VPNルータ配下のスイッチに接続**。VPNルータは**スタンダードプラン＝シングル構成** | コスト重視の代替案 |
| **ルータ＋スイッチ** | 将来の帯域拡張に対応。LB(アプライアンス)をルータ＋スイッチに接続しグローバルNWに配置 | **適切** |

### 採用構成
- **グローバルNW（ルータ＋スイッチ）→ パケットフィルタ → ロードバランサ(アプライアンス・冗長構成) → Web/AP 2台 → DBアプライアンス(冗長化オプション)**。LB(アプライアンス)の冗長化は**「冗長構成」を選択**。
- 代替案: グローバルNW=共有セグメント、LB(アプライアンス)はローカルNWに配置、**VPNルータ(スタンダード)でNATしたユーザー通信を負荷分散**（VPNルータはシングル構成）。

### 判断ポイント
- **L4 LB採用が適するケース**: TLS終端やHTTPヘッダ制御を行わず、ユーザ固有の状態がDB側で管理され、単一サーバ構成をそのまま複数台に拡張したい場合。
- ユーザ固有データ／リアルタイム性重視のケースは**CDNのキャッシュ効果が期待しにくく導入メリットは限定的**。
- ⚠️ **DSR(Direct Server Return)構成のため実サーバ側に設定が必要**: VIP受信用の**ループバックインタフェース設定**、**ARP応答抑制**等のNW調整。→アプリには手を加えず、**サーバ(OS/NW)設定の変更を許容することが前提**。**セッション維持はアプリ側で実装**が必要。
- 代替: バックエンドが複数APIサーバに分散し用途が分かれるなら**APIゲートウェイ**導入も選択肢。
- ⚠️ 帯域100Mbpsで十分でも、**共有セグメント配下はシングル構成のVPNルータ(スタンダード)しか接続できず単一障害点**になりうる。許容できない場合は**冗長構成のVPNルータ(プレミアム)**を選び、これを接続可能な**ルータ＋スイッチ**を採用する。

## ケース3: 業務システムのDR構成（GSLB / DNSベース）

### 業務背景・要件
- 自社＋複数取引先が利用する**受発注システム**。発注状況・納期照会をWeb提供。取引先ごとのIDでログイン、**接続元IPアドレスでアクセス制限**。
- **DRが必要**だが、システム停止は**数時間〜数日まで許容**。高可用性よりコスト重視。
- 利用形態: 特定IPからのアクセスを想定、VPN/閉域網は想定しない。
- 規模: 運用系=Web/AP 1台＋DB 1台、待機系=Web/AP 1台＋DB 1台。HTTPS公開・独自ドメイン。数十秒〜数分間隔の通信、急増想定なし。
- DR要件: メインサイトに運用系、**物理的に十分離れたバックアップサイト**に待機系（最小構成・通常時トラフィック受けない）。被災時は**運用判断による手動切替**。**RPO: 1日、RTO: 6時間以内**。通常時は待機系を停止しコスト削減。

### 選択肢（DR構成）
| 選択肢 | 特徴 | 本ケースの判断 |
|--------|------|----------------|
| GSLB・リージョン間 **Act/Act** | 通常時からDNSベースでマルチリージョン負荷分散、災害時は片系運用。可用性高いがコスト大 | **要件に不適切** |
| GSLB・リージョン間 **Act/Stn 自動切替** | 通常時メイン運用、災害時にバックアップへ自動切替。**GSLBは重み値100:0設定不可**のため**待機系Web/APをソーリーサーバとして設定**。通常時から運用→待機系へのデータ同期が必要で運用コスト増 | コストより即時復旧を重視する代替案 |
| **GSLB・リージョン間 Act/Stn 手動切替** | 通常時メイン運用、災害時に手動切替。被災時に待機系起動→運用系バックアップから待機系へ最新データ反映→GSLB実サーバを待機系に切替。**通常時は待機系停止で最もコストがかからない** | **適切** |
| エンハンスドLB・リージョン間 Act/Stn 手動切替 | DNSベースでなくL7(HTTPS)機能で手動切替 | 要件に不適切。L7で高度な負荷分散を行う場合に検討 |

### 採用構成
- **GSLBのFQDN**にユーザーがアクセス。通常時はGSLBの振り分け先を**メインサイト（東京リージョン）のみ有効化**、バックアップサイト（石狩リージョン）のWeb/AP・DBは**停止**してコスト削減。
- Web/APで**DBのエクスポートデータを取得→バックアップサイトのオブジェクトストレージに定期バックアップ**（ユーザのスクリプトでAPI自動実行等）。
- 被災時はGSLBの振り分け先を**手動で**バックアップサイトに切替。
- 代替案: GSLBにメインのWeb/APのみ登録＋**待機系をソーリーサーバとして登録**。DBエクスポートをバックアップサイトのDBにインポートし定期同期。被災時は**自動切替**。サイト間は**ブリッジ接続**。

### 判断ポイント
- DR構成は**復旧時間とコストのバランス**でバックアップサイト設計・復旧手順を検討。
- さくらのクラウドには**リージョン（ゾーン）間の自動同期/バックアップに対応していない機能がある**ため、必要に応じ利用者側で設計・実装。
- **GSLBの利用**: DNSベースで振り分けるため、**切替反映タイミングはクライアント側のDNSキャッシュ(TTL)に依存**。FQDNを管理する**権威DNSはGSLBとは別に用意**し、**GSLBが生成するFQDNをCNAMEレコードとして設定**。
- ⚠️ リージョンは**東京と石狩の2地域**。メイン/バックアップはリージョンを分けて利用。ゾーンごとに提供プラン・料金・リソース提供状況が多少異なる。**オブジェクトストレージは2025年12月より石狩に加えて東京でも利用可能**となり、メインサイトは東京・石狩いずれにも配置可。
- ⚠️ オブジェクトストレージにDBデータを保存する際は**グローバルNWを経由**する点に注意。セキュリティ向上には **SEG（サービスエンドポイントゲートウェイ）** を利用し、スイッチ経由のプライベートNW経由でアクセス可能。
- Act/Stn構成では、オブジェクトストレージを使わず、バックアップサイトに**NFSアプライアンス**を配置し**DBアプライアンスのバックアップ機能**でDBデータを自動定期取得する構成も選択肢。

### DB同期方式の選択肢（重要表）
| 選択肢 | 特徴 | 本ケースの検討 |
|--------|------|----------------|
| DBアプライアンス（冗長化オプションなし） | マネージド。利用者による手動同期・自動化の実装 | コストと柔軟性を重視する場合 |
| DBアプライアンス（冗長化オプションあり） | マネージド。Pri/Sec構成の自動同期 | **マルチゾーン非対応のため要件に不適切** |
| DBアプライアンス（クラスタ） | マネージド。**3ゾーンでのマルチマスタ(Act/Act)構成**による自動同期。料金負担が大きい | 高い可用性を重視する場合 |
| 利用者でDBサーバ構築 | サーバ上にDBソフトをセットアップし同期設定 | DBアプライアンスの仕様で要件を満たせない場合 |

## 試験対策・要点チェック
- [ ] 中規模の共通前提: **Web/AP 2台・DB 2台**で冗長化、マネージド優先。
- [ ] **L7(エンハンスドLB)＝セッション維持可(スティッキー)・プロキシ型** / **L4(アプライアンスLB)＝DSR型・セッション維持不可**。選択基準は**アプリのセッション維持方式**。
- [ ] ⚠️ **エンハンスドLBのCPSはHTTPSだとプラン表示の1/10**。
- [ ] **NFSアプライアンスはシングル構成**（冗長化は自前）。
- [ ] CDNは**静的のみオフロード**。動的・ログイン後・個人情報は**キャッシュしない**。ユーザ固有/リアルタイムはCDNメリット限定的。
- [ ] **DSR構成**＝実サーバにループバックIF設定＋ARP応答抑制が必要。アプリ非改修だがOS/NW設定変更が前提。
- [ ] グローバルNW: **共有セグメントにはLB(アプライアンス)を直接接続できない**。**VPNルータ スタンダード=シングル / プレミアム=冗長**。帯域拡張や冗長化なら**ルータ＋スイッチ**。
- [ ] DR: **GSLB=DNSベース**、切替は**TTL(DNSキャッシュ)依存**。**重み100:0は設定不可**→ソーリーサーバで対応。権威DNSは別途用意し**GSLBのFQDNをCNAME**設定。
- [ ] **RPO/RTO** の意味（本ケース RPO=1日、RTO=6時間以内）。コスト重視なら**手動切替・待機系停止**。
- [ ] DBのゾーン間同期: **冗長化オプションありはマルチゾーン非対応**。マルチゾーンで自動同期したいなら**DBアプライアンス(クラスタ)＝3ゾーンのマルチマスタ**。
- [ ] **SEG（サービスエンドポイントゲートウェイ）** でオブジェクトストレージへプライベートNW経由アクセス。
- [ ] オブジェクトストレージは**2025年12月より東京でも利用可能**（従来は石狩）。
