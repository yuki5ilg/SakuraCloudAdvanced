## 1. コンテナの基礎

### デプロイの課題（背景）
- クラウドで計算資源は迅速に準備できるが、**ローカル開発環境からクラウドへのアプリのデプロイ**が課題だった。
  - 手元のOS・開発環境を確実に再現する必要
  - 常に新しいアプリへ更新する必要
- 初期の解決策は **Ansible 等の構成管理ツール**（サーバ内の初期設定・パッケージの自動セットアップは可能だが、**アプリケーションは範囲外**）。

### Docker の登場
- **2013年**にLinux上で動作する **Docker** が発表、オープンソースで公開。
- アプリの **"Build, Ship, Run"（構築・移動・実行）** を支援。
- **Dockerイメージ**の中にアプリ実行に必要な全てが入る:
  - Linuxディストリビューションのファイル階層（Ubuntu, Debian, Fedora 等）
  - ソースコード、設定ファイル、依存パッケージ
  - どのプログラムを自動実行するか等のメタ情報
- **Docker Hub** にイメージをアップロード可能 → クラウドにデプロイして確実に実行できる。

### コンテナとは
- コンテナ(container) = **特別な状態のLinuxのプロセス**。
  - プロセスIDやファイルシステムの**名前空間が分離**され、互いに干渉せず実行可能。
  - 1台のPC/サーバ上で複数プロセスを同時実行でき、**リソースを効率利用**。
  - 起動時間が短く、効率的に開発・テストできる。
- コンテナの実行には **Dockerイメージ(image)** が必要。1つのイメージから**複数コンテナ**を作れ、イメージを移動して**スケール可能**。

## 2. さくらのクラウドが提供するコンテナサービス（重要：比較表）

コンテナのライフサイクルに応じたマネージドサービスを提供。

| 項目 | コンテナレジストリ | 高火力DOK | AppRun |
|------|--------------------|-----------|--------|
| 概要 | Dockerイメージを保管・管理するサービス | コンテナのGPU実行環境。レジストリからイメージをデプロイ | サーバレスのコンテナ実行環境。レジストリからイメージをデプロイ |
| 用途 | Dockerイメージの保管・管理・共有 | GPUを必要とする処理、AIモデル実行、機械学習 | ウェブアプリの開発・デプロイ・スケーリング |
| オートスケール | － | なし（タスク単位） | あり（自動） |
| ログ・監視 | － | － | 対応（モニタリングスイート） |
| CI/CD連携 | 対応 | 対応 | 対応 |
| API | なし | あり | あり |

- レジストリ内のイメージは、**AppRun と 高火力DOK の両方にデプロイ可能**。
- 使い分け: プロトタイピング・初期開発はローカルPC/サーバ → **CI/CDの過程やGPU処理のオフロード**としてクラウドを使い分け。

## 3. コンテナレジストリ

### 概要
- さくらのクラウド上の **Dockerイメージの保管場所（リポジトリ機能）**。
- コントロールパネル **「グローバル」** カテゴリから作成。
- レジストリ単位で**公開・非公開**、**ユーザ認証**を設定できる。
- AppRunへのデプロイに利用できるが、**デプロイしなくてもレジストリ単体で利用可能**。

### 名前とアクセス
- 作成時に **「名前」** を指定（一覧表示名かつ保存場所）。**ユニーク（一意）で重複不可**。
- 例:「example01」→ ホスト名 **`example01.sakuracr.jp`**。
- ホスト名形式: **`名前.sakuracr.jp/リポジトリ名:タグ`**
- 操作コマンド:
  - `docker login ~.sakuracr.jp`
  - `docker pull ~.sakuracr.jp/リポジトリ名`
  - `docker push ~.sakuracr.jp/リポジトリ名`

### 公開設定（重要表）
公開設定は2種類。作成時だけでなく**後から変更も可能**。

| 公開設定 | Pull（受信） | Push（送信） | 認証 |
|----------|:---:|:---:|------|
| Pullのみ | ○ | × | 不要 |
| 非公開 | ○ | ○ | ログイン認証 |

- 「Pullのみ」＝誰でも自由にPullして使ってほしい場合。
- 「非公開」＝限られたメンバーが業務利用、ユーザ認証必須。

### ユーザと権限
- セキュリティ向上にはユーザ作成による認証が必要。アクセスには `docker login` が必要。
- レジストリの「詳細」→「ユーザ」で一覧・追加・削除。**ユーザごとにアクセス権限を割当**。
  - **All**: リポジトリ（イメージ）の新規追加・変更・削除を含む**全権限**
  - **Push & Pull / Pullのみ**: リポジトリの変更権限のみ

### 操作コマンド例
```bash
# 接続とPull
$ docker login example01.sakuracr.jp
Username: demo
Password:
Login Succeeded
$ docker pull example01.sakuracr.jp/docker-image:latest

# Push（先にtagでレジストリ名を含むイメージを準備）
$ docker tag docker-image:latest example01.sakuracr.jp/docker-image:latest
$ docker push example01.sakuracr.jp/docker-image:latest
```

### 認証情報
- `docker login` 後、認証情報は **`~/.docker/config.json`** に記録され、以後常に操作可能。
- 別レジストリ操作や不要時は `docker logout`。再ログインは `docker login レジストリ名` だけで過去の認証情報を自動参照。
- 認証情報を残したくない場合は **`~/.docker/config.json` を削除**。

## 4. 高火力DOK

### 概要
- 高性能GPUを**必要な時に必要なだけ**使えるマネージドコンテナサービス。
- **Dockerイメージを渡すだけ**でGPUタスクを実行。インフラ構築不要（CUDAドライバや依存関係の毎回セットアップ不要）。
- オブジェクトストレージに学習データ・成果物を格納可能。
- **秒単位**で利用（**課金対象は起動時間のみ**）。
- **GPU計算を必要とする定型処理の実行に特化**。

### 高火力 3種類の比較（重要表）

| 項目 | 高火力DOK | 高火力VRT | 高火力PHY |
|------|-----------|-----------|-----------|
| サービス区分 | さくらのクラウド マネージドコンテナ | さくらのクラウド サーバ | GPUベアメタルサーバ |
| 操作単位 | タスク、ノートブック | 仮想サーバ | 物理サーバ |
| 用途 | バッチ処理、学習、推論 | 柔軟な利用 | 高パフォーマンス |
| 手軽さ | ◎ | ○ | △ |
| 対応GPU(NVIDIA) | H100、V100 | H100、V100 | H100、H200、B200 |
| GPU専有プラン | 8GPU専有プランあり | － | すべて専有 |

- DOKは「タスク」単位 or「ノートブック」を実行。VRT/PHYはLinux上での操作や環境構築が可能。

### タスク
- **1回のコンテナ実行 = 1回のタスク実行**。タスクを複製して新タスクを簡単に実行可能。
- タスク実行中:
  - **HTTP URL** を作成でき、HTTPSでアクセス可能
  - **SSHログイン**も可能（SSH公開鍵を事前登録）
- タスク結果を**オブジェクトストレージのバケットに出力可能**（環境変数 `S3_BUCKET` 等を指定）。
- 元となるDockerイメージ・レジストリを指定。認証が必要なレジストリは「レジストリー認証情報」で対応。

### コントロールパネル（左メニュー）
- ダッシュボード（お知らせ、ノートブック/タスク作成リンク、利用料金）
- タスク（作成・管理）
- ノートブック（JupyterLab の作成・管理）
- レジストリー認証情報（レジストリログインの事前設定）
- 公開鍵管理（SSH接続鍵の管理）
- オブジェクトストレージ/コンテナレジストリへのリンク、請求情報、設定

### タスク実行の流れ
1. 「タスク」→「新規作成」。名称、Dockerイメージ（**デフォルトはDockerHub**）、各種設定、プラン選択 →「作成」。
2. HTTP/SSHの有効化は**タスク作成時のみ**指定（HTTP=ポート/パス、SSH=シェル指定）。
3. タスク詳細でログ「プレビュー」→コンテナの標準出力を確認（例: `nvidia-smi` でV100を確認）。
4. タスク詳細からHTTP接続先URL、SSH接続コマンドを確認。

### タスクの終了・課金
- タスクは**実行中、常に課金が継続**。
- タスク作成時に **「最大実行時間」** を指定可能。未指定の場合は処理後に**手動停止**。
- 終了: タスク詳細で「中断」。削除: 中断後に「削除」。

### ノートブック
- **JupyterLab** をGPU認識済みの状態ですぐ利用できる機能（ブラウザで操作可能な対話型開発環境）。
- **PyTorch / CUDA がセットアップ済み**のタスクを自動作成。**Dockerの環境・知識がなくても利用可能**。
- 作成: 「ノートブック」→「新規作成」→ GPUプラン・SSH接続許可を選択 →「作成」。
- **アーティファクト**: 環境変数 **`$SAKURA_ARTIFACT_DIR`** のパスにファイルを保存 → タスク終了後に詳細画面からダウンロード可能。

## 5. AppRun

### 概要
- コンテナ化したアプリを**簡単にデプロイ・実行**するサービス。コンテナイメージを準備するだけでWebアプリを公開可能。
- **インフラ管理不要**、アクセス増減に応じた**自動スケーリング**、**API**を備えCI/CD連携可能。
- **共用型**（小規模でも利用可能）と**専有型**（高い安定性）。

### 共用型と専有型の比較（最重要表）

| 項目 | AppRun共用型 | AppRun専有型 |
|------|--------------|--------------|
| 実行環境 | 複数の利用者で共有 | 専有クラスタ |
| 利用規模 | 小規模 | 小規模から大規模 |
| 特長 | **スケール数0に対応**（ゼロスケール） | 高い安定性・分離性 |
| **オートスケールの基準** | **同時リクエスト数** | **CPU使用率** |
| ロードバランサ証明書 | `https://<name>.apprun.sakura.ne.jp/` | 対応（設定可能） |
| 用途 | バックエンドAPIサービス、新規サービスの開発・運用、小規模なWebサービス | マイクロサービス、冗長構成が必要なシステム、災害対策などの可用性 |

> ⚠️ 試験頻出: **オートスケール基準は 共用型＝同時リクエスト数 / 専有型＝CPU使用率**。共用型は**ゼロスケール（スケール数0）**対応。

- GPUが必要な処理や長時間バッチは**高火力DOKが適切な場合もある**。

### 共用型の特長
- 開発スピード向上（イメージ登録だけでデプロイ完了）、インフラ管理からの解放（サーバ/NW管理不要、APIファースト設計でCI/CD連携容易）。
- 自動スケーリング（トラフィックに応じスケールアウト/イン、**アクセスゼロ時はゼロスケールでコスト最適化**）。
- 統一された開発環境（開発と本番の差異を解消）。

### 専有型の特長
- 共用型と同じ利点 + 自動スケーリングは **Kubernetes ワーカノードのCPU使用率を常時監視**し、ワーカノード数を自動調整。
- 高い安定性・セキュリティ: **ワーカノードを仮想サーバレベルで分離**、他ユーザのコンテナの影響を受けない専有環境。**自治体など高セキュリティ要件**にも対応可能。

### 用語と概念（重要）
- **アプリケーション**: AppRunのデプロイ単位。ポート番号、リクエストタイムアウト、オートスケーリング、パケットフィルタ、ログ・メトリクスを**アプリ単位で設定・取得**。
- **コンポーネント**: コンテナ実行に必要な構成情報を定義する単位。
  - デプロイソース（コンテナイメージ・認証情報）
  - リソース設定（vCPU数・メモリサイズ）
  - 実行環境（環境変数・ヘルスチェック）
- **バージョン**: 構成情報変更時に**自動的に最大5世代まで保持**。バージョンを分けた**トラフィック管理**が可能。

### 実行手順の要点
- レジストリにイメージをpushしておく（`docker push`）。
- コントロールパネルから「AppRun」を選択。**共用型と専有型でリンク先が異なる**。
- ⚠️ **共用型⇔専有型の相互変更はできない**。
- 共用型: 「アプリケーションを作成」→ 名称・パラメータ設定 → 詳細画面で公開URL確認・設定変更。
- 専有型:
  - **クラスタ** = 専用Kubernetes環境のノード数を管理する単位。
  - クラスタ作成前に、**「さくらのクラウド > 作成・削除」のIAMポリシーを持つサービスプリンシパル**の作成が必要。
    1. サービスプリンシパルを作成
    2. IAMポリシーでロール「さくらのクラウド > 作成・削除」のアクセス権を設定
  - アプリ更新は「バージョンを追加」→ 対象バージョンを手動「操作」でアクティブ化。

### ログとモニタリング
- ログ・ランタイムメトリクス（CPU/メモリ使用状況）の確認には**モニタリングスイートが必要**（事実上、設定が推奨）。
- 「ログストレージの新規作成」「メトリクスストレージの新規作成」で「デフォルト」ストレージが自動作成され、モニタリングスイートで確認可能。

## 6. 試験対策・要点チェック

- [ ] Dockerの発表年は **2013年**、思想は **Build, Ship, Run**。
- [ ] コンテナ = **名前空間が分離されたLinuxプロセス**。実行にはイメージが必要。
- [ ] レジストリのホスト名形式 = **`名前.sakuracr.jp`**、push前に **`docker tag`** が必要。
- [ ] 認証情報は **`~/.docker/config.json`**。
- [ ] 高火力DOKは**課金対象＝起動時間のみ**、**秒単位**、結果は**オブジェクトストレージ**へ。
- [ ] 高火力 PHYのみ **H200/B200** 対応・すべて専有。DOK/VRTは **H100/V100**。
- [ ] ノートブックのアーティファクトは **`$SAKURA_ARTIFACT_DIR`**。
- [ ] AppRunオートスケール: **共用型＝同時リクエスト数 / 専有型＝CPU使用率**。
- [ ] AppRun共用型は**ゼロスケール対応**、専有型は**Kubernetesワーカノードを仮想サーバレベルで分離**。
- [ ] AppRunバージョンは**最大5世代**保持。共用型⇔専有型の**相互変更不可**。
- [ ] 専有型クラスタ作成には**「作成・削除」IAMポリシーのサービスプリンシパル**が必要。
