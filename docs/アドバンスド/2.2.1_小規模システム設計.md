# 2.2.1 小規模システムにおけるアーキテクチャ設計

> 出典: SCA2.2.1_ArchitectureDesign-for-SmallScaleSystems（さくらのクラウド検定アドバンスド教材 2.2 ケーススタディ, CC BY-SA 4.0 / さくらインターネット）
> 学習目標: 小規模システムの要件・制約を踏まえ、コスト・可用性・拡張性のトレードオフを判断し、過不足のない最小構成のアーキテクチャを設計できる
> キーワード: サイト間VPN / マーケットプレイス ネットワークサービス / ルータ＋スイッチ / 共有セグメント / パケットフィルタ / VPNルータ / リモートアクセスVPN / DBアプライアンス / ネットワーク分離

---

## 0. 全体像

本資料は「2.2 ケーススタディ」のうち、**小規模システム**を題材に3つのケースで設計判断を学ぶ。共通する前提は次の通り。

- いずれも **小規模・低コスト・運用負荷小**、**高可用性・冗長化は必須要件ではない（割り切る）**。
- 各ケースで「要件を満たす**最小構成**」を選ぶ判断が重要。冗長化や複雑な構成はとらない。

| # | ケース | 公開/非公開 | 主な構成要素 | 学習の主眼 |
|---|--------|------------|-------------|-----------|
| 1 | 社内向け業務システム | インターネット**非公開**（VPN前提） | マーケットプレイス ネットワークサービス（サイト間VPN） | 固定IPを持たない拠点とのVPN選択肢、可用性とコストの割り切り |
| 2 | コーポレートサイトのWeb公開 | インターネット**公開** | ルータ＋スイッチ＋パケットフィルタ | 共有セグメントとルータ＋スイッチの使い分け、将来拡張性 |
| 3 | ECサイト | **公開（Web/AP）＋非公開（DB）** | VPNルータ＋共有セグメント＋DBアプライアンス | 公開と管理アクセスの両立、Web/APとDBの分離 |

## ケース1: 社内向け業務システム

### 業務背景・利用形態
- 製造業の**生産ライン進捗を管理・可視化する社内業務向けWebシステム**をさくらのクラウドで運用したい。
- 利用者: **工場(拠点)の生産部門担当者** と **本社の管理部門担当者**。
- 業務用途のため**インターネットへは公開しない**。
- 接続方式: インターネット経由だが**VPN接続を前提**。**不特定多数からのアクセスは想定しない**。

### 前提条件・制約条件
| 区分 | 内容 |
|------|------|
| 規模 | 小規模。**Web/APサーバ1台**、利用拠点**1〜2拠点** |
| 通信 | クライアントから**数十秒〜数分間隔**で通信 |
| 要件 | 初期費用・運用コストを抑える / 運用負荷を増やしたくない / **高可用性・冗長化は必須でない** |
| NW前提 | 各拠点に**VPNルータ機器**があり**サイト間VPN**を構成可能 / 一部拠点は**固定グローバルIPを持たない** / Webシステムはインターネット非公開 |

### 設計選択肢（サイト間VPN）
| 選択肢 | 特徴 | 本ケースでの検討 |
|--------|------|-----------------|
| VPNルータ | 拠点の**固定IP前提** | 固定IPを持たない拠点があり**不適切** |
| **マーケットプレイスのネットワークサービス** | 拠点の**動的IP対応可能** | **適切** |
| インターネット公開 | VPN不要 | 要件に不適切 |

### 採用する構成（図の再現）
- **マーケットプレイスのネットワークサービス（アプライアンス）** を用いたサイト間VPN構成を選択。
- 小規模構成のため冗長化・複雑な構成はとらず、要件に過不足のない構成とする。

```
[拠点]──サイト間VPN──[ グローバルNW ]
                          │
              マーケットプレイス ネットワークサービス（アプライアンス）
                          │
                  [ ローカルNW ]──スイッチ──[Web/APサーバ]
```
- 凡例: グローバルNW / ローカルNW / **サイト間VPN**（拠点間を接続）。
- アプライアンスがグローバル側とローカル側の境界に立ち、配下にスイッチでWeb/APサーバを接続。

### 設計判断ポイント・代替案
- Webシステムでも**業務用途ではインターネット非公開が前提**となる場合がある。
- VPN方式選択時は**拠点側ネットワーク条件（固定IPの有無）を確認**する。
- 拠点側で**固定IPが確保できる場合はVPNルータ構成も選択肢**。
- ⚠️ サイト間VPN接続では、**拠点側ネットワークとクラウド内部ネットワークを互いに重複しないCIDR範囲で設計**する必要がある。

## ケース2: コーポレートサイトのWeb公開

### 業務背景・利用形態
- 不特定多数の利用者へ情報提供する**小規模コーポレートサイト**をWeb公開したい。
- 利用者: **一般利用者（ブラウザアクセス）**。接続はインターネット経由。**不特定多数のアクセスを想定**。
- アクセスは少数で**急激な増加は想定しない**。

### 前提条件・制約条件
| 区分 | 内容 |
|------|------|
| 規模 | 小規模Webサイト。**Web/APサーバ1台**。アクセス少数・急増想定なし。サービス停止の影響は限定的 |
| 要件 | 初期費用・運用コストを抑える / **高可用性・冗長化は必須でない** |
| 拡張要望 | 将来のシステム増強に備え**スケーラビリティを確保** / **グローバルNWの帯域拡張の可能性**を残す / グローバルNW**同一セグメント配下へのサーバ増設**を可能にする |

### 設計選択肢（グローバルネットワーク）
| 選択肢 | 特徴 | 本ケースでの検討 |
|--------|------|-----------------|
| 共有セグメントに接続 | **100Mbpsベストエフォート共有帯域** / **追加料金不要** | 低コスト最優先なら検討（**代替案**） |
| **ルータ＋スイッチに接続** | **100M〜5Gbps**（ゾーンにより**最大10Gbps**）ベストエフォート共有帯域 / **帯域変更可能** / グローバルIPを**纏まったCIDR範囲**で確保し複数サーバを同一セグメントとして構造化できる | **適切** |

### 採用する構成（図の再現）
- **ルータ＋スイッチ**で将来の帯域増強に備え、グローバルNW同一セグメント配下にサーバ増設可能とする。
- **無料のパケットフィルタ**でサーバへ着信するパケットをフィルタリング。
- 小規模構成のため冗長化・複雑な構成はとらない。

```
[ グローバルNW（インターネット） ]
        │
   ルータ＋スイッチ
        │  ← パケットフィルタ（着信をフィルタ／無料）
   [ ローカルNW ]──[Web/APサーバ]
```
- 凡例: グローバルNW / ローカルNW / **パケットフィルタ**。

### 設計判断ポイント・代替案
- 小規模Web公開でも、**特定のグローバルNWのCIDR範囲に接続**しておくと、将来の構成変更（サーバ増設、グローバル帯域変更、セキュリティ制御追加）に柔軟に対応できる。
- コスト最優先なら**共有セグメント構成も選択肢**。ただし帯域増強時にはルータ＋スイッチへ移行が必要となり、**グローバルIPが変更**＝**サーバOS側のIPアドレス設定変更も必要**。
- ⚠️ ルータ＋スイッチの追加IPアドレス（グローバルIP）は、**ネットワーク運用に必要な5個を引いた数**を利用者が割当可能。
  - 例: **追加IP 16個（/28）→ サーバに割当可能は 11個**（16−5）。

## ケース3: ECサイト

### 業務背景・利用形態
- 自社商品を販売する**ECサイト**をさくらのクラウドで運用したい。インターネット公開が前提。
- 利用者: **一般利用者（ブラウザ・インターネット経由）** と **システム運用担当（リモートアクセス）**。
- 運用担当はインターネット経由だが**VPN接続を前提**（会社・自宅から）。**不特定多数のアクセスを想定**。

### 前提条件・制約条件
| 区分 | 内容 |
|------|------|
| 規模 | 小規模ECサイト。**Web/APサーバ1台＋DBサーバ1台**。通信は数十秒〜数分間隔、アクセス少数・急増想定なし。停止の影響は限定的 |
| 要件 | 初期費用・運用コスト抑制 / 運用負荷を増やさない / **高可用性・冗長化は必須でない** |
| NW前提 | **業務データ（顧客情報・注文情報）**を扱うため、**処理内容の異なるコンポーネントごとに影響範囲とリソースを分離** / 業務データへの**不正アクセスリスク**を考慮 / 運用端末から**インターネットVPN**でアクセス |

### 設計選択肢（クラウド内部のネットワーク）
| 選択肢 | 特徴 | 本ケースでの検討 |
|--------|------|-----------------|
| Web/AP・DBともにインターネット公開 | パブリックNWのみ / **第三者からDB接続されるリスク** / 構成シンプル | 要件に**不適切** |
| **Web/APは公開、DBは非公開だがWeb/APと同一セグメントで通信可能** | クラウド内部でプライベートNW運用 / **DBへの直接アクセスを防止** / 構成が比較的シンプル | **適切** |
| Web/APは公開、DBはWeb/APと**別セグメントで非公開** | プライベートNW運用 / DB直接アクセス防止 / **Web/APとDBをネットワークレベルで分離**しWeb/APの問題がDBに波及しにくい / 構成がやや複雑・コスト高 | **セキュリティ最優先なら検討（代替案）** |

### 採用する構成（図の再現）
- **VPNルータ（スタンダード）** でネットワーク境界を設け、Web/APとDBをクラウド内部の**プライベートネットワーク（共有セグメント）**で運用。
- VPNルータの**NAT機能**で、インターネットからのアクセスを**Web/APに転送**。
- VPNルータの**リモートアクセスVPN機能**で運用端末からアクセス。
- DBは**DBアプライアンス**を利用。

```
[ グローバルNW（インターネット） ]
        │  ← リモートアクセスVPN（運用端末）
  VPNルータ（スタンダード） ─ NATでWeb/APへ転送
        │
  [ 共有セグメント（ローカルNW） ]
        ├─ Web/APサーバ
        └─ DBアプライアンス
```
- 凡例: グローバルNW / ローカルNW / **リモートアクセスVPN**。

### 代替案の構成（別セグメント分離 / 図の再現）
- 公開系（Web/AP）と非公開系（DB）の**ネットワークを明確に分離**し、到達可能な範囲を分けてセキュリティレベルを向上。
- **Web/APサーバは2つのNICを持ち、それぞれ異なるスイッチ（＝異なるCIDR範囲）に接続**する。
- VPNルータ（スタンダード）配下に、公開側の共有セグメントとDB側セグメントを別々に構成し、DBアプライアンスを非公開セグメントに配置。

### 設計判断ポイント・注意点
- **処理特性・負荷特性・セキュリティレベルの異なるコンポーネントは、必要に応じてリソースとネットワークを分離**し影響範囲を限定する。**スケーラビリティ維持のためにも分離の考え方が重要**。
- 代替案:
  - DBは**DBアプライアンスを使わず利用者自身でDBサーバを構築**する選択肢もある。その場合、パッケージ更新のため**インターネットへのアウトバウンド通信経路**を検討（別途VPNルータへ接続する構成）。
  - 端末からのVPN接続は、VPNルータの**リモートアクセスVPN機能**に加え**WireGuard機能**を用いたVPN接続も選択肢。
  - 運用性を考慮し、**DBアプライアンスに直接VPNルータとの接続性を持たせる構成**も想定される。

## まとめ: ケース別 構成早見表

| 観点 | ケース1 社内業務 | ケース2 コーポレート | ケース3 EC |
|------|-----------------|---------------------|-----------|
| 公開性 | 非公開（VPN前提） | 公開 | 公開＋非公開（DB） |
| サーバ | Web/AP×1 | Web/AP×1 | Web/AP×1＋DB×1 |
| 採用NW境界/接続 | マーケットプレイス ネットワークサービス（アプライアンス） | ルータ＋スイッチ | VPNルータ（スタンダード） |
| 主なセキュリティ機構 | サイト間VPN | パケットフィルタ（無料） | NAT＋リモートアクセスVPN＋NW分離 |
| 決め手 | 固定IPなし拠点に動的IP対応 | 将来の帯域増強・サーバ増設のためCIDR確保 | DBへの直接アクセス防止 |
| 代替案 | 固定IPありならVPNルータ | コスト最優先なら共有セグメント | DBを別セグメント分離（セキュリティ最優先） |

## 試験対策・要点チェック

- [ ] 全ケース共通: 小規模・低コスト・運用負荷小、**高可用性/冗長化は必須でない（割り切る）**、要件を満たす**最小構成**を選ぶ。
- [ ] ケース1: 拠点に**固定IPがない**ため**VPNルータは不適切**、**マーケットプレイスのネットワークサービス**で動的IPに対応。
- [ ] サイト間VPNでは**拠点側とクラウド内部のCIDRを重複させない**。
- [ ] ケース2: 共有セグメント＝**100Mbps・追加料金不要**。ルータ＋スイッチ＝**100M〜5Gbps（ゾーンにより最大10Gbps）・帯域変更可・CIDRで構造化**。
- [ ] 帯域増強で共有セグメント→ルータ＋スイッチへ移すと**グローバルIPが変わりOS側IP設定変更が必要**。
- [ ] ルータ＋スイッチの追加IPは**運用必要5個を引いた数**が割当可能（**/28=16個→11個**）。
- [ ] ケース2の着信制御は**無料のパケットフィルタ**。
- [ ] ケース3: **Web/AP公開・DB非公開**。「ともに公開」は第三者からのDB接続リスクで不適切。
- [ ] ケース3採用構成: **VPNルータ（スタンダード）**＋共有セグメント＋**DBアプライアンス**、**NATでWeb/APへ転送**、**リモートアクセスVPN**で運用端末接続。
- [ ] ケース3代替案: DBを**別セグメントで非公開**＝Web/APの問題がDBに波及しにくい（複雑・高コスト、セキュリティ最優先時）。Web/APは**2NIC・異なるスイッチ/CIDR**。
- [ ] DBは**アプライアンス**でも**自前DBサーバ**でも可。自前ならパッケージ更新用の**アウトバウンド経路**を検討。
- [ ] リモートアクセスVPNは**WireGuard**も選択肢。
- [ ] 設計原則: **処理特性・負荷・セキュリティが異なるコンポーネントはリソースとネットワークを分離**して影響範囲を限定し、スケーラビリティを維持。
