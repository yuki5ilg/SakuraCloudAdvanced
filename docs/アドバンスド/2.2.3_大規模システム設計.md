# ケースA. エンタープライズ企業の基幹システム

## A-1. 学習ポイント（ページ3）
- さくらのクラウドへの**閉域網の引き込みパターン**
- 役割に応じた**ネットワーク分離**の考え方

## A-2. 業務背景・要件（ページ4-6）
- エンタープライズ企業の**グループ共通システム**（グループウェア、ファイル共有等）をさくらのクラウド上で構築・運用。
- 社員が組織横断で利用する業務システム。現行はオンプレミスで、社内業務NWの端末から**既存の閉域網経由**でアクセス。
- クラウド移行では現行のネットワーク運用を踏襲 → **既存閉域網をクラウドへ延伸**し、プライベートネットワーク経由でアクセス。
- 全社員利用のため**システム停止＝業務全体に影響**。→ **単一障害の発生を前提**とし、通信経路の多重化・冗長構成による高可用基盤が必要。
- ※**災害対策（DR）は対象外**（このケースのみ）。

### 想定規模・要件
- 業務サーバ: **数台～数10台（冗長構成）**。グループウェアサーバ（スケジュール、ワークフロー、掲示板）、申請受付/業務APサーバ（申請受付、ファイルアップロード）。
- 通信間隔: クライアントから**数十秒～数分間隔**。**アクセス数の急増は想定しない**。
- 要件: 単一障害前提の高可用設計 / マネージドサービスで運用負荷軽減 / 必要十分な範囲の多重化（コスト有限）。

## A-3. ネットワーク要件 ─ 役割別3層分離（ページ7・図）

役割に応じてクラウド内NWを**業務NW・中間NW・公開NW**に分離。**業務NWと中間NWはインターネットから直接到達できない非公開構成**。社内業務NWとクラウド業務NWは既存閉域網経由で接続。

| | 業務NW | 中間NW | 公開NW |
|---|--------|--------|--------|
| 役割 | 共通システムの中核／社内業務NWの延長 | 業務NWと公開NW間の**緩衝領域（バッファ）** | インターネットと接続する領域（**DMZ**）／外部通信の入口・出口 |
| 用途 | 業務サーバの利用／無害化データの利用 | 検疫、クレンジング／通信制御、ログ取得 | インターネット公開サーバ |
| サーバ群 | 業務サーバ群（グループウェア、申請業務AP等） | 中継サーバ群（ゲートウェイ、検疫/クレンジング） | 公開サーバ群（公開Web、申請受付等） |

## A-4. 通信要件 ─ 境界での通信制御（ページ8・図）
- **インターネットと業務NW間の直接通信は許可しない**。中間NW・公開NWで**TCPセッションをそれぞれ終端**することで、通信を境界で制御する。
- 公開NWサーバ上に持ち込まれたファイル（顧客の申請ファイル等）は**検疫してから業務NWに連携**。
- ただし**ソフトウェアのアップデートファイルは除去せず**、マルウェア検査や署名検証で安全性を確実にする。
- フロー: 社内業務NW ⇔ 業務NW ⇔ 中間NW（検疫/除去）⇔ 公開NW ⇔ インターネット。

## A-5. 閉域網引き込みの選択肢（ページ9-10）

| 選択肢 | 特徴 | 本ケースでの検討 |
|--------|------|------------------|
| **ダイレクトアクセス利用** | 既存閉域網をクラウドに延伸。閉域網のONUをさくらのDCで運用しハイブリッド接続。**ルータによるL3分割が必要**。運用コスト低いが、引き込める閉域網と冗長性は**回線サービスに依存し自由度が低い** | **適切（条件付き）** |
| さくらインターネットのハウジングラック利用 | 既存閉域網をラック内に延伸しクラウドと接続。ラック契約＋利用者側でラック内構築・機器運用が必要。運用コスト高・リードタイム長いが、引き込める閉域網と冗長性の**自由度が高い** | ダイレクトアクセスで要件を満たせない場合に検討（代替案） |
| OCX利用 | OCX既設回線を利用。複数の閉域回線サービス契約が必要で管理コスト増。運用コスト低・リードタイム短。**標準で冗長構成を提供** | 既存閉域網がOCXの場合や安価で広帯域を求める場合（代替案） |
| プライベートリンク利用 | 特定DC内の利用者ラックから**構内配線**でクラウドと接続。指定DC内にラック契約＋接続口ラックまで構内配線が前提。運用コスト高・リードタイム長。**標準で冗長構成を提供** | 特定DC内にラック契約済みの場合（代替案） |

## A-6. 設計方針と選択する構成（ページ11-12・図）

**採用: ダイレクトアクセス**。構成イメージ:

```
社内業務NW(ノートPC等)
   │ グローバルNW
   ▼
[ONU]→[ルータ＋スイッチ]  ← さくらインターネット（ダイレクトアクセス）
   │ ハイブリッド接続
   ▼
=== さくらのクラウド ===
  [ロードバランサ]
   │ ローカルNW
   ┌──────────┬──────────┐
 業務NW      中間NW      公開NW
 (VPNルータ) (VPNルータ) (VPNルータ)
 サーバ群…   サーバ群…   サーバ群…
```

### 設計方針（逐語要点）
- 既存閉域網をさくらインターネットのDC内に延伸し、**ダイレクトアクセスの専用ラック内にONUを設置**。持ち込み（またはレンタル）ルータでハイブリッド接続のケーブルを収容し、既存閉域網と**L3分割**する。
- 業務NW・中間NW・公開NW間は**それぞれVPNルータで分離**。ファイアウォール機能で必要な通信のみ許可し、**各VPNルータのインターネット接続を無効**にして通信経路を限定する。
- **各サーバはNICを2つ保有**し、各NW境界のVPNルータとスイッチ経由で接続して、隣のNWからの通信を終端する。

## A-7. 設計上の判断ポイント（ページ13-15）
- 大規模システムではクラウドに閉域網を引き込む構成が多い。外部回線引き込みサービスは複数あり特徴が異なるため、要件に応じて最適選択。
- 閉域網とクラウドの接続点では**ルータによるL3分割**を行い、各NW間の到達範囲（ルーティング）を整理。

### 注意点・代替案
- 各NW境界のファイアウォールは**VPNルータのスタンダードプラン**のため**シングル構成**。**プレミアムプランで冗長化可能**だが、インターネット接続無効でも**グローバル側インタフェースにルータ＋スイッチへの接続が必要**。

### 閉域網引き込みサービスの分類（ページ14）

| タイプ | サービス例 |
|--------|------------|
| **既設回線の利用** | プライベートリンク for アルテリア／for BBIX（OCX by BBIX）／for NTTドコモビジネス |
| **利用者による新規回線の引き込み** | ダイレクトアクセス／さくらインターネットのハウジングラック利用 |

- いずれの方式も、一部サービスを除き**ハイブリッド接続に収容**してクラウドに接続。
- 新規回線引き込みタイプでは、原則**利用者側ルータで回線側とのL3分割**が必要。
- ハイブリッド接続のケーブルは**標準で2本提供**され**冗長構成が前提**（※シングル構成の場合は1本のみ接続）。冗長方式はサービス仕様で定められた中から選択。**閉域網側の冗長性設計とルータ設定は利用者側の責任範囲**。
  - 図: ONU×2 → ルータ → ケーブル（2本）。利用者側で 192.168.0.0/24 と 192.168.1.0/24 を分割。

# ケースB. 大規模サービスを支えるWebシステム

## B-1. 学習ポイント（ページ17）
- **SaaSの基盤におけるAct/Act構成**
- **CDNとLBを使った可用性とスケーラビリティの向上**
- **DBのゾーン冗長**を考慮した構成

## B-2. 業務背景・要件（ページ18-20）
- 一般消費者（**BtoC**）向け**SaaS型サービス**（動画/電子コンテンツの**サブスクリプション型**）。
- Webブラウザ/スマホアプリで**不特定多数が24時間利用**。**サービス停止＝利用者離脱** → 高い可用性とスケーラビリティが前提。
- キャンペーン/イベント等で**アクセス数が時間帯により変動**（突発的アクセスを想定）。

### 想定規模
- Web/APサーバ: **数台～数10台（Act/Act）**。
- DBサーバ: **数台（Act/Stn＝Active/Standby）**。
- 要件: **SPOF（単一障害点）を排除**した高可用設計 / マネージドサービス活用 / 必要十分な冗長化。

## B-3. ネットワーク要件・DR要件（ページ21）
- **CDN（ウェブアクセラレータ）経由で画像ファイルへアクセス**しレスポンス性能向上。画像は**オブジェクトストレージに保管**、Web/APが画像のサブドメインを返し、ユーザはCDN経由でアクセス。
- クラウドの**L7ロードバランサでHTTPS通信を終端**しURLパスでルーティング。**HTTPヘルスチェック（ステータスコード等）で異常Web/APを切り離す**。
- **DR要件あり**（ケースAと異なる）: 特定地域の災害でもサービス継続できるDR構成。
- **マルチゾーン構成**: 単一ゾーン障害でも**最小限のダウンタイムで正常ゾーンに自動切替**し継続提供。

## B-4. Web/AP要件・DB要件（ページ22）
- **Web/APはステートレス構成**とし、サーバ負荷に応じ**自動水平スケール**を可能にする。
- 認証は**トークン（JWT）**。通常リクエストは**DBを参照せずトークン検証（署名・有効期限）のみ**で処理。**トークンの即時失効は要件外**、特定操作時のみRDBアクセスが必要な前提。
- **RDBはゾーン間で冗長化した「プライマリ＋複数リードレプリカ」構成**とし、読み取り性能向上と耐障害性を確保。
- **同期レプリケーションによるマルチマスタ構成**は要件次第での選択肢（代替案）。

## B-5. 設計の選択肢

### ゾーン冗長の選択肢（ページ23-24）

| 選択肢（Web/AP層 / DB層） | 特徴 | 本ケースでの検討 |
|---------------------------|------|------------------|
| **全ゾーン現用 / 全ゾーン現用**（DBアプライアンス(クラスタ)によるRDBマルチマスタ） | Web/APがステートレスで性能と可用性の両方重視にマッチ。全ゾーンで運用系DB稼働。一般に競合解決の設計が難しいRDBマルチマスタを**マネージドサービスで運用**。**他選択肢より運用コスト大** | 高可用性を重視する場合（代替案） |
| **全ゾーン現用 / 1ゾーン現用・他ゾーン待機**（利用者でRDBプライマリ・セカンダリ構築） | Web/APステートレスで性能・可用性両立。現用ゾーンで運用系DB稼働、障害時に待機系DBへ切替。**切替時にレプリケーション遅延に起因するデータ欠損リスク** | **適切（本命）** |
| **1ゾーン現用・他ゾーン待機 / 1ゾーン現用・他ゾーン待機**（利用者でプライマリ・セカンダリ構築） | 現用ゾーン停止時に待機系へ切替。待機系は**常時起動(hot)/低性能起動(warm)/平常時停止(cold)** から選択。**運用コスト小だが切替RTOが長くなりやすい** | コストを優先する場合（代替案） |

### Web/AP層の負荷分散の選択肢（ページ25-26）

| 選択肢 | 特徴 | 本ケースでの検討 |
|--------|------|------------------|
| **エンハンスドロードバランサ（エニーキャスト）** | 複数リージョンで稼働するLBに対し、利用者から近いリージョンに接続。**DR構成としてDNSベースよりリージョン障害時の切替が早い**。設定箇所が少なくシンプルで導入容易だがLB制御範囲を超えた柔軟設計は難。**GSLBと比べL7の高度な負荷分散が可能**。プラン性能に応じたコスト | **適切（本命）** |
| **GSLB＋各ゾーンのエンハンスドLB** | **DNSベースでリージョン間負荷分散＋各リージョン内でL7負荷分散の多段構成**。リージョンごとに入口が分かれ1リージョンのトラブルが全体に波及しにくい。契約リソース数で設定箇所が増え構成が複雑・管理コスト増。**DNSキャッシュ/TTLの影響で即時切替不可、数分程度を要する** | リージョンごとに制御する柔軟性を重視する場合（代替案） |

> ⚠️ **エンハンスドLB（エニーキャスト）＝切替が速い・シンプル**／**GSLB＝柔軟だがTTL影響で数分かかる**。

## B-6. 設計方針と選択する構成【本命】（ページ27・図）

```
              [ウェブアクセラレータ(CDN)]──[オブジェクトストレージ]
                       │ グローバルNW
              [エンハンスドLB]  ← パケットフィルタ / オートスケール
        ┌──────────────┴──────────────┐
      【東京ゾーン】                【石狩ゾーン】
      ルータ＋スイッチ              ルータ＋スイッチ
      Web/AP …(複数)              Web/AP …(複数)   ← ローカルNW
      DBサーバ(プライマリ)         DBサーバ(セカンダリ※リードレプリカ)
```

### 設計方針（逐語要点）
- ユーザはエンハンスドLBにアクセス。振り分け先は**東京・石狩ゾーンの各Web/APサーバ**。
- 画像ファイルはオブジェクトストレージに格納し、**ウェブアクセラレータのサブドメイン方式でオリジンに設定**。
- **オートスケール機能でWeb/APサーバの水平スケール**を実装。
- DBサーバのプライマリ・セカンダリを配置、**セカンダリはリードレプリカとして運用**。**ゾーン停止時は異なるゾーンのDBがプライマリになる**。

## B-7. 設計方針と選択する構成【代替案 = DBアプライアンス】（ページ28・図）

本命との違いは**DB層**。**DBアプライアンス（クラスタ）でマネージド型マルチマスタを運用**し、**ロードバランサ（アプライアンス）でDBアクセスを振り分ける**。ゾーンは**東京・石狩第2・石狩第3**の3ゾーンに展開。

```
   [ウェブアクセラレータ]──[オブジェクトストレージ]
   [エンハンスドLB] ← パケットフィルタ / オートスケール
   東京 / 石狩第2 / 石狩第3（ルータ＋スイッチ）
   [LB(アプライアンス)] → [DBアプライアンス(クラスタ)]（マルチマスタ）
```

## B-8. 設計上の判断ポイント（ページ29-30）
- 求められる性能と耐障害性を考慮し、**マルチリージョン・マルチゾーン**の特徴を活かした信頼性の高い構成。
- DB冗長構成は、**マネージド型DBを選ぶか利用者でDBサーバ構築するか**を運用の柔軟性とコストで検討。

### 注意点・代替案
- **大規模システムではDB性能がボトルネックになる可能性を考慮**。
- 読み込み性能向上策: **リードレプリカ**や**インメモリ型DBキャッシュ（Redis等）**。ただし**さくらのクラウドにはマネージド型のDBキャッシュサービスがない** → **利用者自身で構築が必要**。
- **DBアプライアンスを専有ストレージ上で稼働**させると高IOPS・高スループットが期待でき、通常のアプライアンスでは選べない**ハイスペックプラン**を利用可能。コストとのバランスで検討。
- **オブジェクトストレージのリージョン間レプリケーション**で画像バケットを複数サイト間同期可能。ただし**エンドポイント停止時に自動でレプリ先へ切り替わるわけではない** → 利用者構築のプロキシ/APIゲートウェイでオリジンのエンドポイントを変更する**自動切替の仕組みを実装するか手動切替手順を準備**する必要。
- **オートスケール**: **各ゾーン内で最低1台以上のWeb/APを維持**するよう設定。スケールアウト時のディスクソースとして**マイアーカイブの運用が発生** → **最新のマイアーカイブを各ゾーン内で保持**する必要。

## B-9. 代替案: AppRun専有型によるコンテナ運用（ページ31・図）
- **Web/APをAppRun専有型のコンテナで運用する選択肢**もある。
- **オートスケーリンググループとロードバランサノード**でWeb/APの可用性を確保。**ワーカノードからスイッチ経由でDBに接続**。
- 構成: ウェブアクセラレータ＋オブジェクトストレージ／グローバルNW＋パケットフィルタ／東京・石狩の各ゾーンに AppRun専有型（オートスケーリンググループ＋ワーカノード）。

# ケースC. 国産クラウドの特徴を活かしたマルチハイブリッド構成

## C-1. 学習ポイント（ページ33）
- **オンプレミスと複数クラウドの併用**
- **トラフィック課金と為替変動を考慮**したシステム設計
- 新規システム開発と既存環境の移行を踏まえた設計判断

## C-2. 業務背景・要件（ページ34-36）
- エンタープライズ企業で、オンプレミスの基幹システム＋**海外の他社クラウド**上の複数業務システムを維持したまま、今後の新規開発と一部既存システムをさくらのクラウドへ配置・移行したい。
- **トラフィック課金によるコスト高と為替変動リスクを最小化**したい。
- 重要な基幹システムは今後もオンプレミス。海外他社クラウドの既存システムも全てを一律移行対象とはしない。一方、以下はさくらのクラウドを**優先的な配置先・移行先**として選定:
  - 新規開発するシステム / 機能刷新・再構築するシステム / **トラフィック課金の負担が大きい既存システム**。

### 想定規模
- 利用者数: **数百～数千名**。
- 基幹システム: **オンプレミス（物理サーバ数10台）**。
- 業務システム: クラウド（**サーバ・コンテナ・サーバレス混在、オートスケール前提**）。
- 要件: 単一障害前提の高可用設計 / マネージドサービス活用 / トラフィック課金・為替リスク最小化。

## C-3. 移行方針（ページ37-39）
- **数年単位の段階移行**を想定、中長期的なコストの**予測性・安定性**を重視。
- 複数システム間のデータ連携を前提に、**利用中の閉域網を活かした接続構成**。
- オンプレ基幹システムは移行対象外。海外他社クラウドの既存システムは**機能依存度とコスト影響**を踏まえ移行対象を選定。

### システム別の移行判断（重要表）

| 分類 | システム | 特徴 | 方針 |
|------|----------|------|------|
| 基幹 | 販売管理システム | 高いカスタマイズ性、障害時の即時復旧が必要 | **オンプレで継続** |
| 基幹 | 人事給与システム | 機密性の高い個人情報、クローズド環境 | **オンプレで継続** |
| 業務 | 公開システムA | 取引先向け情報配信中心、IP制限前提のインターネット公開 | **他社クラウド→さくらへ移行** |
| 業務 | 公開システムB | イベント駆動型の非同期・**サーバレス前提**で作り込み多い | **他社クラウドで継続** |
| 業務 | データ分析基盤 | 大量データ保有、**クラウド固有サービスへの依存度高** | **他社クラウドで継続** |
| 業務 | 社内認証基盤 | 既存サービスで複雑なガバナンス統制が組込済 | **他社クラウドで継続** |
| 業務 | 社内情報系Web | ポータル/ナレッジ共有、**Web/AP/DBの3層構成** | **他社クラウド→さくらへ移行** |
| 業務 | バッチ処理基盤 | 取引先向けにインターネット経由で帳票・ドキュメント送信 | **他社クラウド→さくらへ移行** |

> 移行判断の軸: **クラウド固有マネージドサービス依存・サーバレス依存・複雑なガバナンス統制 → 残す**／**3層構成・トラフィック課金影響大・新規/再構築 → さくらへ移行**。

## C-4. ネットワーク要件（ページ40）
- 各拠点とDC、および他社クラウド間を接続する**既設の閉域網はそのまま継続利用**。

## C-5. 他社クラウドとの閉域接続の選択肢（ページ41-42）

| 選択肢 | 特徴 | 本ケースでの検討 |
|--------|------|------------------|
| **利用中の閉域網をさくらのクラウドまで延伸** | ダイレクトアクセス経由、または利用中閉域網がプライベートリンク接続可能（OCX等）なら適切サービスで接続。要件を満たせない場合はハウジングラックへの延伸を検討 | **適切（条件付き）** |
| 利用中と異なる閉域網サービスを利用 | さくら⇔他社クラウド間を新たな閉域網で接続し、利用中閉域網とさくら間を直接接続しない。拠点→さくらの通信が他社クラウド経由となり構成が複雑 | **要件に不適切** |
| AWS接続オプション | 他社クラウドがAWS前提。さくら⇔AWS間をさくらの既設回線で接続、利用中閉域網とさくら間を直接接続しない。拠点→さくらの通信がAWS経由となり構成が複雑 | **要件に不適切** |
| インターネットVPN（閉域網との併用含む） | さくら⇔他社クラウド間をサイト間VPNで接続。VPNルータまたはマーケットプレイスのNWサービス等を利用。**VPNルータのサイト間VPN機能はBGP非対応**であり障害時運用に考慮が必要 | クラウド間データ連携の信頼性・セキュリティ要件次第（代替案） |

## C-6. 設計方針と選択する構成（ページ43・図）

**採用: 利用中の閉域網をダイレクトアクセスでさくらのクラウドへ延伸**。

```
 他社クラウド（既存システム）
        │ 閉域回線（グローバルNW）
   [ONU]──[ルータ等]  ← さくらインターネット（ダイレクトアクセス）
        │ ハイブリッド接続
        ▼
   さくらのクラウド
     ├ 新規開発（システム）
     └ 移行（システム）
   （拠点⇔DC⇔他社クラウドの既設閉域網を継続利用）
```

## C-7. 設計上の判断ポイント（ページ44-46）
- **国産クラウドの特徴を活かした適材適所のシステム配置**を検討。
- **海外他社クラウドはトラフィック課金・為替変動の影響を受けやすく、通信量の多いシステムほど中長期のコスト変動リスクが高い**。
- DC⇔クラウド間の閉域接続は**既設回線の延伸を第一候補**とし**ダイレクトアクセス**で接続。条件が合えば OCX・プライベートリンク・AWS接続オプションを選択。

### 注意点・代替案
- クラウドごとに**マネージドサービスの提供範囲・設計思想が異なる**。移行で利用者側の設計・実装・運用負荷が増える場合があり、**単純移行ではなく設計の組み替えを想定した計画とコスト試算**が必要。
- 通信経路の増加に伴う**障害切り分け・責任分界の複雑化**に注意。
- 海外他社クラウド側に高信頼マネージドDBをマスタ運用する場合、クラウド間の都度参照は**アウトバウンド課金・レイテンシ**の影響を受けやすい → 設計で制御:
  - さくら側に参照用データを**複製・同期してローカル参照**。
  - **更新系処理は最小限かつ非同期化**。
- メイン回線（閉域網）の**バックアップ回線、または一時的なクラウド間データ連携経路としてインターネットVPN**を使うケースがある。コスト重視や、将来クラウド間通信の重要度・通信量が低下した場合は**インターネットVPNへの縮退**を検討可能。

### 移行対象の考え方（ページ46・整理）

| さくらへ移行・配置 | 他社クラウドに残す |
|--------------------|--------------------|
| アウトバウンドトラフィック課金の影響が大きい | 機能的に強く依存している |
| 他社クラウドのマネージドサービスに依存していない | 移行コストが非常に高い |
| 海外クラウドにデータを置くことに懸念がある | 通信量が少なく課金影響が軽微 |
| 新規開発・再構築で設計を見直せる | 将来的に廃止予定 |

## 試験対策・要点チェック

### ケースA（基幹システム・閉域網）
- [ ] 3つのNW分離: **業務NW（中核・社内延長）／中間NW（緩衝・検疫/クレンジング/ログ）／公開NW（DMZ・入口出口）**。
- [ ] 業務NW・中間NWは**インターネットから直接到達不可（非公開）**。
- [ ] 中間NW・公開NWで**TCPセッションを終端**して境界制御。**申請ファイルは検疫してから業務NWへ／アップデートファイルは除去しない**。
- [ ] 閉域網引き込みの本命は**ダイレクトアクセス（L3分割が必要、冗長性は回線サービス依存）**。代替: ハウジングラック/OCX/プライベートリンク。
- [ ] **各サーバはNIC2つ**、NW境界は**VPNルータ**で分離、インターネット接続無効化。
- [ ] VPNルータの**ファイアウォールはスタンダードプランでシングル構成**。**プレミアムで冗長化可**。
- [ ] ハイブリッド接続のケーブルは**標準2本（冗長前提）**、シングルなら1本。**閉域網側の冗長設計とルータ設定は利用者責任**。
- [ ] 閉域網引き込みの分類: **既設回線の利用＝プライベートリンク for アルテリア/BBIX(OCX)/NTTドコモビジネス**／**新規引き込み＝ダイレクトアクセス/ハウジングラック**。
- [ ] **このケースはDR対象外**。

### ケースB（SaaS・Web）
- [ ] Web/APは**ステートレス**＋**オートスケールで水平スケール**。**Act/Act**。DBは**Act/Stn**。
- [ ] 認証は**JWT（トークン検証のみ、通常はDB参照しない）**、即時失効は要件外。
- [ ] **CDN＝ウェブアクセラレータ**。画像は**オブジェクトストレージ**、**サブドメイン方式でオリジン設定**。
- [ ] **L7ロードバランサでHTTPS終端＋URLパスルーティング＋HTTPヘルスチェックで異常Web/AP切離し**。
- [ ] DB本命: **プライマリ＋リードレプリカ（セカンダリ）をゾーン間冗長**。**ゾーン停止時は別ゾーンDBがプライマリ化**。
- [ ] 負荷分散の本命: **エンハンスドLB（エニーキャスト）＝切替が速くシンプル、L7高度負荷分散**。代替: **GSLB＋各ゾーンのエンハンスドLB（多段、TTL影響で即時切替不可・数分）**。
- [ ] 代替DB案: **DBアプライアンス（クラスタ）でマネージド型マルチマスタ＋LB(アプライアンス)振り分け**（東京/石狩第2/石狩第3）。
- [ ] **DBがボトルネック**になりうる。キャッシュは**Redis等を利用者自身で構築（マネージドDBキャッシュは無い）**。
- [ ] **DBアプライアンス＋専有ストレージで高IOPS/高スループット、ハイスペックプラン可**。
- [ ] **オブジェクトストレージのリージョン間レプリは自動切替されない** → 切替の仕組みを利用者実装。
- [ ] オートスケールは**各ゾーン最低1台維持**、**最新マイアーカイブを各ゾーンで保持**。
- [ ] 代替: **AppRun専有型＋オートスケーリンググループ＋ロードバランサノード**でWeb/AP運用。

### ケースC（マルチハイブリッド）
- [ ] **オンプレ（基幹・物理数10台）＋海外他社クラウド＋さくらのクラウド**の3者併用、段階移行。
- [ ] さくらへ移行する基準: **トラフィック課金影響大／マネージドサービス非依存／データ国内志向／新規・再構築**。
- [ ] 残す基準: **サーバレス/クラウド固有サービス依存／複雑なガバナンス統制／移行コスト高／廃止予定**。
- [ ] 閉域接続の本命: **利用中の閉域網をダイレクトアクセスでさくらへ延伸（条件付き適切）**。
- [ ] 「異なる閉域網」「AWS接続オプション」は**他社クラウド経由で複雑化＝要件に不適切**。
- [ ] **インターネットVPNはVPNルータのサイト間VPNがBGP非対応**に注意。バックアップ/縮退の選択肢。
- [ ] 海外クラウドは**アウトバウンド課金・為替変動・レイテンシ**に注意。対策＝**ローカル参照用データ複製・更新系の非同期化**。
- [ ] クラウド間で**マネージドサービスの提供範囲・思想が異なる** → 単純移行でなく**設計組み替え＋コスト試算**。
