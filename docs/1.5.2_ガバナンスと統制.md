## 1. サービスポリシー

### 1.1 検討にあたっての考慮事項（コンプライアンス違反防止）
- クラウド利用においては、**利用者の誤操作やルールの理解不足により、意図せずコンプライアンス違反が発生するリスク**が存在する。
  - 操作対象の取り違えによる**重要リソースの設定変更**
  - 組織で**許可されていないサービスや機能の利用**
- **管理者が事前の操作制限を適用**することで、コンプライアンス違反を未然に防止する。
  - 組織の標準的な**ルールテンプレート**を適用し、不適切な操作をブロックする。

### 1.2 さくらのクラウドのサービスポリシー機能
- **組織単位**でリソース作成や操作を制御することができる。
- 誤操作やコンプライアンス違反を防ぎ、**組織全体で統一したガバナンスを確立**できる。

### 1.3 適用と継承の構造（重要：階層図）

サービスポリシーは**組織（最上位）に「適用」され、配下のフォルダ・プロジェクトに「継承」される**。

```
組織  ←── サービスポリシー（適用）
 ├─ フォルダA   （継承）
 │    ├─ プロジェクトA  （継承）→ 東京第1ゾーン利用不可
 │    └─ プロジェクトB  （継承）→ 東京第1ゾーン利用不可
 └─ フォルダB   （継承）
      ├─ プロジェクトC  （継承）→ 東京第1ゾーン利用不可
      └─ プロジェクトD  （継承）→ 東京第1ゾーン利用不可
```

- 階層は **組織 → フォルダ → プロジェクト**。
- 例: 組織に「東京第1ゾーンは利用不可」を適用すると、**全フォルダ・全プロジェクトに継承**され、すべてで東京第1ゾーンが利用不可になる。
- ポイント: サービスポリシーは**リソース階層（組織）に対して継承して適用**される（後述のアクセス制御比較表）。

### 1.4 サービスポリシー機能の設定（4つのルール：最重要表）

設定可能なルールは4種類。**ルール名（識別子）を逐語的に押さえる**こと。
※クラウドマニュアルにて、ルールの一覧と詳細を確認することができる。

| # | ルール名 | 識別子 | 内容 | 設定例 |
|---|----------|--------|------|--------|
| ① | ゾーン制限 | `cloud-restrict-zone` | 利用できる「**場所（ゾーン）**」を制限する | 「石狩第1ゾーン(is1a) だけ許可し、他ゾーンは使えないようにする」 |
| ② | サービス制限 | `cloud-restrict-service` | 利用できる「**機能（サービス）**」を制限する | 「サーバ作成(IaaS) は許可するが、KMSや専用サーバは禁止する」 |
| ③ | 会員認証制限 | `cloud-restrict-member-authentication` | **会員IDでの認証**を制限する | 「さくらのクラウドにおいて会員認証を禁止し、会員IDでの利用を制限する」 |
| ④ | APIキー作成禁止 | `iam-disable-api-key-creation` | **APIキーの新規作成**を禁止する | 「APIキーの新規作成をすべて禁止し、既存キーのみ利用可能にする」 |

### 1.5 アクセス制御の検討（IAMポリシー/IDポリシー vs サービスポリシー：最重要表）

- **サービスポリシーの制限は、IAMポリシーおよびIDポリシーよりも優先して適用される。**
- IAMポリシー・IDポリシーとサービスポリシーは、**どちらか一方だけを使うものではなく、両方の特性を理解し、適切に組み合わせる**。

| 観点 | IAMポリシー、IDポリシー | サービスポリシー |
|------|------------------------|------------------|
| 概要 | 誰が何をできるか（**権限付与**） | 何を禁止／制限するか（**操作制御**） |
| 用途 | 主に**人（ユーザ）の権限管理**に関わる | 主に**リソース操作の制御とガバナンス**に関わる |
| 対象 | **ユーザーやグループ**に対して付与される | **リソース階層（組織）**に対して継承して適用される |

> ⚠️ 試験頻出: **サービスポリシーはIAM/IDポリシーより優先**。サービスポリシー＝「禁止・制限（操作制御）」、IAM/ID＝「権限付与」。

## 2. セキュリティコントロール

### 2.1 検討にあたっての考慮事項（セキュリティ監視と脅威検知）
- クラウド環境では、**リソースの設定ミスや意図しない構成変更**が、セキュリティリスクの発生要因となる可能性がある。
- アクセス制御やログ取得といった対策に加え、**運用中のリソースの状態を継続的に監視**し、潜在的なリスクを早期に発見・対応する仕組みが重要。
- リソース構成の不備（例: **暗号化の未設定、公開範囲の過剰な設定**など）は、インシデントの原因となり得る。
- 誤った設定や予期しない変更を検出することで、**被害の未然防止や対応の迅速化**が可能になる。
- 監視と検知を**自動化**することで、**人的リソースの負荷を抑えつつ**、セキュリティレベルの維持・向上を図ることができる。

### 2.2 さくらのクラウドのセキュリティコントロール機能
- クラウド環境の問題を早期に発見して対応を支援する **イベントログの拡張機能** であり、さくらのクラウド上のリソース設定や挙動を**継続的に監視**できる。

| 機能 | 内容 |
|------|------|
| **発見的統制** | クラウド環境におけるリソースや設定を継続的に監視し、**不正な状態や望ましくない構成を検知して通知**する |
| **脅威検知** | **不審なアクセスや挙動、潜在的な攻撃の兆候を自動的に検知**し、被害が拡大する前に対応を促す |

### 2.3 機能の場所・ダッシュボード
- セキュリティコントロールは、コントロールパネルのホーム画面にある **「イベントログ」＞「セキュリティコントロール」** から確認できる。
- **ダッシュボード**は、検知された**評価結果や対応状況**をひと目で把握できる。

### 2.4 自動アクション（連携）
- セキュリティコントロールで検出されたイベントに対して、**通知やワークフローなどの自動アクション**を設定できる。

| 自動アクション | 内容 |
|----------------|------|
| **シンプル通知との連携** | 検出された**重大度やルール**に応じて、**メールなど**で自動通知を送信できる |
| **ワークフローの実行** | 特定の検出条件を**トリガー**として、ワークフローを自動的に起動できる |

### 2.5 評価ルール（運用指針）
- 各ルールに基づいて、**リソースが適切に設定されているか評価**される。
- 教材で挙げられた評価ルール例（識別子を押さえる）:

| 評価ルール（識別子） | 内容 |
|----------------------|------|
| `iam-member-operation-detected` | **会員権限による操作検知** |
| `server-no-public-ip` | **パブリックIPアドレス割り当て検知** |

### 2.6 評価結果と対応指針（重大度：最重要表）
- セキュリティコントロールの検出結果は重大度に応じて **「低・中・高／致命的」** に分類され、それぞれに**推奨される対応方針**が定められている。
- 影響が小さい項目は必要に応じて対応し、**リスクが高い項目ほど、計画的または迅速な対応**が求められる。

| 重大度 | 説明 | 推奨対応 |
|--------|------|----------|
| **低** | 侵害に直接つながらない。不要なら抑止設定可 | 必要に応じて対応 |
| **中** | 悪用されればアクセス権奪取などに至る可能性あり | チケット管理し、定期的に対応検討 |
| **高 / 致命的** | 任意コード実行やデータ引き出しの恐れあり | 可及的速やかに対応、臨時メンテ実施 |

### 2.7 Tips：評価結果の取り扱い
- 評価結果はあくまで **「リスクの可能性」を示すもの**であり、**最終的な対応判断は利用者自身で行う必要がある**。

## 3. 試験対策・要点チェック

- [ ] ガバナンスと統制は2本柱: **サービスポリシー（予防的統制）** と **セキュリティコントロール（発見的統制／脅威検知）**。
- [ ] サービスポリシーは **組織単位** で制御し、階層 **組織 → フォルダ → プロジェクト** に **継承** される。
- [ ] サービスポリシーの4ルール: **①ゾーン制限 `cloud-restrict-zone` / ②サービス制限 `cloud-restrict-service` / ③会員認証制限 `cloud-restrict-member-authentication` / ④APIキー作成禁止 `iam-disable-api-key-creation`**。
- [ ] **サービスポリシーは IAMポリシー・IDポリシーより優先**して適用される。
- [ ] IAM/IDポリシー＝「**誰が何をできるか（権限付与）**」「**ユーザ・グループ**対象」。サービスポリシー＝「**何を禁止／制限するか（操作制御）**」「**リソース階層（組織）**に継承適用」。
- [ ] セキュリティコントロールは **イベントログの拡張機能**。コントロールパネルの **「イベントログ」＞「セキュリティコントロール」** から確認、**ダッシュボード**で評価結果・対応状況を把握。
- [ ] 自動アクション: **シンプル通知との連携（メール通知）** と **ワークフローの実行（トリガー起動）**。
- [ ] 評価ルール例: `iam-member-operation-detected`（会員権限による操作検知）、`server-no-public-ip`（パブリックIPアドレス割り当て検知）。
- [ ] 重大度は **低・中・高／致命的** の3区分。**高/致命的＝任意コード実行やデータ引き出しの恐れ → 可及的速やかに対応・臨時メンテ**。
- [ ] 評価結果は **「リスクの可能性」** を示すのみで、**最終判断は利用者**が行う。
