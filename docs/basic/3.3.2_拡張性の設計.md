## 1. リソースの上限値

### 作成上限値とは
- さくらのクラウドでは、各リソースに **作成できる数や拡張数の上限（作成上限値）** が設けられている。目的は次の3つ。
  - **APIのプログラミングミスによる誤操作**の防止
  - **急速な在庫枯渇による他の利用者への影響**の防止
  - **クラウド基盤システムの制約**への対応
- 上限は **プロジェクト・ゾーン・各サーバ単位** で設定される。
- 作成上限値は **すべてのプロジェクトにデフォルトで設定**されている。**クラウドマニュアル**で公開されているほか、**コントロールパネル上でも表記を確認**できる。

### 作成上限値の引き上げ
- 利用者が **サポート宛にメールで問い合わせる**ことで、引き上げを依頼できる。
  - さくらインターネット側で **利用者の過去の利用実績を確認**した上で、引き上げの可否が判断される。
  - 引き上げ依頼用の **メールテンプレートはクラウドマニュアル**で確認できる。
- 引き上げ後、**申告した消費ペースと実際のリソース利用に乖離がある場合**、適切なリソース提供のために **上限が引き下げられる可能性がある**。

### 検討にあたっての考慮事項
- 大規模システム構築時は、**作成予定のリソース数を事前に確認**し、必要に応じて引き上げを依頼する。

### 主要な上限値（重要表・数値逐語）

| 品目 | 上限値 |
|------|--------|
| プロジェクト | 1会員IDあたり **3個** |
| サーバのメモリ割当量 | 1プロジェクトあたり、各ゾーンごとに合計 **300GB** |
| ディスクのサイズ | 1プロジェクトあたり、各ゾーンごとに合計 **20TB** |
| 自動バックアップの作成上限数 | 1プロジェクトあたり、**5設定** |

> ⚠️ 試験頻出: メモリ割当量・ディスクサイズは「**1プロジェクトあたり、各ゾーンごと**」の合計値であることに注意。

## 2. リソースの制限値

### 制限値とは
- **クラウド基盤システムの制約により変更できない上限値**や、**仕様上の制限値**が存在する。情報は **クラウドマニュアル**で確認できる。
- **スイッチ**については、定められた上限値とは別に、**ネットワークリソースが不足する可能性のあるゾーン**において、**新規のスイッチ作成が制限されている場合がある**。

### 主要な制限値（重要表・数値逐語）

| 品目 | 制限値 |
|------|--------|
| サーバ1台あたりに接続可能なディスク数 | 最大 **3個** |
| 1つのアーカイブの最大サイズ | **1TB** |
| 1つのパケットフィルタに登録可能なルール数 | **30個** |

### 利用可能なリソースの制限（Tips）
- サーバの **2枚目以降の追加NIC** を、**共有セグメントやルータ＋スイッチに接続することはできない**。
- さくらのクラウドのネットワーク上で、**タグVLANを使用することはできない**。
- スイッチに接続するリソースの台数に **制限はない**。ただしARPストーム発生の懸念があるため、**1つのスイッチに対する接続台数は200台程度を上限**とすることが推奨される。
- ディスクは **プランに応じてIOPSとデータ転送帯域の基準値** が設けられ、基準値で性能が制限される（基準値はクラウドマニュアルで確認）。

## 3. ネットワーク帯域の制限値

### 全体方針
- **共有セグメント・スイッチ・ルータ＋スイッチ** それぞれに利用可能なネットワーク帯域の制限がある。予想されるトラフィックを事前に確認し、要件にあったリソースとプランを選択する。

### 共有セグメント
- サーバからの **アウトバウンド通信（送信方向）は 100Mbps** で帯域制限される。
- **インバウンド通信（受信方向）の帯域は制限されない**。

### スイッチ
- スイッチに接続されたサーバは、**サーバの搭載メモリ量に応じて** スイッチへのアウトバウンド通信の回線帯域が制限される。**インバウンド通信は制限されない**。
- ただし接続サーバが **専有ホスト上で稼働している場合**、対象サーバとスイッチ間の回線帯域は **制限されない**。専有ホストの接続回線は **10Gbpsのベストエフォート**であり、専有ホスト上で稼働するサーバの合計帯域の上限は **おおよそ10Gbps** となる点に注意。
- スイッチに接続される **アプライアンスやブリッジ** については、対象リソースとスイッチ間の帯域は **制限されない**。

#### 搭載メモリ量と帯域制限値（重要表・図16/18より）

| サーバ搭載メモリ量 | 帯域制限値 |
|--------------------|-----------|
| 32GB未満 | **1.0Gbps** |
| 32GB以上 128GB未満 | **2.0Gbps** |
| 128GB以上 224GB未満 | **5.0Gbps** |
| 224GB以上 | **10.0Gbps** |

> ※ この表は「スイッチ」「ルータ＋スイッチ」のいずれも同一の帯域制限値（図16・図18で共通）。

### ルータ＋スイッチ
- 接続サーバは **スイッチと同様の条件で帯域が制限される**（上表が適用される）。
- **専有ホスト上で稼働するサーバ・アプライアンス・ブリッジ** は、スイッチと同様に **帯域は制限されない**。
- グローバルネットワークとルータ＋スイッチの帯域は、**アウトバウンド・インバウンドそれぞれに対して確保**され、**プランに応じた帯域**を利用できる。
  - 例: 接続帯域 **500Mbps** のプランを選択した場合、ピーク時には **受信方向・送信方向それぞれに500Mbps** の共有帯域を利用可能。
  - （図18）グローバルネットワークの接続帯域プランは **100〜5000Mbps**。

### 転送量に応じたトラフィック制限
- 接続する回線（**共有セグメント、ルータ＋スイッチ**）ごとに **転送量目安** があり、トラフィックが目安を **大幅に超過**するとサーバの帯域が制限されることがある。転送量目安はクラウドマニュアルで確認。
- 帯域制限が実施される場合、通常は **緊急連絡用メールアドレス宛に事前連絡**される（ただし緊急時はその限りではない）。
- （Tips）ルータ＋スイッチの転送量目安は、接続されている **全リソースの合計転送量**。トラフィックは **アウトバウンド・インバウンドそれぞれ個別に計算**され、**グローバルネットワークとの通信が対象**（スイッチ内で完結する通信は対象外）。

#### 転送量目安（重要表・図20より ※一部の情報のみ。完全な情報はクラウドマニュアル参照）

| 回線 | 制限を行う転送量しきい値の目安 |
|------|------------------------------|
| 共有セグメント（100Mbps） | 月間 **1.6TB**（平均5Mbps） |
| ルータ＋スイッチ（100Mbps） | 月間 **3.2TB**（平均10Mbps） |
| ルータ＋スイッチ（250Mbps） | 月間 **8.1TB**（平均30Mbps） |

## 4. パケットの制限

- 共有セグメント・スイッチ・ルータ＋スイッチでは **通過できるパケットが制限**されている。一般的な利用では影響は少ないが、特定条件下で運用する場合は事前確認が必要。

### サーバ → 共有セグメント に発信されるパケット

| 区分 | 条件 |
|------|------|
| 通過できる | ソースIPアドレスがサーバに割り当てられたIPアドレス |
| 通過できる | ARPパケットのSender IP addressがサーバに割り当てられたIPアドレス |
| 通過できない | ソースMACアドレスがサーバ作成時に割り当てられたものと異なる |
| 通過できない | ARP以外のブロードキャスト／マルチキャストパケット |
| 通過できない | その他、通過できる条件に当てはまらないパケット |

### サーバ → スイッチ または ルータ＋スイッチ に発信されるパケット
- **通過できる条件**:
  - **IPv6パケット、ARPパケット、DHCPパケット**（DHCPはUDPソース68番ポート・宛先67番ポートのもの）
  - ソースMACアドレスが **VRRPの仮想MACアドレス（VRID 1〜4）**
  - **ユニキャストパケット**
  - ブロードキャスト／マルチキャストの場合は、以下のプロトコルのみ: **ARP、DHCP、IPv6、VRRP、OSPF、RIP**
  - ルータ＋スイッチの場合は、ソースIPアドレスが **ルータ＋スイッチに割り当てられたIPアドレス範囲**
- **通過できないパケット**:
  - ソースMACアドレスがサーバ作成時に割り当てられたものと異なる
  - その他、通過できる条件に当てはまらないパケット

## 5. システムの拡張性（設計の考え方）

- システムの需要変化に対応できるよう、**サービスの継続性を保つ柔軟なシステム構成**を検討する（サーバのスペック・台数、ストレージ保存領域を必要に応じて増減）。
- **各役割に応じてサーバを稼働**させ、**特定のサーバのみを独立してスケーリング**する構成を検討する。これにより、トラフィック増加や負荷発生時に **ボトルネックのサーバのみをスケーリング**可能。
- 求める拡張性を実現可能な機能・サービスを選択する。さくらのクラウドでは **オートスケール機能、オブジェクトストレージ** などの選択肢がある。

---

## 6. 負荷に応じたスケーリング（オートスケール）

### 基本概念（重要）
- システム運用中の負荷に応じて、サーバの **スペック増減** や **台数増減** を行う。

| 用語 | 意味 |
|------|------|
| 垂直スケール | サーバの **スペック増減** |
| 水平スケール | サーバの **台数増減** |
| スケールアップ／スケールダウン | スペックを **上げる／下げる**（垂直） |
| スケールアウト／スケールイン | 台数を **増やす／減らす**（水平） |

- **オートスケール機能** を使うと自動的にサーバをスケーリングできる。負荷発生時に **スケールアップとスケールアウトの両方を利用可能**。負荷が解消されると自動的に **スケールダウン／スケールイン** が行われる。

### サーバのオートスケールの構成上の考慮
- サービス継続維持のため、**複数サーバによる分散構成**を前提とし、**グローバルネットワークに負荷分散用リソースを配置**する構成を検討する。
  - **垂直スケール**時は、**プラン変更に伴いサーバ停止が発生**することを考慮。
  - **水平スケール**時は、**スケールアウトしたサーバへアクセスを振り分ける**必要があることを考慮。
- オートスケールをサポートする負荷分散用リソース: **GSLB、エンハンスドロードバランサ、ロードバランサ**。**DNSアプライアンスを使ってDNSラウンドロビン**の構成もとれる。

### トリガーと監視間隔（試験頻出）
- オートスケールの **トリガー**として、次のいずれかを選択できる。
  - サーバのアクティビティの **CPU時間（CPU TIME）**
  - ルータ＋スイッチのアクティビティの **トラフィック**
- オートスケール機能の **監視は10分間隔** で実行される。
- （Tips）**API**を利用すれば、設定内容に基づき **任意のタイミング**で実行可能。対応していないトリガーや監視間隔で動かしたい場合は、利用者がAPI等で必要なデータを取得し、そのデータに基づいてAPIで実行する作り込みを検討する。

### ステートレスな構成（重要）
- 水平スケール構成では、**スケールイン時のデータ消失に備えて、特定サーバに依存しないステートレスな構成**を実装する。
  - スケールインでは **サーバとディスクが自動的に削除**されるため、各サーバの **ローカルに保持したデータはディスク削除とあわせて消失**する。
  - ステートレスな構成として、**外部のデータベースやNFS領域内**で必要なデータを保持する選択肢がある。
  - 一般的に **セッション情報やログ（アクセスログ等）** は、スケールイン後にも保持しておくデータ。
- 図（ステートフル vs ステートレス）: ステートフル構成ではスケールインでユーザのセッション情報が消失する。ステートレス構成では **セッション情報を外出し**して消失を防ぐ。

### 台数維持機能
- サーバ障害時の自動復旧や一定台数の維持が求められる場合は、**水平スケールの台数維持機能**の利用を検討する。
  - **ヘルスチェックで不健康と判定されたサーバを自動的に入れ替える**仕組み。復旧作業の自動化・可用性向上に寄与。
  - 短時間のレスポンス遅延などで **誤検知**が発生する可能性があるため、ロードバランサ／エンハンスドロードバランサ連携を使う構成では、**アプリケーションの特性に応じてヘルスチェック設定を適切に**行う。

### 運用上の注意・スケジュール実行
- オートスケールは **予期せぬサーバ負荷でも発動**するため、運用開始後も継続的に動作確認し、設定をチューニングしていく必要がある。
- （Tips）**スケジュール機能**で、予め登録した任意の時間にスケーリングを実行できる。負荷が高くなる時間帯を見越して、あらかじめスケールアップ・スケールアウトしておく運用も可能。

### ルータ＋スイッチのスケーリング
- 運用中に発生したトラフィックに応じて、**ルータ＋スイッチの帯域を増減**することを検討する。オートスケール機能で自動スケーリング可能。
- （Tips）オートスケールでは **ルータ＋スイッチのトラフィック増減によってルータのプランを変更**できる。**ルータのプラン変更は無停止**で行え、可用性を維持した帯域のスケールアップ・ダウンを単体で実現できる。

### ディスクのスケーリング
- 運用中のデータ容量に応じてディスクサイズを増やすことを検討。ただし前提あり。
  - ディスクサイズを増やす場合、**接続サーバの停止が必要**。
  - **対象ディスクのサイズを直接増減することはできない** → 対象ディスクを **コピー元とし、よりサイズの大きいディスクを新規作成**する手順となる。
  - 新規ディスク作成後、**パーティション拡張機能（またはOS内操作）でファイルシステムのパーティションを拡張**し、サーバの接続ディスクを新ディスクに変更する必要がある。

### データベースアプライアンスのスケーリング
- 負荷や容量に応じてスケーリングを検討。ただし前提あり。
  - **プラン変更により CPUコア数・メモリサイズ・ディスクサイズをスケールアップ可能**。ただし **データベースアプライアンスの停止が必要**で、柔軟なスケーリング運用は難しいことを前提とする。
- **リードレプリカ** を使うことで **読み取り性能を向上**できる。大量アクセスが予測される場合やアクセス増加が見込まれる際に検討。
  - リードレプリカは **作成後に後から有効化が可能**。ただし **有効化時にデータベースアプライアンスの停止が必要**。

## 7. スケーラブルなストレージ（オブジェクトストレージ）

- 大量のデータを取り扱う場合は **オブジェクトストレージ**の使用を検討する。**保存するデータ量に応じて容量を拡張**できるため、将来必要となる容量の予測が難しい場合でも高い拡張性を持つ構成を実現できる。

### 容量の目安（重要表・数値逐語）

| 項目 | 値 |
|------|-----|
| 1バケットあたりの最大容量 | **10TiB** |
| 1プロジェクトあたりに作成可能な最大バケット数 | **20個** |
| 標準で利用可能な最大容量 | **200TiB**（= 10TiB × 20バケット） |

## 8. 試験対策・要点チェック

- [ ] 作成上限値の目的 = **誤操作防止／在庫枯渇による他者影響防止／基盤システムの制約**。
- [ ] 上限値: プロジェクト **3個/会員ID**、メモリ **300GB/プロジェクト・ゾーン**、ディスク **20TB/プロジェクト・ゾーン**、自動バックアップ **5設定/プロジェクト**。
- [ ] 制限値: サーバ接続ディスク **最大3個**、アーカイブ最大 **1TB**、パケットフィルタのルール **30個**。
- [ ] 共有セグメントのアウトバウンドは **100Mbps制限**、インバウンドは無制限。
- [ ] スイッチ／ルータ＋スイッチの帯域はメモリ量依存: **32GB未満=1.0 / 〜128GB=2.0 / 〜224GB=5.0 / 224GB以上=10.0Gbps**。専有ホストは制限なし（合計約10Gbpsベストエフォート）。
- [ ] スイッチ接続台数の推奨上限 = **200台程度**（ARPストーム対策）。**タグVLAN不可**、**2枚目以降の追加NICは共有セグメント／ルータ＋スイッチに接続不可**。
- [ ] オートスケールのトリガー = **CPU TIME** または **ルータ＋スイッチのトラフィック**。**監視は10分間隔**。
- [ ] 用語: スペック増減＝**垂直スケール**、台数増減＝**水平スケール**。
- [ ] スケールインで **サーバとディスクが削除** → ローカルデータ消失。対策は **ステートレス構成**（外部DB/NFSにセッション・ログを外出し）。
