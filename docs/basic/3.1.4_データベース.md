## 1. データベースアプライアンスの基礎

### 概要
- **データベースサーバ**を提供するアプライアンス。**RDBMS（リレーショナルデータベース管理システム）**を利用でき、**データベースサーバの運用コストを削減**できる。
- **RDBMS** = 行と列の表形式でデータを蓄積し、複数の表を関連付けて複雑なデータを整理保管する。データの一貫性が保たれる。
- **データベース管理システム** = データベース全体の機能を提供するソフトウェア。作成・管理・操作を行い、**SQL**でデータを操作する。

### 提供プラン（重要：冗長化オプションの有無で体系が異なる）

| 区分 | プランの決まり方 | 仮想コア数・メモリ | ディスクサイズ |
|------|------------------|--------------------|----------------|
| **冗長化オプションあり** | CPUの仮想コア数 × メモリサイズの組み合わせ | プランで選択 | **全プランで共通**（共通から選択） |
| **冗長化オプションなし** | ディスクサイズ | **ディスクサイズに応じて自動的に決定** | プランで選択 |

> ⚠️ 試験頻出: 冗長化**なし**は「ディスクサイズを選ぶと仮想コア数とメモリが決まる」。冗長化**あり**は「コア数×メモリの組み合わせでプランが決まり、ディスクサイズは共通」。

### 料金・ディスクに関するTips
- 料金は**プランと冗長化オプションの有無**に応じて、**時間額・日額・月額**が設定されている。
- 使用ディスクは**全プラン共通でSSD**。アプライアンスとして一体化されており、**ディスク料金はアプライアンス料金に含まれる**。
  - ディスクを個別リソースとして管理できず、**コントロールパネルのディスクメニューにも表示されない**。
- **専有ホスト（専有ストレージ用）および専有ストレージ上**に作成可能。この場合、**アプライアンス自体には課金されず**、専有ホスト・専有ストレージに対してのみ**月額固定料金**が発生する。

## 2. 冗長化オプション

### 概要
- データベースサーバを**2台で冗長化**し、それぞれのデータベース内容を**常時同期**させる機能。
- いずれか一方のデータベースを収容するホストサーバが停止しても、**動作を継続**できる。
- 構成は VIP（仮想IP）配下に Primary / Secondary を配置し、障害時に役割が切り替わる（フェイルオーバ）。

### 仕様（重要表）

| 項目 | 仕様 |
|------|------|
| 構成 | 冗長構成の各サーバとも**同一ゾーン**に配置される |
| スペック | 各サーバとも**同じ仮想コア数・メモリサイズ・ディスクサイズ** |
| 必要IPアドレス数 | **3個**（仮想IPアドレス1個 + 各サーバの実IPアドレス2個） |
| レプリケーション | **不可** |

> ⚠️ 必要IP数は **3個**（VIP×1 + 実IP×2）。冗長化オプションありでは**レプリケーション（リードレプリカ）は不可**＝併用不可（後述）。

## 3. リードレプリカ機能

### 概要
- **読み込み専用**のデータベースサーバを作成する機能。
- **マスター側**のデータベースアプライアンスを指定すると、その複製が**リードレプリカ**として作成される。
- 用途: 参照(SELECT)系を分離し、**マスター側データベースの負荷を軽減**。大量データや複雑なクエリを扱う処理をレプリカ側に逃がす（更新(UPDATE)はマスター）。

### 仕様（重要表）

| 項目 | 仕様 |
|------|------|
| 構成 | マスターとレプリカは**同一ゾーン**に配置 |
| スペック | レプリカは**マスターと同じプラン**で複製（コア数・メモリを個別指定できない） |
| マスター1台あたりの作成可能数 | **最大3台** |
| 同期方式 | **非同期レプリケーション**。マスター更新から**数秒～数十秒程度の同期遅延**が発生 |
| マスターへの昇格機能 | **なし** |
| リードレプリカのバックアップ | **取得不可** |

### 作成時のTips
- 作成前に、**マスター側でリードレプリカを有効化**し、**レプリカユーザ(replica)のパスワード**を設定しておく必要がある。
- 有効化はアプライアンス作成後でも変更可能だが、**対象アプライアンスの停止が必要**。
- 作成時に**仮想コア数・メモリサイズは指定できない**。マスターと同じプランで個別のリソースが作成される。

---

## 4. 冗長化オプションとリードレプリカの関係（重要）

- **冗長化オプションとリードレプリカは併用できない**。有効化できるのは**いずれか片方のみ**。
- データベース一覧画面の **「構成」** 表記で、両者の有無を確認できる。

| 構成の表記 | 冗長化オプション | リードレプリカ |
|------------|------------------|----------------|
| シングル | なし | なし |
| 冗長化 | あり | なし |
| レプリケーション有効 | なし | あり（マスター側データベース） |
| マスター：IPアドレス | なし | あり（レプリカ側データベース） |

## 5. データベースクラスタ

- **3台のノード**で構成されたデータベースサーバを利用する機能。
- **ゾーンA / ゾーンB / ゾーンC** にそれぞれ Master ノードを配置し、相互にデータ同期する。
- **Active-Active型のマルチマスター構成**。
- 接続時は**各ノードに割り当てたIPアドレス**にアクセスし、どのノードへ接続するかは**アプリケーション側で指定**する（ロードバランサ（アプライアンス）併用時はLBの仮想IPで自動振り分け、後述）。

## 6. データベースアプライアンスの作成

### 作成時の主な選択肢
- **冗長化オプション**: 利用する場合は有効にする。
- **リードレプリカ**: 利用する場合は有効にする。
- **クローン**: 既存のデータベースアプライアンスをクローンして作成する場合に選択。
- **TCPポート**: データベース接続用のTCPポートを指定可能。
- 詳細画面でデータベース接続用の**SQLコマンド例**を確認できる。

### データベース（RDBMS）
- 利用可能なRDBMS: **PostgreSQL、MariaDB**。
- **デフォルトユーザ**を設定する（利用者がDBに接続するためのユーザ）。
  - **ユーザ名と同名のデータベースが自動的に作成される**。
- バージョン表記は基本 **X.Y.Z**（X.Y=メジャー、Z=マイナー）。Y表記やマイナー表記がない場合もある。不具合修正・セキュリティ更新で付与される**パッチバージョン**がある。
- ⚠️ 利用者には**管理者権限が付与されない**（PostgreSQLのSuperuserロール、MariaDBのSUPER権限/ALL PRIVILEGES権限は無し）。DBの作成・管理に必要な権限のみ。

### ネットワーク（重要）
- **スイッチ**、または**ルータ＋スイッチ**に接続する必要がある。**共有セグメントには接続不可**。
  - 冗長化オプションありの場合は、**スイッチにのみ接続可能**。
- データベース接続用TCPポート番号を指定可能。
  - **デフォルト: 5432（PostgreSQL）/ 3306（MariaDB）**。
  - 冗長化オプションありの場合は、**デフォルトから変更不可**。
- **ゲートウェイのIPアドレスは必須**設定。
- ⚠️ 作成後は、**接続先スイッチの変更・切断、およびIPアドレス等のネットワーク設定の変更はできない**。

## 7. データベースアプライアンスの利用

### 電源操作
- 停止・再起動などサーバと同様の操作が可能（**cloud-init起動を除く**）。
- 起動中リソースの **「DBインスタンス再起動」** が可能。
- 作成後は**自動的に起動**する。
- 削除する場合は**停止が必要**。
- 起動失敗時は詳細画面の**「ログ」タブ**でシステムログ・エラーメッセージを確認。MariaDBでは**Syslog転送**の設定も可能。

### クローン機能
- データベースの内容や設定情報を含めて**複製**を行う機能。
- 複製先は、クローン元と**同じか上位のプラン**を選択する必要がある。
- クローン元と**同じデータベースエンジン**を使用し、メジャーバージョンは**同じかそれ以降**を選択する必要がある。
- ⚠️ **冗長化オプションありのアプライアンスはクローン不可**。

### バックアップ
- 自動または手動で取得可能。取得・復元時は**対象アプライアンスが起動している必要**がある。
- バックアップデータは**最大8世代まで保管可能**。
- 方式は **「バックアップ(v1)」** と **「継続的バックアップ」** から選択。**いずれか一方のみ**有効化可能。

#### バックアップ(v1)
- **手動バックアップ**（いつでも実行可）と**定期バックアップ（自動取得）**の両方が利用可能。
- 復元は**「取得したバックアップの時点」に戻す方式**。
- 定期バックアップの設定: **実行間隔（毎日 or 曜日選択）** と **実行時間（0時〜24時、15分単位）** を指定。

#### 継続的バックアップ（PITR）
- データベース全体のバックアップ（**物理バックアップ**）に加え、**トランザクションログを継続取得**し、**任意の時点へ復元（PITR: Point in Time Recovery）**できる。
- バックアップ保存先に **NFSアプライアンス**を準備する必要がある。
- 復元は、**既存とは別の新しいアプライアンス**として復元される。
- 設定: **バックアップ先（NFSアプライアンス）/ 実行間隔（毎日 or 曜日）/ 実行時間（0時〜24時、15分単位）**。
- 特定のデータベースエンジン・バージョンでのみ利用可能で、**冗長化オプションを有効にした構成では利用不可**。
- 世代管理・削除はアプライアンス側で自動。NFS上のバックアップファイルを直接操作するとPITR動作は保証されない。

#### バックアップ保存場所のTips
- バックアップデータは**アプライアンスのディスクとは別の領域**に保存される（DBの保存領域を圧迫しない）。
- ただし**冗長化オプションありの場合は、保管場所として別途NFS共有領域を利用者側で用意する必要**がある（NFSアプライアンスの利用を検討）。
- 冗長化なしの場合でも、**特定エンジン・バージョンではNFS共有領域を指定可能**。

### アクセス制限
- データベース接続を許可する**ネットワークを制限**できる。許可する**IPアドレス、またはネットワーク範囲**を指定する。

### バージョン更新機能
- 利用中のデータベースの**パッチバージョン**を更新できる。
- 対象バージョンや構成に利用条件あり（詳細はクラウドマニュアル参照）。
- **時間指定での自動更新**、または**任意タイミングでの手動更新**が可能。手動は**「バージョン設定」タブ**から実行。

## 8. データベースアプライアンスの検討（設計の考え方）

### エンジン・種類の選択
- 導入するソフト・アプリのシステム要件に応じてデータベースの種類とエンジンを選択する。
- リレーショナル型以外に**NoSQL・時系列データベース**など複数タイプがある。**データベースアプライアンスはリレーショナル型**であるため、それ以外は**利用者がサーバ上に構築**する必要がある。
- さくらのクラウドでDBを運用する2つの選択肢:
  - a. **データベースアプライアンスを利用する**（エンジンが **PostgreSQL / MariaDB** の場合に検討）
  - b. **利用者がサーバ上にデータベースを構築する**
- ⚠️ さくらのクラウドの仕様上、**Oracle DB は運用できない**。専用サーバPHY上にOracle DBをセットアップし、**ブリッジ接続経由でクラウドサーバと連携**することを検討する。

### プラン・オプション選択
- 冗長化オプション**あり**は**高スペックのプラン**を選択でき、**大規模システムに適する**。
- 冗長化オプション**なし**は、**ディスクサイズを選ぶとCPU仮想コア数とメモリが決まる**点に留意。
- リードレプリカ、バックアップ、アクセス制限、プラグイン利用、RDBMSのパラメータ変更などの機能が利用可能。
- 専有ホスト（専有ストレージ用）・専有ストレージ上でのみ作成可能な**高スペック専用プラン**がある: **16TBプラン（64コア / 512GBメモリ）**。

### バージョン更新の方法（更新種別ごと）

| 更新種別 | 更新方法 | 留意事項 |
|----------|----------|----------|
| パッチバージョンの更新 | **バージョン更新機能**で実施 | 対象DB・バージョン・構成により利用条件が異なる。更新時にDBが再起動し一時的に利用不可となるため計画的に実行 |
| メジャー／マイナーバージョンの更新 | **クローン機能**で実施 | 起動状態でのクローン取得は可能だが、バックアップから復元されるデータの整合性は保証されない。更新後バージョンは**新規作成時に選択可能なものに限られる** |

### 接続方式
- サーバ上のアプリ等から**ネットワーク経由でアクセス**する方式。**コンソール機能が無い**ため、セットアップやクエリ実行にもネットワーク経由アクセスが必要。
- アプライアンスは**グローバル／ローカルどちらのネットワークにも接続できるが、接続できるのは一つのみ**。
- 冗長化オプションありは、必ず**仮想IPアドレス**にアクセスする（実サーバの物理IPに直接アクセスすると予期しない不整合の恐れ）。
- データベースクラスタ利用時は**各ノードのIPアドレス**にアクセスし、接続先はアプリ側で指定。**ロードバランサ（アプライアンス）**で自動振り分けする場合は、**LBに設定した仮想IPアドレス**にアクセスする。

### バックアップ・クローン運用上の注意
- **バックアップ(v1)** によるデータ取得・復元は**データの整合性が保証されない**。
  - 取得中はDB内データへのアクセスを控えることが推奨。定期バックアップの実行時間を検討する。
  - 復元時は接続元ネットワークを制限し、アクセスを発生させない。
- クローンする場合も、クローン元の接続元ネットワークを制限し、**アクセスを発生させずにバックアップを取得した後にクローン**することが推奨。
- 障害・操作ミスによるデータ不整合に備え、**継続的バックアップ（PITR）**で任意の時点に復元できる運用を検討する。
  - **物理バックアップの取得頻度はトレードオフ**:
    - 頻繁に取得 → 復元時間は短いが、復元できる期間も短い。
    - 取得間隔が長い → 復元時間は長いが、より過去まで復元できる。
  - 物理バックアップの取得頻度は**最短で1日1回**、保持期間は**最大8世代**が前提。

## 9. 試験対策・要点チェック

- [ ] データベースアプライアンスは**リレーショナル型**。利用可能RDBMSは **PostgreSQL / MariaDB**。**Oracle DBは運用不可**（PHY＋ブリッジ接続で連携）。
- [ ] ディスクは**全プラン共通でSSD**、料金はアプライアンスに含まれ、**ディスクメニューに表示されない**。
- [ ] 冗長化**あり**＝コア数×メモリでプラン決定・ディスク共通。冗長化**なし**＝**ディスクサイズを選ぶとコア数・メモリが決まる**。
- [ ] 冗長化オプション = 2台・常時同期・同一ゾーン・**必要IP 3個（VIP1+実IP2）**・**レプリケーション不可**。
- [ ] リードレプリカ = 読み込み専用・**最大3台**・**マスターと同じプラン**・**非同期レプリケーション（数秒〜数十秒遅延）**・**昇格機能なし**・**バックアップ取得不可**。事前に有効化＋replicaユーザPW設定（変更には停止が必要）。
- [ ] **冗長化オプションとリードレプリカは併用不可**（片方のみ）。一覧の「構成」表記で判別。
- [ ] データベースクラスタ = **3ノード（ゾーンA/B/C）・Active-Active型マルチマスター**。接続先はアプリ指定 or LB（アプライアンス）の仮想IP。
- [ ] デフォルトユーザ作成で**同名DBが自動作成**。利用者に**管理者権限は付与されない**。
- [ ] ネットワーク: スイッチ or ルータ＋スイッチ、**共有セグメント不可**。デフォルトポート **5432（PostgreSQL）/ 3306（MariaDB）**。冗長化ありはポート変更不可。**作成後のNW設定変更不可**。
- [ ] クローン = クローン元と**同じか上位プラン**・**同じエンジン**・**同じか以降のメジャーバージョン**。**冗長化ありはクローン不可**。
- [ ] バックアップは **最大8世代**。**バックアップ(v1)**（取得時点へ復元）と**継続的バックアップ(PITR・NFSアプライアンス必須・別アプライアンスで復元)** のいずれか一方。定期バックアップは間隔（毎日/曜日）＋時間（0〜24時、15分単位）。
- [ ] 継続的バックアップは**冗長化オプション有効構成では利用不可**。物理バックアップは**最短1日1回・最大8世代**前提。
- [ ] バージョン更新: **パッチ＝バージョン更新機能 / メジャー・マイナー＝クローン機能**。
- [ ] 専有ホスト・専有ストレージ上の高スペック専用プラン: **16TBプラン（64コア / 512GBメモリ）**。
