## 1. さくらのクラウドにおける認証

### 会員ID
- さくらインターネットのサービスを申し込む際、**利用者ごとに一意に付与されるID**。
- **アルファベット3文字と数字5文字**で構成（例: `nnn12345`）。
- サービスの利用に重要な情報。会員ごとにユニークで、**利用者の個人情報に相当**。第三者に共有せず安全な場所に保管する。
- **会員IDには管理者権限が付与されている**。
- 会員IDでログインすると、**会員IDで作成した全てのプロジェクトにアクセス可能**。

### プロジェクト
- **リソースの作業空間**を表す。
- **リソースの管理と請求処理は、プロジェクトごとに区分される**。

### クラウドユーザ（ユーザ）
- リソースを操作するために用いる。
- リソースを操作する**社員やメンバーごとにユーザを作成する**。

### ユーザグループ
- ユーザをグループ化し、**ユーザグループごとにアクセス権限をコントロール**する機能。
- グループに所属する**全ユーザにまとめて権限を適用**できる。

### サービスプリンシパル
- システムやアプリケーションが**APIにアクセスするための認証手段**。
- 主に**自動処理やシステム連携**などの用途で利用する。

### プリンシパル（重要）
> 【Tips】プリンシパル（Principal）とは、「**誰が操作を実行するか**」を表す概念。さくらのクラウドでは **ユーザ・グループ・サービスプリンシパルの三種類**を指す。

### プロジェクトと権限管理の仕組み（図）
- 会員IDでログインすると、全てのプロジェクト（**リソース利用と請求の単位**）にアクセス可能。
- プロジェクトは顧客・案件・プロジェクトごとに作成し、リソースと請求を分けられる（例: プロジェクトA／B／C）。
- 社員やメンバーごとにユーザを作成し、各々の役割に応じて権限・アクセス可能なリソースを割り当てる（例: ユーザ1=すべての権限、ユーザ2=請求情報のみ、ユーザ3=閲覧のみ）。
- **グループ**を利用するとユーザへの権限を一括設定できる。
- **サービスプリンシパル**でシステム（例: システムA=リソース作成・削除）に権限を割り当てる。

### リソース管理機能
- **組織＞フォルダ＞プロジェクト**という階層でリソースを柔軟に管理できる。

| 階層 | 説明 |
|------|------|
| 組織（Organization） | 所属組織（会社名など）を表す。**リソース階層のルートノード** |
| フォルダ（Folder） | プロジェクトを階層的に分類・整理するためのリソース |
| プロジェクト | リソースの作業空間（最下層） |

### リソースID
> 【Tips】さくらのクラウドにおける認証とは関係ないが覚えておく。リソースIDは、さくらのクラウド上で**各リソースに一意に付与される12桁の数字**。請求・メンテナンス通知・サポートへの問い合わせ時に、対象リソースを特定する際に使用する。

## 2. さくらのクラウドにおけるアクセス管理

### アクセスレベル
- **プリンシパルの組み合わせごと**に、コントロールパネルやAPIでの操作範囲を制限できる。
- ユーザの役割に応じたアクセスレベルを設定することで、利便性やセキュリティを向上できる。
- **APIキー**については、**プロジェクトごとに作成されたAPIキー**に対してアクセスレベルを設定できる。

### アクセスレベルと操作権限
- リソース操作に関わる権限を制限可能。閲覧や設定の編集等、複数の権限レベルがある。
- 操作権限は**4段階**に分かれ、**数値の大きな権限レベルほど、より小さな権限を包含**する。
- （図）アクセスレベルの凡例: **アクセス不可 / リソース閲覧 / 電源操作 / 設定編集 / 作成・削除**。管理者がユーザ・アクセスレベル・プロジェクトを設定し、各ユーザに各プロジェクトへの権限を割り当てる。

### IAMポリシー（重要）
- さくらのクラウドにおける**リソースへのアクセス制御を定義するためのルール**。
- プリンシパルに対して「**何ができるか**」「**どのリソースに対して操作できるか**」を明示的に指定し、利便性やセキュリティを向上できる。
- **個別のアクセス権限をひとまとめにしたものを「ロール」と呼ぶ**。
- （例）ユーザに「リソースの作成・削除を許可」するIAMポリシー（ロール）を付与すると、新規にサーバを作成できる。

### ロール（リソース操作系）— アクセスレベルの段階（重要表）

| ロール | 対象プロジェクト内で許可される操作 |
|--------|--------------------------------------|
| KMS管理者 | KMSの全操作 |
| クラウドHSM管理者 | クラウドHSMの全操作 |
| シークレットマネージャ管理者 | シークレットマネージャの全操作 |
| リソース閲覧 | リソース閲覧 |
| 電源操作 | リソース閲覧で許可される全ての操作 ＋ サーバ/アプライアンスの電源操作 |
| 設定編集 | 電源操作で許可される全ての操作 ＋ 請求金額の増減が発生しないリソースの作成/削除操作 ＋ 作成済みリソースの設定変更 |
| 作成・削除 | 請求金額が増減する作業を含めた全ての操作 ＋ APIキーの発行/参照 |

> ⚠️ 試験頻出: 操作権限は **リソース閲覧 ＜ 電源操作 ＜ 設定編集 ＜ 作成・削除** の順で上位が下位を包含する4段階。

### ロール（各機能へのアクセス権限）
- 請求情報とイベントログの閲覧、および以下の各コントロールパネルへのアクセス権限は、以下のロールで付与する。
- ※リソース操作のアクセスレベルとは別系統の「各機能へのアクセス権限」である点に注意。

| 権限名 | 許可される操作 |
|--------|----------------|
| 請求閲覧権限 | プロジェクトの請求情報の参照 |
| オブジェクトストレージ | オブジェクトストレージへのアクセス |
| さくらのウェブアクセラレータ | さくらのウェブアクセラレータへのアクセス |
| さくらの専用サーバPHY | さくらの専用サーバPHYへのアクセス |
| AppRun | AppRunへのアクセス |
| 高火力DOK | 高火力DOKへのアクセス |
| APIゲートウェイ | APIゲートウェイへのアクセス |
| ワークフロー | ワークフローへのアクセス |
| イベントログ | イベントログの参照 |

### ロール（オーナー／セキュリティコントロール）

| ロール | 対象プロジェクト内で許可される操作 |
|--------|--------------------------------------|
| オーナー | プロジェクトを管理する権限 / 請求金額が増減する作業を含めた全ての操作 / APIキーの発行・参照 / プロジェクトの削除 / プロジェクトへのIAMポリシーの設定・更新 |
| セキュリティコントロール管理者 | すべての設定・評価・チケット・自動アクションを含む全操作の管理・更新が可能 |
| セキュリティコントロール運用者 | 設定変更は限定され、参照＋一部運用（チケット更新など）が可能 |
| セキュリティコントロール閲覧者 | 全項目の参照のみが可能 |
| セキュリティコントロールエージェント | セキュリティコントロールの内部処理用（**自動付与**） |

### IAMポリシーと各機能へのアクセス権限
- IAMポリシーでアクセスが許可されていない場合、コントロールパネルのアイコンをクリックしても**権限不足でエラーが表示される**（例: オブジェクトストレージへのアクセス未許可時）。

### コントロールパネル操作
- IAMポリシーの設定は、ホーム画面の**「IAMポリシー」メニュー**から行う。
- APIキーのアクセスレベルの設定は**「APIキー」メニュー**から行う。
- IAMポリシーおよびアクセスレベルの設定は、**会員IDでコントロールパネルにログインした際に行える**。
- プロジェクトに対するIAMポリシー設定では、(1) 適用する**プリンシパルを選択**し、(2) 付与する**ロールを選択**する。

### IDポリシー（重要）
- さくらのクラウドにおける**ユーザやグループへのアクセス制御を定義するためのルール**。
- プリンシパルに対して、**ID管理・認証・権限設計に関する操作**を明示的に指定し、権限管理の一貫性とセキュリティを向上できる。
- **パスワード変更といった、ユーザ操作権限の付与**に利用する。
- （例）ユーザAに「ユーザに対する全操作を許可」するIDポリシー（ロール）を付与すると、ユーザAは他ユーザ（ユーザB）のパスワードを変更できる。

> ⚠️ 違いに注意: **IAMポリシー＝リソースへのアクセス制御** / **IDポリシー＝ユーザ・グループ（ID管理・認証）へのアクセス制御**。

### ロール（ID系：IDポリシー）

| ロール | 許可される操作 |
|--------|----------------|
| ID管理者 | ・ユーザに対する全操作<br>・ユーザの2要素認証の操作（**ワンタイムパスワード、セキュリティキーの登録を除く**）<br>・ユーザグループに対する全操作<br>・IDポリシーに対する全操作<br>・SSOプロファイルの設定<br>・ユーザープロビジョニングの設定<br>・認証設定（パスワードポリシー、認証条件） |
| ID閲覧者 | ・ユーザの取得<br>・ユーザグループの取得 |

## 3. プロジェクトとユーザの利用（設計の考慮事項）

### プロジェクト分割の検討
- 提供サービスや開発プロジェクトごとにプロジェクトを分けることで、利用できるリソースを制限しセキュリティを強化できる。
- これにより、**異なるプロジェクトのリソース間で相互に接続できない構成**を実現する。
- 異なるプロジェクトのリソース間で通信させる必要がある場合は、**ローカルルータの利用を検討**する。
- 開発から本番リリースまでのライフサイクルをプロジェクトごとに分け、運用効率とリスク低減を実現する。
- 環境ごとにフォルダやプロジェクトを分けることで、本番環境への意図しない変更を防ぎ、安全な構成を実現する。

### アクセスレベルの検討
- 利用者の役割に応じて、各ユーザに基本的なアクセスレベルを設定する。
- ユーザごとに各プロジェクトに対するリソース操作のアクセスレベルを設定し、さらに利用サービスに応じて各コントロールパネルへのアクセス権限を設定する。
- ユーザグループを利用すると同様の権限を複数ユーザに一括設定でき、利便性・セキュリティを向上できる。
- ユーザが複数グループに所属する場合は、意図通りに権限が適用されているか確認する。
- ⚠️ **権限の合成ルール（頻出）**:
  - **リソース操作のアクセスレベル ＝「より強い権限」が優先**して適用される。
  - **各コントロールパネルへのアクセス権限 ＝「許可した権限の足し合わせ」**になる。

### 会員IDの使用方針
- 会員IDは**以下の必要な場合にのみ使用**し、通常のアクセス制御やリソース操作には**ユーザを使用**する。
  - プロジェクトの作成
  - イベントログでコントロールパネルへのログイン履歴の確認
  - サービス間接続の申し込み
  - ローカルルータに関する操作（ハイブリッド接続のローカルルータ作成、専用サーバPHY/さくらのVPS等における各サービス内スイッチへの接続/切断操作）
  - 会員情報の変更、支払方法の変更　など

> 【Tips】会員IDの設定変更は**会員メニュー**から行う（**コントロールパネルからは変更できない**）。また、セキュリティ上の理由により、**さくらのクラウド内のネットワークからは会員IDでのコントロールパネルログインが制限**されている。

### 認証方式の検討（2要素認証）
- 会員ID・ユーザの認証方式として、通常のパスワード認証に加え**2要素認証**を利用でき、認証経路を複数化してセキュリティを強化する。
- 2要素認証を有効化すると、ユーザ名＋パスワードに加え、**FIDO2対応デバイスを用いるセキュリティキーの登録**もしくは**一般的なTOTP方式によるワンタイムパスワードの入力**が必須となる。
- これによりパスワード漏洩・パスワード攻撃時の不正ログインリスクを軽減できる。
- ⚠️ **会員IDでのログインは2要素認証が必須**。一方、**クラウド上のユーザ認証方式は任意で設定**できる。

#### 認証の補助設定
- **パスワードポリシー**: 「8文字以上64文字以内の半角英数字」に加え、大文字/小文字/記号を含むよう定義できる。
- **認証条件**: 送信元IPアドレスやログイン期間などを制御できる。
- **ユーザロックアウト機能**: 所定時間内に連続して既定回数以上パスワードを誤入力すると、一定時間ログインできなくなる。
- 2要素認証の利用要件:
  - ワンタイムパスワード: **QRコード読み取り機能を備えたTOTP認証アプリ**がインストールされたデバイス（スマートフォン等）が必要。
  - セキュリティキー: **FIDO2対応デバイス**が必要。

> 【Tips】TOTP（Time-based One-Time Password）方式 = 事前提供の秘密鍵と現在時刻に基づき生成されるワンタイムパスワードを用いた認証方式。さくらのクラウドでは **Google Authenticator / Authy** での動作を確認済み。

> 【Tips】FIDO（Fast IDentity Online）= 非営利団体「FIDO Alliance」がパスワードに依存しない新しいオンライン認証技術の標準化を目指して策定・普及する認証技術。FIDO2対応デバイスにより、フィッシング・パスワード漏えいリスクを低減しつつ利便性と高いセキュリティを両立できる。

### シングルサインオン（SSO）連携機能
- SSO連携を有効化し、**SAML 2.0準拠の外部IdP**と連携することで、さくらのクラウドへの**認証の一元管理**が可能。
- SSOは**一度の認証で複数サービスへのログインを可能にする仕組み**。外部IdP（**Google Workspaceなど**）とSAML 2.0で連携し、管理画面を含む各種リソースへのアクセスを一元化できる。
- ⚠️ **SSO認証が有効となるのは、メールアドレスが登録されているクラウドユーザのみ**。
  - メールアドレス未登録のユーザはSSO認証されず、**さくらのクラウドのユーザ情報（2要素認証やパスワード）でログイン**する。

### ユーザープロビジョニング機能
- 有効化し**外部IdP（Microsoft Entra IDなど）**と連携することで、外部IdPで一元管理されているユーザ・グループ情報を**さくらのクラウドへ自動反映**できる。
- IdPで追加・変更・削除されたユーザ情報をクラウドに**同期**し、ユーザ管理を自動化。手動のユーザ登録・更新が不要となり、アカウントのライフサイクル管理を効率的かつ整合性のある形で実施できる。
- ⚠️ **同期で作成されたクラウドユーザはパスワードを保持せず、同一IdPとのSSOで認証**してログインする。
- ユーザグループもIdPの情報をもとに連携され、グループ単位でのアクセス制御・権限設定を簡素化できる。

> 比較メモ: **SSO＝認証の一元化（ログイン）** / **ユーザープロビジョニング＝ユーザ・グループ情報の自動同期（アカウント管理）**。例示されたIdPは SSO=Google Workspace、プロビジョニング=Microsoft Entra ID。

## 4. シングルサーバコントロールパネルの利用

- 管理者が**サーバ1台ごとに個別に制御するだけの権限を持ったAPIキー**を発行し、利用者がそのAPIキーでログインすると、**対象のサーバ1台だけ**を操作できる機能を持つコントロールパネル。
- 用途: 保守委託先の外部業者によるメンテナンス用、学校での学生への演習用など。ユーザ・プロジェクトを発行するより**手軽に、サーバ1台操作に最小限の機能と操作権限**を備えた環境を提供できる。
- ⚠️ 操作可能な機能は**リソース閲覧とサーバ操作のみ**。サーバ操作は**電源操作とリモートコンソール操作**が許可される。
- ログインは、発行された**シングルサーバAPIキーのアクセストークン・アクセストークンシークレットの組**を入力して行う。

> 【Tips】「**シングルサーバAPIキー**」というAPIキーの種類を設定し、アクセスレベルと紐付け先サーバを設定することで、シングルサーバコントロールパネル用のAPIキーを発行できる。

## 5. ログの取得と保管

### 考え方
- 不正アクセスやウィルス感染等の**セキュリティインシデント**発生時に各リソースの調査・分析ができるよう、必要なログを取得し適切な期間保管する。
- さくらのクラウドでは**標準でイベントログが取得される**。一部リソースでは**ログ表示機能やsyslog転送機能**が提供されている。

### イベントログ（重要）
- **コントロールパネルとAPIの操作履歴、およびログイン履歴**をイベントログで確認可能。
- リソース操作の履歴を確認でき、各操作には**ソースIPアドレスと共に実行日時**が記録される。
- 記録されるイベントの種類は**クラウドマニュアル**で確認できる。
- 確認場所: コントロールパネルのホーム画面の**「イベントログ」メニュー**。

> 【Tips】オートスケール機能利用時は、各オートスケール設定の詳細画面の**「ログ」タブ**で実行ログを確認でき、ローカルPCにファイルとしてダウンロードも可能。

#### イベントログの保管（頻出）
- ⚠️ イベントログで確認できる履歴は**過去一年間分のみ**。それより前を保持したい場合は利用者が**CSV形式で保存**する必要がある。
- 「CSVに保存」ボタンで、検索結果を反映したCSVファイルをローカルPCに保存できる。
- ⚠️ **CSVでダウンロードできるイベントログの件数は最大1000件**。

### ネットワークのログ（VPNルータ）
- VPNルータのログ表示機能で、**VPN・ファイアウォール・セッション統計情報**のログを取得できる。
- ⚠️ コントロールパネル上で確認できるのは**最新の100件のみ**。永続的に保管したい場合は**syslog転送機能**を使用する。
- ファイアウォールのログは、**ログ記録が有効化されたルールにマッチした通信**がロギング対象。不要な大量取得は検索効率低下やストレージ利用量増加につながるため、必要なログのみ取得する。

### サーバのログ
- ⚠️ **サーバのOSは利用者の責任範囲**。サーバ内部で記録されるログはさくらインターネットから提供されないため、**利用者側の責任で取得・保管**する必要がある。
- パブリックアーカイブから作成したサーバには、OSの標準設定により初期設定で取得されるログが存在する。利用するパブリックアーカイブの仕様を確認し、必要なログを取得・保管する。
- 一般的に、セキュリティに関するOS上のログとして**監査ログやセキュリティログ**の取得を検討する。
- **サーバのアクセスログ**: 接続元クライアントの情報をサーバ側ログとして取得することを検討（OSへのリモートログインログ、WebサーバへのHTTPアクセスログ等）。

> 【Tips】**エンハンスドロードバランサ**使用時は実サーバへのプロキシ時にHTTPヘッダが付加され、**ウェブアクセラレータ**利用時はオリジンサーバへの接続時にリクエストヘッダが付与される。これらのヘッダ情報を実サーバ／オリジンサーバ側のアクセスログに出力させ、接続元IPアドレス等を記録することを検討する。

### コンテンツ配信のログ（ウェブアクセラレータ）
- ユーザーからのリクエスト内容や応答ステータス等を記録したアクセスログを、**指定先のオブジェクトストレージに定期的に自動アップロード**できる。
- アクセスログが外部に公開されないよう、**アップロード先オブジェクトストレージの権限設定に注意**する。

## 6. サーバアクセス手段の検討

### 考え方
- 悪意のある第三者による**通信の盗聴リスク**を考慮してアクセス手段を選択する。
- ネットワーク経由でリモートアクセスする際は、**SSHやRDPを用いた暗号化通信**の利用を検討する。SSH接続時は**公開鍵認証**を利用してセキュリティレベルを高める。
- さくらのクラウドでは、リモート接続せずに**コンソール接続でウェブブラウザから直接OSを操作**することもできる。

> 【Tips】サーバ作成・起動直後はOSのセキュリティ設定が不十分で不正アクセスリスクが高まることがある。**サーバ作成時、または作成後の起動前にパケットフィルタを適用**すると、不要ポートの閉塞やアクセス元ネットワークの制限をした状態でサーバを起動できる。

### 公開鍵認証
- 安全なリモート接続のために用いる方式。**公開鍵をサーバに置き、クライアント側に秘密鍵を用意**し、パスワードを使わずに安全にログインできる。
- 辞書攻撃などによる不正ログインリスクがあるパスワード認証とは異なり、**秘密鍵が盗まれない限り認証を突破されるリスクが大幅に低減**される。

### 公開鍵の管理
- コントロールパネルのホーム画面の**「公開鍵」メニュー**で利用者の公開鍵を管理できる。
- サーバ作成時に登録済みの公開鍵を指定し、自動的にサーバ内に設置できる。
- サーバ作成・ディスク追加・ディスク修正時の**「公開鍵」ラジオボタン**で事前登録した公開鍵を選択できる。
- ⚠️ **「パスワード/チャレンジレスポンスでのSSHログインを許可しない」を有効化**してサーバを作成すると、SSHの認証方式は**公開鍵認証のみ**となる。
- ユーザが**GitHubに登録しているSSH公開鍵**を選択することも可能。

## 7. 試験対策・要点チェック

- [ ] 会員IDは**アルファベット3文字＋数字5文字**、**管理者権限**を持ち、作成した**全プロジェクトにアクセス可能**。
- [ ] プリンシパルの三種類 = **ユーザ・グループ・サービスプリンシパル**。サービスプリンシパルはAPIアクセス（自動処理・システム連携）用。
- [ ] リソース階層 = **組織＞フォルダ＞プロジェクト**。リソースIDは**12桁の数字**。
- [ ] **IAMポリシー＝リソースへのアクセス制御** / **IDポリシー＝ユーザ・グループ（ID管理・認証）へのアクセス制御**。権限の束が**ロール**。
- [ ] リソース操作の4段階 = **リソース閲覧 ＜ 電源操作 ＜ 設定編集 ＜ 作成・削除**（上位が下位を包含）。
- [ ] 権限合成: アクセスレベルは**より強い権限が優先**、各コントロールパネルへの権限は**足し合わせ**。
- [ ] **会員IDログインは2要素認証必須**、ユーザの認証方式は任意。2要素認証は**FIDO2セキュリティキー or TOTPワンタイムパスワード**。
- [ ] **SSO＝SAML 2.0で外部IdP連携（例: Google Workspace）、認証の一元化**。有効になるのは**メールアドレス登録済みユーザのみ**。
- [ ] **ユーザープロビジョニング＝外部IdP（例: Microsoft Entra ID）とユーザ/グループ情報を自動同期**。同期ユーザは**パスワードを持たずSSOで認証**。
- [ ] シングルサーバコントロールパネルは**サーバ1台のみ**、機能は**リソース閲覧＋サーバ操作（電源操作・リモートコンソール）**、**シングルサーバAPIキー**でログイン。
- [ ] イベントログは**操作・ログイン履歴＋ソースIP＋実行日時**を記録。確認できるのは**過去1年分**、CSVは**最大1000件**。
- [ ] VPNルータのログはCP上で**最新100件**、永続保管は**syslog転送**。サーバOSのログは**利用者の責任範囲**。
- [ ] リモートアクセスは**SSH/RDPの暗号化通信**＋**公開鍵認証**。「パスワード/チャレンジレスポンスでのSSHログインを許可しない」で**公開鍵認証のみ**に。GitHub登録のSSH公開鍵も選択可。
