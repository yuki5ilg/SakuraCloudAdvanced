## 1. 責任分界点

- **責任分界点**とは、さくらインターネットがサービス継続に責任を負う範囲と、利用者の責任により運用する範囲を定める**境界**のこと。

### さくらインターネットの責任範囲
- 物理的な機器（サーバ・ストレージ装置など）やクラウド基盤（コントロールパネル・APIなど）を構成する**ハードウェア部分**。
- ハイパーバイザやクラウド基盤（コントロールパネル・APIなど）を構成する**ソフトウェア部分**。
- **PaaS/SaaS系**のハードウェアとソフトウェアを一体として提供するサービス。

### 利用者の責任範囲
- API・コントロールパネルを通じた、仮想サーバやアプライアンスなどの**設定変更作業**。
- **OSの設定**、その上で実行されるミドルウェア・アプリケーション、**アクセス権の管理**。
- **OSやその上で動作するソフトウェア**。次を含む:
  - サーバ上のOSの設定・管理・運用・保守・データ
  - 各種サーバソフトウェアのインストールや設定
  - ディスク上のファイルシステムの設定／ファイルシステム上のデータ
  - 複数NIC搭載時、スイッチごとにセグメントを割り当ててルータ化する際の各リソース間のネットワーク接続設定
  - APIを操作する利用者独自のプログラム
  - さくらインターネット責任範囲外の不具合（利用者サーバが停止しても、調査でホストサーバに異常が見られなかった場合など）

> 図（責任分界点）では、最上層の「**利用者業務データ**」が責任範囲の境界をまたいで配置され、下層ほどさくらインターネットの責任範囲（HW・OS基盤・PaaS/SaaS）、上層ほど利用者の責任範囲（アプリケーション・ミドルウェア・OS等）となるレイヤ構造で示される。

### 責任範囲についての帰結
- さくらインターネットの責任範囲部分はさくらインターネットの運用責任となり、その**瑕疵（かし）**により利用者運用部分に影響が及んだ際には、**約款やSLAなどの定めに従い、正常な状態に復旧する義務を負う**。
- 利用者の責任範囲部分は基本的に利用者の責任のもとで運用する必要があり、**さくらインターネットの窓口に問い合わせてもサポートできない**。

## 2. 品質保証（SLA）

- さくらのクラウドは品質保証として **SLA（Service Level Agreement; サービス品質保証規約）** を定めている。
- ⚠️ **月間のサーバー稼働率を 99.95% 以上保証**することをSLAで定めている。

### 月間稼働率の算出（逐語）

```
月間稼働率＝(月間総稼動時間−累計障害時間)÷月間総稼動時間×100
```

- **月間総稼働時間** … 暦月の初日から末日までの期間。
- **累計障害時間** … 以下のいずれかの状態が生じたことを、さくらインターネットがサービスサイトの障害情報で報告した時間、または利用者がこれを証明できる時間。
  - サーバの**電源が入らない**状態
  - サーバに**全くアクセスできない**状態
  - サーバに接続されている**ディスクに全くアクセスできない**状態

### 稼働率に伴う減額
- SLA適用サーバが定められた稼働率を満たさない場合、当該稼働を満たさなかった部分に相当する利用サービスの**利用料金を減額**できる。
- 減額を希望する場合は、**利用者による減額申請が必要**。
  - 影響を受けたサーバの**リソースID**やサーバの稼働時間等に関する情報を**サポート宛にメール**する。

## 3. 設備の冗長性

### ホストサーバの冗長性
- さくらのクラウドのサーバは**仮想サーバ**として提供され、収容される**ホストサーバは冗長化**されている。
- ホストサーバで異常が発生し停止した場合、収容された仮想サーバも同時に停止するが、その後**自動復旧プログラム**により**他のホストサーバで起動が試みられる**。
- **サーバとディスクは分離**されており、ホストサーバ障害に伴うディスク内のデータ消失はない。
  - ただし、突発的なOS停止による**論理的なデータ破損**の可能性はある。

### ストレージの冗長性
- ディスクを提供するストレージ機器は冗長構成。**アクティブ側コントローラの異常検知時に自動的にスタンバイ側へ切替**えてサービス継続。
- ストレージ機器内のディスクは **RAID** による冗長構成。**ディスクが同時に数台程度故障してもサービス継続性に影響しない**。

### ネットワークの冗長性
- ストレージネットワークや、仮想サーバが外部と通信するネットワークなど**重要な経路はすべての回線・ネットワーク機器・インタフェース等が2重化**。
- 2重化部分に障害が発生した場合、**瞬時に片側へ切替**わり、影響を最小限に抑える。

## 4. 障害とメンテナンス

### 定義
- **障害** … 機器の突発的な故障やコントロールパネルなどの不具合により、**通常の品質でサービスが提供できなくなる状態**。
- **メンテナンス** … 構成するハードウェアやソフトウェアについて、**あらかじめ予定を決定した上で**機器の交換やソフトウェアアップデートなどを行うもの。

### サービス稼働情報
- 稼働状況は **https://status.cloud.sakura.ad.jp/** で確認できる。
- 定期監視で予期しないステータスが記録された場合、マークが表示される。

### 障害発生時の対応
- クラウド基盤は **24時間監視**され、障害発生時はさくらインターネットにより迅速に復旧対応される。
- **利用者個別のサーバ／ディスクのみの障害**は、さくらインターネットで検知が難しいケースがあり、その場合は**利用者からサポートに問い合わせ**る必要がある。
- 問い合わせ時は、調査・復旧がスムーズに行えるよう**障害対象リソースID等の情報**を含めて連絡する。

### メンテナンス発生時の対応（連絡）
- 利用者に影響を与えるメンテナンスを予定している場合、事前に「**障害・メンテナンス連絡ポリシー**」の基準に従い対象利用者へ**事前連絡**される。
- 各リソースごとに定められた手順に従い、**利用者による事前作業が必要となる場合がある**。
- 障害・メンテナンス連絡ポリシー: https://manual.sakura.ad.jp/cloud/support/notice-policy.html

### セキュリティインシデント発生時
- 利用者に影響する恐れのある情報セキュリティインシデント発生時は、**さくらのサポート情報による公開やメール通知**等で利用者へ連絡される。
- サポート情報: https://help.sakura.ad.jp/

## 5. 障害とメンテナンス発生時の連絡

- 障害・メンテ発生時は、影響度合い・発生期間・内容などに応じ、適切な頻度・手段で利用者へ案内。アナウンス発出基準は「障害・メンテナンス連絡ポリシー」に記載。

### 障害発生時のアナウンス（種類: ウェブ掲載／メール）

| リソース種別 | アナウンス方針 |
|--------------|----------------|
| サーバ／アプライアンス | ウェブ掲載・メール |
| ストレージ（ディスク/アーカイブ/一部アプライアンス） | ウェブ掲載 |
| ネットワーク | ウェブ掲載 |
| コントロールパネル・API | ウェブ掲載 |

### メンテナンス発生時のアナウンス（種類: ウェブ掲載／メール／コントロールパネル）

| リソース種別 | 初回告知日（メンテナンス日基準） | アナウンス方針 |
|--------------|-------------------------------|----------------|
| サーバ／アプライアンス | おおむね**1か月前** | ウェブ掲載・メール・コントロールパネル |
| ストレージ（ディスク/アーカイブ/一部アプライアンス） | おおむね**2週間前** | ウェブ掲載 |
| ネットワーク | おおむね**2週間前** | ウェブ掲載 |
| コントロールパネル・API | おおむね**2週間前** | ウェブ掲載 |

### ウェブ掲載によるアナウンス
- 「メンテナンス・障害情報」に掲載。**現在・過去の障害/メンテ情報、将来のメンテ予定**を確認可能。コントロールパネルのホーム画面上でも確認できる。
- メンテナンス・障害情報: https://help.sakura.ad.jp/status/

### メールによるアナウンス
- ホストサーバで障害発生時、**会員IDに登録のメールアドレス、または緊急連絡用メールアドレス**に通知。
- **緊急連絡用メールアドレスが1つでも登録されている場合は、会員IDのメールアドレスには通知されず、緊急連絡用にのみ通知**される。
- 緊急連絡用に加えて会員IDメールにも通知したい場合は、緊急連絡用に会員IDのメールアドレスを登録する必要がある。

### 緊急連絡用メールアドレス
- 会員ID登録メールとは別に、**さくらのクラウド関連に限定**した障害情報やメンテ予告の連絡先として任意のメールを登録できる。
- コントロールパネルの「**オプション**」画面から設定。
- 設定は**プロジェクト単位**。複数プロジェクトで共通の連絡先でも、各プロジェクトごとに設定が必要。
- **1つのプロジェクトにつき最大10個まで**登録可能。

### ホストメンテナンス予定確認画面
- 利用者のサーバ／アプライアンスを収容する**ホストサーバのメンテナンス情報を一覧表示**。
- ログイン中の会員ID／プロジェクトが利用中のサーバ/アプライアンス収容ホストの情報を一覧化。
- コントロールパネルのホーム画面左メニュー「**ホストメンテナンス**」から確認。

### データベースアプライアンスのメンテナンス（通知）
- **DBエンジンの再起動が発生する場合はコントロールパネルで通知**される。
- 管理ソフトウェアのバージョンアップやアプライアンス仕様変更に伴う修正のためメンテが発生することがある。

## 6. メンテナンス発生時の対応（利用者作業）

### ホストサーバのメンテナンス
- メンテナンス連絡があった場合、**あらかじめ利用者側で対象サーバ／アプライアンスの停止と起動操作**を行い、起動先ホストを変更する。
- **停止→起動の順**で操作すると、対象は自動的に**健全なホストサーバ上で起動**される。
- これにより、さくらインターネットの定めたメンテナンス日時での**対象サーバの停止は発生せず**、利用者都合の良いタイミングでホスト変更作業を実施できる。

### 専有ホストのメンテナンス
- メンテナンス連絡があった場合、**利用者側で対象専有ホスト上のサーバを停止・起動**し、稼働する専有ホストを変更する。
- メンテ発生時は**代替の専有ホストが割り当てられ**、1つの専有ホスト契約に対して**一時的に2台のホストサーバが割り当てられた状態**となる。
  - ただし、収容可能な**CPUコア数やメモリは1台分を上限**として計算される。
- メンテ通知以降に専有ホスト上でサーバを起動すると、**新たに割り当てられた専有ホスト上で起動**する。

### データベースアプライアンスのメンテナンス
- 管理ソフトウェア更新に伴うアップデートの場合: 対象DBアプライアンスの詳細画面から「**アップデート**」ボタンを押下。
- **再起動が必要なアップデート**の場合: 「**電源操作**」→「**DBインスタンス再起動**」を実行。

## 7. システムの監視

### 考慮事項
- システムの正常性を監視し、異常検知時に管理者へ通知することで**障害を早期検知**。あわせて**障害検知後に迅速復旧できる体制・環境**も考慮する。
- 障害を引き起こす可能性のある異常を検出し、**未然に障害を防ぐ**ことも必要。システム見直しには**過去のアクティビティやログの収集・運用**が必要で、監視の仕組みとあわせて検討する。
- **監視対象・監視項目・監視手段**を検討。サーバやアプリケーションを対象に、稼働状況・リソース使用状況に加え、**提供サービスが正常に利用可能かどうか**も監視に含める。
- 監視手段の選択肢: **シンプル監視**／利用者契約の外部サービス／マーケットプレイス提供の監視サービス／利用者構築の監視サーバ。

## 8. シンプル監視の利用

- 監視サーバ構築の手間・運用コスト削減のため、**シンプル監視**を検討する。
- 監視可能項目: ネットワーク疎通監視（**ping, tcp**）、アプリケーション監視（**http, smtp** など）。要件に適した項目を選択。
- ⚠️ **シンプル監視はさくらのクラウドのグローバルネットワークから監視が行われる**点に注意。監視対象サーバがローカルネットワークに所属する場合、接続元ネットワークからアクセス可能な構成が必要（例: クラウド内部のプライベートネットワークへの**ポートフォワーディング**）。

### 通知方法
- 通知方法は**メール／Webhook**のいずれか、または両方。
- Webhook選択時は通知先がメンテ・障害で受け取れない場合があるため、**メールもあわせて設定することが推奨**。

> 【Tips】Webhook注意: 通知先URLへの通知が失敗すると**自動的に通知が無効化**される。また同一Webhookに短時間で多くの通知が発生すると、各サービスのAPI制限により**通知が遅延または届かない可能性**がある。

### シンプル監視の限界とアクティビティの活用
- シンプル監視だけでは、**サーバのリソース監視**や**監視結果に基づく自動アクション**の実装ができない。
- **アクティビティやAPI**を使い利用者で監視の仕組みを構築する必要がある。例: APIでサーバの**アクティビティ**から**サーバ負荷・ディスクI/O・トラフィック**などの値を取得し、値に応じた通知・自動アクションを実現。

> 【Tips】ルータ＋スイッチのアクティビティ: 確認できるトラフィックは**サンプリングのため帯域/転送量は推定値**。**Ethernet header込みでのカウント**のため、サーバ側計測値より若干大きくなる傾向。

### 利用者で構築する監視サーバ
- シンプル監視の仕様が要件に合わない場合、マーケットプレイスの監視サービスや利用者構築の監視サーバを検討。
- 監視サーバは**クラウド内外のいずれにも配置可能**。他社の外部サービス利用も選択肢。
- 一部アプライアンスは **SNMPエージェント機能**を提供。必要に応じSNMP監視を検討。
- ⚠️ クラウド内で監視サーバを運用する場合、**クラウドのネットワーク障害時に監視サーバから管理者への通知が届かなくなる可能性**がある。**シンプル監視やクラウド外部からの監視を併用**することを検討。

## 9. 冗長構成と分散配置（単一障害点をなくす）

- システム全体が停止しないよう、冗長構成や分散配置で**単一障害点をなくし**サービス継続性を高める。
- 冗長構成・分散配置は相応のコストが必要。さくらインターネットの品質保証・設備冗長性で維持される可用性を前提に、利用者が求める可用性レベルを満たす構成を選択する。
- **BCP（事業継続計画）／DR（災害復旧）** を考慮し、外部接続サーバや消失してはならないデータなど特に重要な部分を、**地理的に十分離れた複数のデータセンターに分散配置**することを検討。
  - **ブリッジ接続・ハイブリッド接続・負荷分散**を可能にするサービス／リソースを使い、リージョン間で冗長構成・地理的分散を実現。
  - 1箇所のデータセンターが完全に機能停止しても、サービス停止やデータ消失を防ぐ設計が可能。

## 10. リージョン間の冗長構成

- リージョン間冗長により、データセンターやネットワークの障害が発生してもサービスを継続し高い可用性を実現。

### さくらのクラウド構成
- クラウド内でリージョン間構成をとる場合、**東京リージョンと石狩リージョン間**で冗長構成。各リージョン内のスイッチを相互接続し、**プライベートネットワーク環境でL2通信を行うためにブリッジを利用**。
- リージョン間でDBの冗長構成をとる場合は **データベースクラスタ** の利用を検討。
  - **3つのデータベースノードを3つのゾーン（複数のリージョン）に配置**してDR構成を実現。
  - **1ノード障害**でも、正常なノードでDB運用を継続できる。
  - ⚠️ **2ノード障害で正常ノードが1つになると、DBの読み込みと書き込みが停止**する。
- DBアプライアンスを使わず、利用者側で**異なるゾーンに複数のDBサーバを構築し同期**する構成も検討可能。

### 他サービスを併用する構成（利用可能地域）
さくらインターネットの各サービスは利用可能地域が異なる。複数サービスに跨り地理的分散を実現できる。

| サービス | 地域 | 備考 |
|----------|------|------|
| クラウド | 東京、石狩 | |
| VPS | 東京、大阪、石狩 | **for Windows は東京のみ** |
| 専用サーバPHY | 石狩 | |
| 高火力PHY | 石狩 | |
| ハウジング | 東京、大阪、石狩 | |

### 接続方式の使い分け
- **ハウジングで利用する機器と他サービス間**をプライベートネットワークを介してL2接続する場合 → **ハイブリッド接続**。
- **ハウジングを含まないサービス間**の接続 → **ブリッジ接続**。

### 冗長構成に用いるリソース
- リージョン間冗長では**グローバルリソースである GSLB やエンハンスドロードバランサ**を選択することを検討。
  - ⚠️ **ゾーン内リソースであるロードバランサ**を選択すると、対象ゾーンを運用するDC/ネットワークの障害時に利用へ影響が出る可能性がある。
- エンハンスドロードバランサでリージョン間冗長をとる際は、**エンハンスドロードバランサ自体もリージョン間冗長にするため、エニーキャストを選択**することを検討。
- オブジェクトストレージ利用時は、**リージョン間レプリケーション（CRR）** の有効化を検討。
  - ⚠️ **CRRは非同期方式**のため、複製元で作成したオブジェクトを複製先で**リアルタイム参照することはできない**。
  - ⚠️ **CRR設定前に作成したオブジェクトは複製されない**。

## 11. 単一ゾーン内の冗長構成

- 単一ゾーン内でサーバの冗長構成をとり、単一サーバ障害でもサービスを継続し可用性を維持。

### 冗長構成に用いるリソース
- 単一ゾーン内のサーバ冗長には **GSLB／エンハンスドロードバランサ／ロードバランサ** の利用を検討。マーケットプレイスの仮想アプライアンスで多機能ロードバランサも利用可能。
- ロードバランサ使用時は、ゾーン内で **VRRPによるロードバランサの冗長構成**が可能なプランを検討。
- **GSLBとエンハンスドロードバランサは、標準でゾーン内冗長構成**がとられている。

### VPNルータの冗長化
- ゾーン内で **VRRPによるVPNルータの冗長構成**が可能なプランを検討（対象は**プレミアム/ハイスペックプラン**）。
- プラン選択時は障害発生時の**復旧時間の目安**を考慮する。

| プラン | 対象の機能 | 復旧時間の目安 |
|--------|-----------|----------------|
| スタンダード | サイト間VPN、L2TP/IPsec、PPTP | 10～15分程度 |
| スタンダード | NAT、PPTP、DHCPサーバ | 1分程度 |
| プレミアム/ハイスペック | サイト間VPN、L2TP/IPsec、PPTP | 10～15分程度 |
| プレミアム/ハイスペック | NAT、PPTP、DHCPサーバ | **15秒程度** |

> ※原文表記は「LT2P/IPsec」だが、一般的な L2TP/IPsec を指すと解される（※要確認）。

### サーバの冗長化（VRRP）
- スイッチ、またはルータ+スイッチに接続されたサーバは **VRRPを使用した冗長構成が可能**。ロードバランサを使わずに冗長化したい場合に検討。
- ⚠️ **VRRPによるサーバ冗長構成はさくらのクラウドの機能として提供されておらず、利用者にて実装**する必要がある。
- さくらのクラウドの仕様上、頻繁な切り替えを避けるため、**VRRP Advertisement送出間隔を5秒以上**に設定することが推奨。

### NFSアプライアンスの冗長化
- ⚠️ **NFSアプライアンスはVRRPによる冗長構成をとれず、シングル構成**となる点に注意。
- 稼働ホストで障害発生時は自動復旧プログラムが作動し自動再起動するが、**起動完了・復旧までの目安は10～15分程度**。
- 冗長構成が必要な場合は、**利用者でNFSサーバを構築し冗長化**する。

### データベースアプライアンスの冗長化
- DBアプライアンスの**冗長化オプション**の利用を検討。
- **主系DB停止時の自動切り替え時間の目安は約30秒程度**。
- ⚠️ 冗長化オプション利用時は**プラン変更とクローン機能が利用できない**。柔軟性の高いDB運用が必要な場合は、利用者側で構築したDBサーバの運用を検討。

## 12. 他社クラウドとの冗長構成（マルチクラウド）

- さくらのクラウドと他社クラウド間で冗長構成（**マルチクラウド構成**）をとることで、さくらのクラウドで障害が発生してもサービスを継続し高い可用性を実現。
- マルチクラウド構成では他社クラウドサービスの設計にも**高度な知識が必要**。検討事項は広範囲にわたり、管理者には各サービス仕様の十分な理解が求められる。
- クラウド間の**閉域網接続**を比較的簡単に実現したい場合は、次の利用を検討:
  - **AWS接続オプション**
  - **プライベートリンク for BBIX、OCX by BBIX**
  - **プライベートリンク for NTTドコモビジネス** 等

> 【Tips】SSO連携: さくらのクラウドは**シングルサインオン（SSO）連携機能**を利用でき、他社クラウドと連携して認証運用を効率化できる。ただしSSO連携を有効にすると、クラウドユーザは**SSO認証のみ利用可能**となるため、外部クラウドで障害が発生した場合の影響を考慮した上で利用を検討する。

## 13. リソースの分散収容

- 複数のサーバやディスクが冗長構成をとっている場合、各リソースが配置されるホストサーバやストレージを分散させ、一つの障害でもサービスを継続し可用性を維持する。

### サーバの分散収容
- ⚠️ 電源停止状態の複数サーバを同時起動すると、起動処理が並行し**各サーバが同一ホストサーバに収容されてしまう可能性**がある。
- **特殊タグ `@group`** を付与するとサーバをグループ化し起動ホストを分離できる。**異なるグループ名のタグが付与されたサーバはそれぞれ別ホストで起動**されるため、冗長構成サーバの起動先を分けたい場合に利用を検討。

### ディスクの分散収容
- 新規ディスク作成時に、ディスク作成画面で「**ストレージ分散**」にチェックを入れて既存ディスクを選択すると、指定したディスクとは**別のストレージに収容**できる。
- 同じサーバに接続されたディスクをそれぞれ別ストレージに収容し可用性を高めることを検討。

## 14. バックアップの取得（システム復旧の準備）

### 考慮事項
- システム障害・データ消失時に迅速復旧し影響を最小化するため、システム・データのバックアップを取得し必要期間保持する。
- システム復旧の手順を用意し、想定する **RPO（目標復旧時点）** と **RTO（目標復旧時間）** を達成できる状態かを**復旧テスト**で確認し、手順の妥当性を確認する。

### バックアップ手段
- さくらのクラウドのバックアップ: **自動バックアップ機能**による定期的なアーカイブ取得、**DBアプライアンスのバックアップ機能**。要件に合わない場合はマーケットプレイスのバックアップサービス、または利用者構築のバックアップサーバ＆ストレージを検討。
- 各リソースの**クローン機能**でリソースごと複製する選択肢もある。
- ⚠️ **NFSアプライアンスはバックアップ機能が提供されていない**。データバックアップは利用者にて取得する必要がある。

### バックアップの保存先と注意点
- ⚠️ **自動バックアップ機能のアーカイブも、DBアプライアンスのバックアップ機能で取得したデータも、いずれも同一ゾーン内に保持**される。
- リージョン間冗長で障害時にメインサイトのデータでバックアップサイトを復旧させる場合、平常時にメインサイト→バックアップサイトへ**データをコピー**する必要がある。
  - ⚠️ **DBアプライアンスのバックアップ機能で取得したデータは単独でコピーできない**。
  - 対策: バックアップ保存先として同一ネットワーク上の**NFS領域**を指定してバックアップファイルを取得するか、利用者側で**DBのダンプ**を取得してコピーする等を検討。
  - 想定例: DBアプライアンスとは**異なるゾーンにNFSアプライアンスを配置し、ブリッジ接続**してバックアップを保持する構成。
- ゾーン間のコピーを自動化したい場合は、利用者側でAPI等を使った仕組みを実装する。

## 15. 試験対策・要点チェックリスト

- [ ] **SLAの月間サーバー稼働率保証は 99.95% 以上**。
- [ ] 月間稼働率＝**(月間総稼働時間−累計障害時間)÷月間総稼働時間×100**。累計障害時間は「電源が入らない／全くアクセスできない／ディスクに全くアクセスできない」状態。
- [ ] 稼働率未達時の**減額には利用者の申請が必要**（リソースID等をサポートへメール）。
- [ ] **責任分界点**: さくら＝HW・基盤SW・PaaS/SaaS、利用者＝設定変更・OS・ミドル・アプリ・データ・アクセス権。
- [ ] 設備冗長性: ホストサーバ障害時は**自動復旧プログラムが他ホストで起動**。**サーバとディスクは分離**（データ消失なし／論理破損の可能性あり）。ストレージは**RAID＋コントローラ自動切替**、重要NWは**2重化**。
- [ ] 障害アナウンス＝ウェブ掲載/メール、メンテアナウンス＝ウェブ掲載/メール/コントロールパネル。**サーバ/アプライアンスのメンテ初回告知はおおむね1か月前**、他は2週間前。
- [ ] **緊急連絡用メールが1つでもあると会員IDメールには通知されない**。**プロジェクト単位**で**最大10個**まで登録。
- [ ] ホストメンテ対応は**停止→起動操作で健全ホストへ自動移動**。専有ホストは**一時的に2台割当（上限は1台分）**。
- [ ] **シンプル監視はグローバルネットワークから監視**（ローカル対象はポートフォワーディング等が必要）。**ping/tcp/http/smtp**。リソース監視・自動アクションは不可→アクティビティ/APIで実装。
- [ ] Webhookは**失敗で自動無効化**、メール併用推奨。
- [ ] リージョン間冗長は**東京-石狩**、L2は**ブリッジ**。**DBクラスタは3ノード/3ゾーン**、**2ノード障害で読み書き停止**。
- [ ] リージョン間冗長は**GSLB/エンハンスドLB（グローバル）**。エンハンスドLBは**エニーキャスト**。オブジェクトストレージは**CRR（非同期・リアルタイム参照不可・設定前データは非複製）**。
- [ ] 単一ゾーン冗長: **GSLB/エンハンスドLBは標準でゾーン内冗長**。VPNルータは**プレミアム/ハイスペックでVRRP冗長**（NAT等の復旧目安15秒）。**サーバVRRPは利用者実装**（Advertisement間隔5秒以上推奨）。
- [ ] **NFSアプライアンスはシングル構成**（復旧目安10～15分、バックアップ機能なし）。**DBアプライアンス冗長化は自動切替約30秒、プラン変更・クローン不可**。
- [ ] マルチクラウド閉域接続: **AWS接続オプション**、プライベートリンク for BBIX/OCX by BBIX/for NTTドコモビジネス。SSO連携有効化で**SSO認証のみ**になる点に注意。
- [ ] 分散収容: サーバは**特殊タグ `@group`**、ディスクは作成時の「**ストレージ分散**」。
- [ ] バックアップは**同一ゾーン内保持**。**RPO/RTO**を復旧テストで検証。DBアプライアンスのバックアップは**単独コピー不可**（NFS領域指定やダンプで対応）。
